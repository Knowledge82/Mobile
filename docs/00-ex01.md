## 1. Задача и с чего начать

### 1.1 Условия сабжа

- **Папка сдачи:** `mobileModule00`
- **Файлы для сдачи:** `ex01` и все необходимые файлы
- **Запрещённые функции:** нет
- **Подсказка сабжа:** взять код из предыдущего упражнения и создать **новый** проект `ex01`.

### 1.2 Проблема

Нужно добиться, чтобы текст, показанный в приложении, менялся при нажатии кнопки:

- при первом нажатии вместо исходного текста показывается **«Hello World!»**;
- при каждом следующем нажатии текст **переключается** между исходным и «Hello World!».

### 1.3 Требования

**Функциональные:**

1. Основа берётся из ex00: текст и кнопка под ним, оба по центру.
2. Первое нажатие показывает «Hello World!».
3. Каждое следующее нажатие переключает текст туда и обратно.

**Нефункциональные:**

1. Адаптивность сохраняется (требование ex00 остаётся основой).
2. `flutter analyze` без замечаний, `flutter test` зелёный.
3. Проект `ex01` самостоятельный: `ex00` не меняется.

> Вывод в консоль («Button pressed») в тексте ex01 отдельно не требуется. Оставляем его или нет, решаем осознанно: см. [решение 3](#решение-3-оставлять-ли-вывод-в-консоль).

### 1.4 Что не входит в задачу (non-goals)

- Анимации смены текста.
- Сохранение состояния между запусками приложения.
- Больше двух вариантов текста.
- Оливковый фон под текстом и прочие украшения на картинках сабжа (сабж сам предупреждает, что демо может содержать необязательные дополнения).

### 1.5 Критерии успеха

- [ ] Создан **новый** проект `ex01` (а не скопирована папка `ex00`).
- [ ] Исходный текст при запуске совпадает с ex00 (`A simple text`).
- [ ] Первое нажатие: «Hello World!».
- [ ] Второе нажатие: снова исходный текст. Дальше чередование без сбоев.
- [ ] Раскладка по центру и адаптивность не сломались.
- [ ] `flutter analyze` и `flutter test` чистые (тест написан под ex01).
- [ ] `ex00` остался без изменений.

### 1.6 Первый шаг (spike)

Сначала убеждаемся, что цепочка «новый проект, код из ex00, запуск» работает, и **только потом** меняем логику. Так при поломке сразу ясно, чья это вина: переноса или новой логики.

```bash
cd ~/Projects/Mobile/mobileModule00
flutter create --platforms=android,web ex01
cd ex01
grep material_ui pubspec.yaml || flutter pub add material_ui
cp ../ex00/lib/main.dart lib/main.dart
sed -i "s/'ex00'/'ex01'/" lib/main.dart      # только название приложения
flutter run -d chrome                        # должно вести себя как ex00
```

Тест из ex00 в этот момент **упадёт или не скомпилируется**: он импортирует `package:ex00/main.dart`, а проект теперь называется `ex01`. Это ожидаемо, тест мы заменим в [4.6](#46-тест-testwidget_testdart).

## 2. Теория

### 2.1 Что такое «состояние» и почему Stateless тут не справится

**Состояние** (state) это данные, от которых зависит, **как выглядит экран**, и которые **меняются во время работы**. Здесь это одно: «сейчас показан исходный текст или Hello World».

В ex00 страница была `StatelessWidget`: её вид задавался только параметрами при создании, после чего не менялся. Метод `build()` у такого виджета по сути чистая функция: одни и те же входные данные дают одно и то же дерево.

Теперь нужно, чтобы **одна и та же страница** в разные моменты показывала разное. Значит, где-то должна лежать переменная, которая переживает нажатия, и кто-то должен сказать Flutter «переменная изменилась, перерисуй». Обе задачи решает `StatefulWidget`.

Если вам знаком C: `StatelessWidget` похож на функцию без `static`-переменных, а `State` на структуру, которая живёт между вызовами, плюс функция «пометь структуру изменённой».

### 2.2 StatefulWidget: два класса и зачем они

Короткое объяснение уже есть в [ex00, раздел 2.4](00-ex00.md#24-statelesswidget-и-statefulwidget). Здесь разберём, **почему именно два класса**, потому что это самый частый вопрос.

```dart
class HomePage extends StatefulWidget {         // 1) конфигурация: неизменяемая, лёгкая
  const HomePage({super.key});

  @override
  State<HomePage> createState() => _HomePageState();
}

class _HomePageState extends State<HomePage> {  // 2) состояние: изменяемое, долгоживущее
  bool _isHello = false;
  // ...
}
```

Вспомните три дерева из [ex00, раздел 2.3](00-ex00.md#23-три-дерева):

| Что | Живёт | Меняется |
|---|---|---|
| **Widget** (`HomePage`) | коротко: пересоздаётся при каждой перестройке родителя | нет, все поля `final` |
| **State** (`_HomePageState`) | долго: пока Element жив в дереве | да, это место для изменяемых полей |
| **Element** | долго | он держит ссылку на State |

Смысл разделения: **виджет можно пересоздавать сколько угодно, не теряя данные**, потому что данные лежат не в нём, а в `State`. Родитель перестроился, создал новый объект `HomePage`, Element увидел «тот же тип, тот же ключ, значит оставляю старый State», и `_isHello` на месте.

Если бы переменная лежала в самом виджете, она обнулялась бы при каждом пересоздании. Именно этот «подводный камень» и объясняет, почему обычная `bool` в `StatelessWidget` не работает (см. [4.5](#45-симуляция-что-будет-без-setstate)).

Жизненный цикл `State` (напоминание):

```
createState → initState → didChangeDependencies → build ⇄ (setState) → dispose
```

В ex01 нам нужен только `build()` и `setState`. `initState` и `dispose` понадобятся, когда появятся ресурсы вроде контроллеров и подписок.

### 2.3 setState: что он делает на самом деле

```dart
setState(() {
  _isHello = !_isHello;
});
```

По шагам:

1. **Синхронно** выполняется переданная функция. Поле `_isHello` меняется прямо сейчас.
2. Element этого `State` помечается **«грязным»** (dirty), то есть «моё описание устарело».
3. Flutter не перестраивает ничего немедленно. Он ставит Element в очередь и **на ближайшем кадре** вызывает `build()` у всех грязных Element.
4. Новое дерево виджетов сравнивается со старым, и обновляются только те RenderObject, которые изменились.

Из этого следуют три вещи, о которые обычно спотыкаются:

- **Менять поле без `setState` можно, но экран не обновится.** Переменная изменится, а `build()` никто не вызовет. Подробная симуляция в [4.5](#45-симуляция-что-будет-без-setstate).
- **Функцию внутри `setState` нельзя делать `async`.** Flutter в debug-режиме выбросит ошибку «setState() callback argument returned a Future». Асинхронную работу делают снаружи, а внутрь кладут только присваивание результата.
- **`setState` после `dispose()`** (например, ответ сети пришёл, когда экран уже закрыт) вызывает ошибку. Защита: `if (!mounted) return;` перед `setState`. В ex01 асинхронности нет, поэтому это пока теория.

### 2.4 Что перестраивается при setState

`setState` вызывается у `_HomePageState`, значит `build()` этого State выполнится заново **целиком**: заново создадутся `Scaffold`, `SafeArea`, `LayoutBuilder` и всё ниже. Звучит расточительно, но:

- создание виджетов дёшево (это маленькие неизменяемые объекты);
- дальше Flutter **сравнивает** новое дерево со старым и трогает дорогие RenderObject только там, где данные изменились. Здесь это один `Text`;
- виджеты, созданные через `const`, это один и тот же объект, и Flutter пропускает их сразу (`const SizedBox(height: 24)`, `const Text('Click me')`).

Вывод: пока страница маленькая, перестраивать её целиком нормально. Если бы внутри был тяжёлый список или карта, «узкий» Stateful вокруг изменяемой части оказался бы лучше. Это тема [решения 1](#решение-1-какой-виджет-делать-stateful).

### 2.5 Где живёт состояние: hot reload, hot restart, поворот экрана

Это полезно знать на практике, и в [разделе 6](#6-запуск-и-проверка) мы это проверим руками.

| Действие | Что с состоянием `_isHello` |
|---|---|
| **Hot reload** (`r` в консоли `flutter run`) | **Сохраняется.** Код подменяется, `State` остаётся тем же. Инициализаторы полей заново не выполняются. |
| **Hot restart** (`R`) | **Сбрасывается.** Приложение запускается заново, `_isHello = false`. |
| **Поворот экрана / изменение размера окна** | Должно **сохраниться**: Element тот же, `State` тот же, перестраивается только раскладка. Проверяем руками. |
| **Полный перезапуск приложения** | Сбрасывается. Мы нигде ничего не сохраняем (это non-goal). |

Практическое следствие: если вы поменяли начальное значение поля (`bool _isHello = true;`) и сделали hot reload, **вы ничего не увидите**, потому что инициализатор не выполнился повторно. Для проверки нужен hot restart. Это классическая причина фразы «я поменял, а оно не работает».

## 3. Декомпозиция и решения

### Решение 1: какой виджет делать Stateful

- **Варианты:**
  - **A.** Сделать `HomePage` Stateful (как есть, целая страница).
  - **B.** Оставить `HomePage` Stateless, а изменяемую часть (текст и кнопку) вынести в маленький отдельный Stateful-виджет.
  - **C.** Сделать Stateful уже `MyApp`.
- **Выбрано:** **A**.
- **Почему:** это минимальное изменение относительно ex00: меняется заголовок класса, появляется `State`, а `build()` переезжает туда почти без правок. Читать и проверять проще всего. Перестроение страницы целиком здесь копеечное (см. [2.4](#24-что-перестраивается-при-setstate)).
- **Что теряем / риски:** при каждом нажатии пересоздаются `Scaffold`, `LayoutBuilder` и прочее, хотя меняется один `Text`. На такой странице это незаметно. Вариант C хуже всего: перестраивалось бы всё приложение, включая тему.
- **Когда выбрать B:** если на странице появится тяжёлое содержимое, которое не должно перестраиваться при каждом нажатии.

### Решение 2: чем представить состояние: bool, String или enum

- **Варианты:**
  - **A.** `bool _isHello` (флаг).
  - **B.** `String _text`, где хранится сама показанная строка.
  - **C.** `enum` с вариантами.
- **Выбрано:** **A**.
- **Почему:** состояний ровно два, и флаг это ровно «одно из двух». Переключение пишется как `!_isHello`, без сравнений строк. Единственный «источник правды» это флаг, а тексты лежат в константах. С вариантом B пришлось бы писать `_text = _text == initial ? hello : initial`, дублируя знание о том, какие тексты бывают.
- **Что теряем / риски:** если когда-нибудь появится третий вариант текста, `bool` перестанет хватать. Тогда переходим на `enum`: это дёшево, и компилятор подскажет все места, где надо добавить ветку.

### Решение 3: оставлять ли вывод в консоль

- **Варианты:** оставить `debugPrint('Button pressed')` из ex00 или убрать.
- **Выбрано:** **оставить**.
- **Почему:** сабж говорит «возьмите код из предыдущего упражнения». Убирая вывод, мы создаём регресс относительно ex00 без всякой выгоды. Строка ничего не стоит, а при проверке нажатие по-прежнему видно в консоли.
- **Что теряем / риски:** ничего заметного. Защитник мог бы спросить «почему вывод остался», и ответ простой: «поведение ex00 не должно ломаться».

### Решение 4: что класть внутрь setState

- **Варианты:** вызвать `debugPrint` внутри `setState`; или снаружи; или поменять поле без `setState`, а потом вызвать `setState(() {})`.
- **Выбрано:** внутрь `setState` кладём **только** изменение поля. `debugPrint` вызываем **снаружи**, до `setState`.
- **Почему:** внутри `setState` должны быть только изменения состояния. Побочные эффекты (вывод, запросы, запись на диск) внутрь не кладут: коллбэк должен быть быстрым и предсказуемым.
- **Что теряем / риски:** формально `setState(() {})` с пустой функцией тоже работает (он лишь помечает Element грязным), но это путает читателя: непонятно, что именно изменилось. Читаемость важнее.

### Решение 5: новый проект, а не копия папки

- **Варианты:** скопировать папку `ex00` в `ex01` и переименовать; или `flutter create` с новым именем и перенос кода.
- **Выбрано:** **`flutter create`** (как требует и README, раздел 5.1).
- **Почему:** в `pubspec.yaml` записано имя пакета, а в тестах импорт вида `package:ex00/main.dart`. При копировании папки они останутся старыми и указывают на другой проект. К тому же в копии осталась бы папка `build/` и кэш анализатора с путями старого проекта.
- **Что теряем / риски:** нужно один раз выполнить `flutter create` и `pub add material_ui`. Это секунды.

### Решение 6: какой тест писать

- **Варианты:**
  - **A.** Оставить дымовой тест из ex00 (`текст и кнопка на месте`) с поправленным импортом.
  - **B.** Заменить его тестом, который проверяет **переключение**.
- **Выбрано:** **B**, но он включает проверку из A (начальное состояние), так что дымовая проверка сохраняется.
- **Почему:** главная новая функциональность ex01 это переключение. Дымовой тест из ex00 прошёл бы, даже если бы кнопка вообще ничего не делала. Тест на переключение проверяет именно то, что требует сабж.
- **Что теряем / риски:** тест чуть длиннее. Зато он ловит самую вероятную ошибку: забыли `setState` или перепутали порядок.

## 4. Разбор кода

### 4.1 Полный `lib/main.dart`

```dart
import 'package:material_ui/material_ui.dart';

void main() {
  runApp(const MyApp());
}

class MyApp extends StatelessWidget {
  const MyApp({super.key});

  @override
  Widget build(BuildContext context) {
    return MaterialApp(
      title: 'ex01',
      debugShowCheckedModeBanner: false,
      theme: ThemeData(
        colorScheme: ColorScheme.fromSeed(seedColor: Colors.indigo),
      ),
      home: const HomePage(),
    );
  }
}

class HomePage extends StatefulWidget {
  const HomePage({super.key});

  @override
  State<HomePage> createState() => _HomePageState();
}

class _HomePageState extends State<HomePage> {
  static const String _initialText = 'A simple text';
  static const String _helloText = 'Hello World!';

  bool _isHello = false;

  void _onButtonPressed() {
    debugPrint('Button pressed');
    setState(() {
      _isHello = !_isHello;
    });
  }

  @override
  Widget build(BuildContext context) {
    return Scaffold(
      body: SafeArea(
        child: LayoutBuilder(
          builder: (context, constraints) {
            return SingleChildScrollView(
              child: ConstrainedBox(
                constraints: BoxConstraints(minHeight: constraints.maxHeight),
                child: Center(
                  child: ConstrainedBox(
                    constraints: const BoxConstraints(maxWidth: 480),
                    child: Padding(
                      padding: const EdgeInsets.all(24),
                      child: Column(
                        mainAxisSize: MainAxisSize.min,
                        children: [
                          Text(
                            _isHello ? _helloText : _initialText,
                            textAlign: TextAlign.center,
                            style: Theme.of(context).textTheme.headlineMedium,
                          ),
                          const SizedBox(height: 24),
                          ElevatedButton(
                            onPressed: _onButtonPressed,
                            child: const Text('Click me'),
                          ),
                        ],
                      ),
                    ),
                  ),
                ),
              ),
            );
          },
        ),
      ),
    );
  }
}
```

> **О проверке.** Этот код написан по документации и исходникам Flutter, но **не запускался** на устройстве теми, кто его писал: проверка за вами (`flutter analyze`, `flutter test`, запуск). Если что-то не сойдётся, это нормально, разберём по выводу.

### 4.2 Что изменилось по сравнению с ex00

Сравните с ex00: изменилось **ровно три места**, всё остальное идентично.

| # | Где | Было (ex00) | Стало (ex01) |
|---|---|---|---|
| 1 | заголовок класса | `class HomePage extends StatelessWidget` | `class HomePage extends StatefulWidget` + новый класс `_HomePageState extends State<HomePage>` |
| 2 | обработчик | `debugPrint('Button pressed');` | `debugPrint('Button pressed');` **и** `setState(() { _isHello = !_isHello; });` |
| 3 | текст | `Text('A simple text', ...)` | `Text(_isHello ? _helloText : _initialText, ...)` |

Плюс косметика: `title: 'ex01'` и две константы со строками.

Самый маленький возможный diff, и это сознательно: чем меньше изменений, тем меньше шансов, что сломается адаптивность из ex00.

### 4.3 Разбор сверху вниз

Всё, что идентично ex00 (`MyApp`, `LayoutBuilder`, `SingleChildScrollView`, два `ConstrainedBox`, `Padding`, `Column`), разобрано в [ex00, раздел 4.2](00-ex00.md#42-разбор-сверху-вниз). Здесь только новое.

```dart
class HomePage extends StatefulWidget {
  const HomePage({super.key});

  @override
  State<HomePage> createState() => _HomePageState();
}
```

- **`extends StatefulWidget`**: теперь страница изменяемая. Сам класс остаётся неизменяемым (никаких полей, кроме `key`), поэтому конструктор по-прежнему `const`.
- **`createState()`**: фабрика состояния. Flutter вызывает её **один раз** при вставке виджета в дерево. Дальше этот объект `State` живёт, а `HomePage` может пересоздаваться много раз.
- **`State<HomePage>`**: обобщённый тип, который связывает `State` с его виджетом. Благодаря этому внутри `State` доступно поле `widget` (текущая версия `HomePage`). Нам оно не нужно, но именно так в `State` попадают параметры виджета.
- **`_HomePageState` с подчёркиванием**: в Dart подчёркивание делает имя **приватным для файла**. Снаружи этот класс никому не нужен, поэтому его прячем.

```dart
class _HomePageState extends State<HomePage> {
  static const String _initialText = 'A simple text';
  static const String _helloText = 'Hello World!';

  bool _isHello = false;
```

- **`static const String`**: константы на уровне класса, одни на все экземпляры, значения известны на этапе компиляции. Строки вынесены в константы, чтобы не плодить «магические строки» в `build()` и чтобы менять текст в одном месте.
- **`bool _isHello = false;`**: **единственное изменяемое состояние** во всём приложении. `false` значит «показан исходный текст». Это **начальное значение**: оно задаётся один раз при создании State (поэтому hot reload его не сбрасывает, см. [2.5](#25-где-живёт-состояние-hot-reload-hot-restart-поворот-экрана)).

```dart
  void _onButtonPressed() {
    debugPrint('Button pressed');
    setState(() {
      _isHello = !_isHello;
    });
  }
```

- **`debugPrint`** остался из ex00 ([решение 3](#решение-3-оставлять-ли-вывод-в-консоль)), и стоит **снаружи** `setState` ([решение 4](#решение-4-что-класть-внутрь-setstate)).
- **`setState(() { ... })`**: см. [2.3](#23-setstate-что-он-делает-на-самом-деле). Передаём **анонимную функцию**, внутри которой меняем поле.
- **`!_isHello`**: логическое отрицание. `false` становится `true`, `true` становится `false`. Это и есть «переключение туда-обратно» без всяких `if`.

```dart
  @override
  Widget build(BuildContext context) {
    return Scaffold( ... );
  }
```

- `build()` теперь метод **State**, а не виджета. Он по-прежнему возвращает дерево виджетов, но может читать поля State (`_isHello`).
- `context` это тот же `BuildContext`, что и раньше. Он по-прежнему доступен как параметр.

```dart
Text(
  _isHello ? _helloText : _initialText,
  ...
)
```

- **Тернарный оператор** `условие ? значение_если_да : значение_если_нет` (то же, что в C). Если `_isHello` истинно, показываем «Hello World!», иначе исходный текст.
- Это **единственное** место, где состояние влияет на картинку. В этом суть декларативного подхода: **вы не говорите «замени текст на экране», вы говорите «экран зависит от `_isHello`»**, а Flutter сам разбирается, как перерисовать при изменении.

```dart
const SizedBox(height: 24),
ElevatedButton(
  onPressed: _onButtonPressed,
  child: const Text('Click me'),
),
```

- `const SizedBox` и `const Text('Click me')` остаются `const` и при каждом перестроении пропускаются Flutter (см. [2.4](#24-что-перестраивается-при-setstate)). Заметьте: `Text(_isHello ? ...)` уже **не** `const`, потому что зависит от переменной.
- `onPressed: _onButtonPressed` по-прежнему **ссылка** на функцию, без скобок (см. [ex00, 4.2](00-ex00.md#42-разбор-сверху-вниз)).

### 4.4 Симуляция: серия нажатий

Состояние до начала: `_isHello == false`, экран показывает `A simple text`.

**Нажатие 1:**

```
1. Касание → hit test → арена жестов → распознан tap (как в ex00, 4.4).
2. Вызывается onPressed → _onButtonPressed().
3. debugPrint('Button pressed') → строка уходит в консоль.
4. setState(...) выполняет функцию: _isHello = !false → _isHello = true.
5. Element страницы помечен «грязным», поставлен в очередь на кадр.
6. Следующий кадр: вызывается build() у _HomePageState.
   Text(_isHello ? ... ) → _isHello истинно → Text('Hello World!').
7. Element сравнивает новый Text со старым: тот же тип, другие данные.
   → RenderObject текста обновляется (пересчёт размера текста), перерисовка.
   Кнопка, SizedBox и обёртки не изменились: их RenderObject не трогаются.
8. На экране «Hello World!».
```

**Состояние после нажатий 1–4:**

| Нажатие | `_isHello` до | `_isHello` после | Что на экране |
|---|---|---|---|
| (старт) | — | `false` | A simple text |
| 1 | `false` | `true` | Hello World! |
| 2 | `true` | `false` | A simple text |
| 3 | `false` | `true` | Hello World! |
| 4 | `true` | `false` | A simple text |

Заметьте шаг 7: `Text` меняется, а ширина текста может отличаться («Hello World!» короче, чем «A simple text»). Поэтому после смены текста **раскладка пересчитывается**, и текст остаётся по центру. Именно ради этого мы не используем жёсткие координаты.

### 4.5 Симуляция: что будет без setState

Допустим, написали так (**ошибочный** вариант, для демонстрации):

```dart
void _onButtonPressed() {
  debugPrint('Button pressed');
  _isHello = !_isHello;          // поле изменили, setState не вызвали
}
```

```
Нажатие 1: _isHello стало true.  Element НЕ помечен грязным.
           build() НЕ вызывается. На экране всё ещё «A simple text».
           В консоли «Button pressed» есть. Кажется, что кнопка «сломана».

Нажатие 2: _isHello стало false. Экран по-прежнему «A simple text».

Нажатие 3: _isHello стало true.  Экран по-прежнему «A simple text».
```

А теперь **эффект, который сбивает с толку**: если после нескольких нажатий случайно что-то другое вызовет `build()` (поворот экрана, изменение размера окна, hot reload), то страница вдруг покажет текст, **соответствующий текущему значению** `_isHello`. Переменная всё это время была правильной, просто никто не просил Flutter перерисовать экран.

Вывод: **поле меняет данные, `setState` объявляет о том, что данные изменились**. Без второго экран отстаёт от первого.

### 4.6 Тест `test/widget_test.dart`

Заменяем тест целиком (старый импортирует `package:ex00/main.dart` и в `ex01` не соберётся):

```dart
import 'package:flutter_test/flutter_test.dart';
import 'package:ex01/main.dart';

void main() {
  testWidgets('toggles the text on every button press',
      (WidgetTester tester) async {
    await tester.pumpWidget(const MyApp());

    // Старт: исходный текст, Hello World ещё нет.
    expect(find.text('A simple text'), findsOneWidget);
    expect(find.text('Hello World!'), findsNothing);

    // Нажатие 1: Hello World!
    await tester.tap(find.text('Click me'));
    await tester.pump();
    expect(find.text('Hello World!'), findsOneWidget);
    expect(find.text('A simple text'), findsNothing);

    // Нажатие 2: обратно.
    await tester.tap(find.text('Click me'));
    await tester.pump();
    expect(find.text('A simple text'), findsOneWidget);
    expect(find.text('Hello World!'), findsNothing);
  });
}
```

Что тут нового по сравнению с тестом ex00:

- **`tester.tap(finder)`** имитирует касание в центре найденного виджета. Мы целимся в надпись `Click me`, а она лежит внутри кнопки, поэтому нажатие доходит до кнопки.
- **`await tester.pump()`** обязателен после `tap`. `setState` лишь **ставит** перестроение в очередь, а в тестовой среде кадры сами не идут. `pump()` прокручивает один кадр, и только после него дерево обновлено. Без `pump()` проверка увидит старый текст, и тест упадёт **по вине теста**, а не приложения. Это ещё одна параллель с `setState`: «изменили» не значит «перерисовалось».
- **`findsNothing`**: «ни одного такого виджета». Мы проверяем и то, что нужный текст появился, и то, что **ненужный исчез**. Проверка только «появилось» пропустила бы баг, при котором показываются оба текста.
- В выводе `flutter test` могут встретиться строки `Button pressed`: это наш `debugPrint` при нажатиях. Это нормально.

> **О проверке.** Этот тест тоже написан по документации и не запускался теми, кто его писал. Он основан на тех же приёмах, что и дымовой тест ex00, плюс `tap` и `pump`.

## 5. Альтернативы

Все варианты решают ту же задачу. Для ex01 выбран самый простой: `StatefulWidget` и `setState`.

| Вариант | Идея | Плюсы | Минусы | Когда уместен |
|---|---|---|---|---|
| **`StatefulWidget` + `setState`** (наш) | Флаг в `State`, `setState` при нажатии | Минимум кода, встроено во Flutter, понятно | Перестраивается вся страница; для общего состояния нескольких экранов не годится | Локальное состояние одного экрана |
| **Узкий Stateful** (вынести текст и кнопку в отдельный виджет) | Меньший виджет держит состояние | Перестраивается только он | Лишний класс | Страница тяжёлая |
| **`StatefulBuilder`** | Stateful «на месте», без отдельного класса | Короче | Хуже читается, состояние живёт в замыкании | Маленький локальный кусок (диалог) |
| **`ValueNotifier` + `ValueListenableBuilder`** | Значение лежит в объекте-наблюдателе, перестраивается только слушатель | Перестраивается только `Text`; логику можно отделить | Объект нужно создать и освободить (`dispose`), а значит всё равно нужен `State` | Состояние нужно разделять между виджетами |
| **`AnimatedSwitcher`** | Плавная смена текста | Красиво | Это non-goal; сложнее тест | Когда требуется анимация |
| **Пакеты состояния** (Provider, Riverpod, Bloc) | Состояние вне виджетов | Масштабируется, тестируется | Лишняя зависимость; для переключателя это пушка по воробьям | Большие приложения |

Пример варианта с `ValueNotifier` (для сравнения, в ex01 **не используем**):

```dart
import 'package:flutter/foundation.dart'; // ValueNotifier живёт здесь
import 'package:material_ui/material_ui.dart';

class _HomePageState extends State<HomePage> {
  final ValueNotifier<bool> _isHello = ValueNotifier<bool>(false);

  @override
  void dispose() {
    _isHello.dispose();   // освободить, как free() в C
    super.dispose();
  }

  void _onButtonPressed() {
    debugPrint('Button pressed');
    _isHello.value = !_isHello.value;   // setState не нужен
  }

  // в build():
  //   ValueListenableBuilder<bool>(
  //     valueListenable: _isHello,
  //     builder: (context, isHello, _) =>
  //         Text(isHello ? 'Hello World!' : 'A simple text', ...),
  //   )
}
```

Обратите внимание: даже здесь нужен `State`, потому что `ValueNotifier` надо где-то создать и вовремя освободить. Поэтому для первого упражнения на состояние классический `setState` самый честный. Отдельный импорт `foundation.dart` нужен, потому что, по исходникам `widgets.dart` (Flutter 3.35), `ValueNotifier` оттуда не реэкспортируется; на вашей версии это проверит компилятор.

Запустите `flutter run`, нажмите кнопку один раз (на экране «Hello World!»), затем:

## 7. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| Кнопка нажимается (в консоли `Button pressed`), а текст не меняется | Не вызван `setState`: поле изменено «молча» | Обернуть изменение поля в `setState(() { ... })` |
| Текст меняется, но после hot reload «откатился» к исходному | Был hot **restart**, а не reload | Это ожидаемо: restart сбрасывает состояние |
| Поменяли `bool _isHello = true;` и ничего не изменилось после hot reload | Инициализатор поля не выполняется при hot reload | Сделать hot restart (`R`) |
| `flutter test` не компилируется: `Target of URI doesn't exist: 'package:ex00/main.dart'` | Остался старый тест из ex00 | Заменить `test/widget_test.dart` (см. 4.6), импортировать `package:ex01/main.dart` |
| Тест падает на `expect(find.text('Hello World!'), findsOneWidget)` после `tap` | Нет `await tester.pump()` после нажатия | Добавить `await tester.pump();` |
| `setState() callback argument returned a Future` | Функция внутри `setState` объявлена `async` | Убрать `async`, асинхронную работу вынести за `setState` |
| `Target of URI doesn't exist: 'package:material_ui/...'` | Пакета нет в `pubspec.yaml` | `flutter pub add material_ui`, затем `flutter pub get` |
| `flutter analyze` ругается `prefer_const_constructors` | Где-то можно добавить `const` | Добавить `const` там, где указывает линт (у `Text` с переменной `const` ставить нельзя) |
| Текст «Hello World!» сдвигается или кнопка «прыгает» | Не центрирован верхний уровень или жёсткие размеры | Вернуть раскладку из ex00: `Center`, `Column(mainAxisSize: min)`, без фиксированных координат |
| `flutter create` ругается на имя проекта | Недопустимые символы в имени | Имя только из строчных букв, цифр и `_`; `ex01` допустимо |

## 8. Безопасность и риски

В этом упражнении **нет сети, нет файлов, нет разрешений, нет секретов**, так что классических рисков безопасности нет. Но есть несколько практических рисков:

- **Утечки в логах.** Сейчас в консоль уходит только `Button pressed`. Привычка выводить в консоль данные (особенно пользовательские, токены, пароли) плохая: на Android `debugPrint` пишется в системный лог (`logcat`), который могут читать другие инструменты. Для ex01 это безопасно, но правило стоит закрепить с первого раза: **в лог не пишем ничего секретного**.
- **Зависимость `material_ui`.** Это внешний пакет из pub.dev. Версия зафиксирована в `pubspec.lock`. Не обновляйте зависимости в день сдачи: новая версия может сломать то, что вчера работало.
- **Регресс ex00.** Если вы случайно правили `ex00` в процессе (например, скопировали и забыли поправить), на защите это выглядит плохо. Проверка: `git status` должен показывать изменения только внутри `mobileModule00/ex01` и `docs`.
- **Мусор в репозитории.** Проверьте, что в коммит не попали `build/`, `.dart_tool/` и `local.properties` (они уже в `.gitignore` проекта, но проверьте командой `git status` перед коммитом).

## 10. Что запомнить

**По языку (Dart):**

- `static const` в классе: константа, общая для всех экземпляров, значение известно при компиляции.
- Приватность в Dart через `_` в начале имени; действует на уровне **файла**, а не класса.
- Тернарный оператор `условие ? a : b`: выбор значения прямо в выражении.
- `!` перед `bool` это логическое отрицание. Переключатель в одну строку: `x = !x`.
- Анонимная функция `() { ... }` передаётся как аргумент (`setState`).

**По фреймворку (Flutter):**

- **`StatefulWidget`: два класса.** Виджет неизменяемый и пересоздаётся, `State` изменяемый и живёт долго. Данные лежат в `State`, поэтому не теряются.
- **`setState` не «меняет экран».** Он выполняет вашу функцию и **сообщает**, что `build()` надо вызвать заново. Меняете поле без него, и экран отстаёт.
- **Декларативный подход:** вы описываете «экран зависит от `_isHello`», а не «замени текст». Flutter сам вычисляет, что перерисовать.
- **`build()` вызывается часто и может выполняться целиком.** Это нормально: виджеты дешёвые, а `const`-виджеты пропускаются.
- **Hot reload сохраняет `State`, hot restart сбрасывает.** Инициализаторы полей при hot reload заново не работают.
- **Внутри `setState` только изменение полей.** Без `async`, без побочных эффектов.
- **В тестах после действия нужен `pump()`**, иначе дерево не перестроится. Проверяйте и «появилось нужное», и «исчезло ненужное» (`findsNothing`).

**По логике и реализации:**

- Состояние должно быть **минимальным**: `bool` вместо строки, потому что вариантов ровно два.
- Начинайте с самого маленького изменения относительно прошлого упражнения: меньше diff, меньше поломок.
- Новый проект делаем командой `flutter create`, а не копированием папки: имя пакета записано в `pubspec.yaml` и в импортах тестов.
- Любое поведение, которое требует сабж, должно быть **проверено тестом**: дымовой тест этого не сделает.
