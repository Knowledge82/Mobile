# Модуль 04, ex01: Profile Page

> Второе упражнение модуля: у приложения появляется **память**. Дневник хранит записи в **облачной базе Cloud Firestore**, а страница профиля их показывает, даёт **создать, прочитать и удалить**, и всё это обновляется **само**, без кнопки «обновить». Главные новые темы: **документная база данных** (коллекции, документы, поля), **живой поток изменений** (`snapshots()` + `StreamBuilder`), **правила безопасности Firestore** (чтобы чужие записи не читались даже при взломанном приложении), **работа без сети** (запись «уже есть», а сервер ещё не ответил), **формы с проверкой ввода** (`Form`, `validator`) и **диалоги**. Здесь же то, что сабж просит отдельной строкой: **Google-аккаунт для проверяющего с готовыми записями**.

> **Честная пометка о проверке.** Код модуля 04 написан **без запуска**: в среде подготовки нет Flutter SDK, а `pub.dev` недоступен. Синтаксис Dart прогнан парсером (ошибок нет). Имена методов Firestore (`collection`, `doc`, `orderBy`, `snapshots`, `add`, `delete`, `Timestamp`) сверены с исходным кодом пакета на GitHub (ветка `main`), но **ни разу не выполнялись**. Самые непроверенные места: **правила безопасности** (синтаксис я сверяла по справке, но не запускала), поведение **без сети** (восемь секунд ожидания и сообщение) и внешний вид на телефоне. Если что-то падает, пришлите текст ошибки целиком, и мы поправим.

## 1. Задача и с чего начать

### 1.1 Условия сабжа

- **Папка сдачи:** `mobileModule04`
- **Файлы для сдачи:** `diary_app` и все необходимые файлы
- **Запрещённые функции:** нет
- **Требования ex01:**
  - страница профиля **доступна только вошедшему** пользователю; система аутентификации **перенаправляет** на неё после входа или **сразу**, если пользователь уже вошёл;
  - перед этим нужно **настроить базу данных** для записей дневника;
  - в базе хранить: **почту** пользователя, **дату** записи, **заголовок**, **самочувствие дня**, **текст** записи;
  - структура базы «должна напоминать» картинку из сабжа;
  - нужно уметь **создавать, читать, удалять** записи (логика этих операций);
  - страница профиля содержит: **список всех записей**, **кнопку новой записи**, **чтение записи по нажатию**, **кнопку удаления**;
  - при создании и удалении записи **список обновляется**;
  - **для проверки нужно создать Google-аккаунт для проверяющего**, и в нём должны быть **записи**.
- **Про картинки:** сабж напоминает, что демо и картинки могут содержать необязательные добавления. Обязательно только то, что сказано **текстом**. Отсюда решение 1 (имена полей по тексту) и решение 2 (подколлекция вместо плоской таблицы).

### 1.2 Проблема

Нужно хранить **личные** записи так, чтобы:

1. они **не пропадали** при закрытии приложения и были доступны с любого устройства;
2. каждый видел **только свои** (иначе это не дневник, а стена объявлений);
3. список **менялся сам**: добавили запись, она появилась; удалили, исчезла; пришла правка с другого телефона, тоже появилась;
4. приложение **не зависало и не врало**, когда пропадает интернет.

### 1.3 Требования

**Функциональные:**

- Профиль показывает: «Signed in as <имя>», кнопку выхода, список записей (новые сверху), кнопку **New diary entry**.
- В строке записи: значок самочувствия, **заголовок**, дата, кнопка удаления (мусорка).
- Нажатие на запись открывает окно чтения: заголовок, самочувствие, дата и время, текст целиком (с прокруткой).
- Новая запись: **заголовок**, **самочувствие** (пять вариантов), **текст**; поля не пустые (в том числе из одних пробелов).
- Удаление всегда через вопрос «Delete this entry?» (случайно нажатая мусорка не должна стирать память).
- Пустой дневник: понятная подсказка, как начать.
- Загрузка: индикатор. Ошибка: сообщение и кнопка «Try again».
- Выход (Log out) возвращает на приветствие.

**Нефункциональные:**

- **Правила базы**: чужие записи недоступны даже тому, кто подменил приложение; создание проверяет форму данных.
- **Без сети**: запись сразу видна в списке; через несколько секунд ожидания пользователь получает честное «сохранено на устройстве, отправится при появлении сети».
- **Один испорченный документ не роняет весь список** (терпимое чтение).
- Экраны не зависят от Firebase (интерфейс `DiaryRepository`), поэтому всё проверяется тестами без интернета.

### 1.4 Что не входит в задачу (non-goals)

- Редактирование записи (сабж просит создать, прочитать, удалить; правила базы **запрещают** обновление).
- Поиск, фильтры, группировка по датам, постраничная загрузка (при тысячах записей понадобится: см. раздел 9).
- Вложения (фото) и форматированный текст.
- Общие записи нескольких пользователей.
- Статистика и «последние две записи» (это модуль 05).
- Экспорт и резервные копии.

### 1.5 Критерии успеха

- [ ] После входа открывается профиль; у нового пользователя пусто и есть подсказка.
- [ ] **New diary entry**: окно с заголовком, пятью вариантами самочувствия и текстом; пустое не сохраняется.
- [ ] Сохранили: окно закрылось, запись **появилась в списке сама**; в консоли Firebase есть документ `users/{uid}/entries/{id}` с пятью полями.
- [ ] Нажатие на запись показывает её целиком.
- [ ] Мусорка: вопрос, подтверждение, запись **исчезла сама**; Cancel ничего не меняет.
- [ ] Запись, добавленная с другого устройства или из консоли (с правильными полями), **появляется без обновления**.
- [ ] Самолётный режим: создаём запись, она видна сразу; через ~8 секунд полоска «Saved on this device...»; включили сеть: запись уходит на сервер (видно в консоли).
- [ ] Пользователь B **не видит и не может удалить** записи пользователя A (проверка правилами: раздел 6.5).
- [ ] У проверяющего есть Google-аккаунт с несколькими записями.
- [ ] `flutter analyze` и `flutter test` зелёные.

### 1.6 Первый шаг (spike)

Прежде чем писать код приложения, поиграйте с базой **руками**:

1. Консоль Firebase → **Firestore Database → Create database** (раздел 6.2).
2. Вкладка **Data → Start collection**: `users` → документ с любым id → вложенная коллекция `entries` → документ с полями `title` (string), `date` (timestamp), `email` (string), `feeling` (string `satisfied`), `content` (string).
3. Посмотрите, как это выглядит: **коллекции содержат документы, документы содержат поля и вложенные коллекции**. Именно эту структуру мы будем описывать кодом.
4. Удалите пробный документ (после подключения правил из `firestore.rules` консоль всё равно позволит вам это как владельцу проекта).

Так вы поймёте модель данных **до** того, как увидите её в Dart.

Предыдущий разбор ([04-ex00, раздел 1.7](04-ex00.md#17-как-начать-модуль)) уже создал проект и платформы. Здесь нужно ещё две вещи:

## 2. Теория

### 2.1 Словарик (простыми словами)

| Слово | Что это |
|---|---|
| **База данных** | Организованное хранилище, из которого можно быстро найти, добавить и удалить данные. |
| **Cloud Firestore** | Облачная «документная» база Google, часть Firebase. Умеет присылать изменения «вживую» и работать без сети. |
| **Документная база** | База, где данные лежат не в таблицах со строками, а в **документах** (набор полей «имя → значение»), а документы собраны в **коллекции**. |
| **Коллекция (collection)** | «Папка» документов. Например, `entries`. |
| **Документ (document)** | Один «листок» с полями. Например, одна запись дневника. Имеет **id** (имя). |
| **Поле (field)** | Одно значение в документе: строка, число, дата, логическое, список, вложенная карта. |
| **Подколлекция** | Коллекция внутри документа: `users/{uid}/entries`. Позволяет складывать записи каждого пользователя «в его папку». |
| **Путь** | Адрес документа: `users/abc123/entries/xYz`. Чётные сегменты это документы, нечётные коллекции. |
| **`DocumentReference` / `CollectionReference`** | Ссылки на документ и коллекцию (адрес, а не сами данные). |
| **`Query` (запрос)** | Коллекция с условиями: порядок, отбор, ограничение количества. Запрос **не читает** данные, пока вы не вызвали `get()` или `snapshots()`. |
| **`QuerySnapshot`** | «Снимок» результата запроса в какой-то момент: список документов. |
| **`snapshots()`** | Живой поток снимков: новый снимок приходит при **каждом** изменении данных. Это то, что обновляет список само. |
| **`get()`** | Разовое чтение (один снимок и всё). |
| **`add()`** | Создать документ с автоматическим id. |
| **`Timestamp`** | Тип даты Firestore. Показывается в консоли как «дата и время». |
| **Кэш и офлайн-режим** | Firestore на Android хранит копию данных на телефоне: чтение и запись работают без сети, а когда сеть вернётся, всё синхронизируется. |
| **Латентная компенсация (latency compensation)** | Ваша запись **сразу** видна в ваших же запросах, ещё до ответа сервера. |
| **Ожидающая запись (pending write)** | Запись, которая уже в локальном кэше, но сервер её ещё не подтвердил. |
| **Правила безопасности (Security Rules)** | Текст на специальном языке, который Firestore хранит **на сервере** и по которому решает, пускать ли каждый запрос. Единственная настоящая защита данных. |
| **`request.auth`** | В правилах: кто делает запрос (`null`, если не вошёл; иначе есть `uid`). |
| **`request.resource.data`** | В правилах: данные, которые пытаются **записать**. |
| **Production mode / Test mode** | Режимы создания базы: «всё запрещено, пока не напишете правила» и «всё разрешено на 30 дней» (опасный). |
| **`StreamBuilder`** | Виджет, который **перерисовывает** себя при каждом новом значении потока. |
| **`AsyncSnapshot`** | Состояние потока для `StreamBuilder`: есть ошибка (`hasError`), есть данные (`data`) или пока ничего. |
| **`Form` / `FormState`** | Контейнер для нескольких полей с проверкой: `validate()` проверяет все сразу. |
| **`TextFormField` / `validator`** | Поле ввода внутри `Form`; `validator` возвращает текст ошибки или `null` («всё хорошо»). |
| **`showDialog`** | Показать всплывающее окно; результат (`pop(значение)`) возвращается через `await`. |
| **`AlertDialog`** | Стандартное окно с заголовком, содержимым и кнопками. |
| **`ChoiceChip`** | «Таблетка», которую можно выбрать; у нас пять штук для самочувствия. |
| **`SnackBar`** | Узкая полоска сообщения внизу экрана. |
| **`ListView.builder`** | Список, который строит только **видимые** строки (экономит память при большом числе записей). |
| **`Timer` / `.timeout`** | Ограничение ожидания: если `Future` не завершился за срок, бросается `TimeoutException`. |
| **Enum (перечисление)** | Закрытый набор значений: `Feeling.satisfied`. В базе хранится его **имя** строкой. |
| **Подделка (fake)** | Простая ненастоящая версия сервиса для тестов. |
| **Gate (`Completer`)** | «Шлагбаум» в тесте: `Future` не завершится, пока тест его не откроет. Так подделка изображает «сервер не отвечает». |

### 2.2 Модель данных: как лежит дневник в базе

В реляционной базе вы сделали бы таблицу `entries` со столбцами. Здесь **иерархия документов**:

```
users                         коллекция
└── {uid}                     документ пользователя (у нас пустой «ярлык-папка»)
    └── entries               подколлекция
        └── {id}              документ записи (id выдаёт Firestore)
              email    "alice@example.com"        string
              date     2026-11-28 09:30:00        timestamp
              title    "A good day"                string
              feeling  "verySatisfied"             string (имя значения enum)
              content  "We walked by the sea."     string
```

Что важно:

- **Пять полей с именами из сабжа**: `email`, `date`, `title`, `feeling`, `content`.
- Документ `users/{uid}` **мы не создаём**: подколлекции могут существовать «под несуществующим» документом. В консоли он показан курсивом. Это нормально.
- **Почему подколлекция, а не одна общая коллекция `entries` с полем `uid`?** Раздел 3, решение 2. Коротко: путь сам несёт владельца, правила получаются в одну строку, запрос не требует составного индекса.
- **Почему `feeling` это строка-имя, а не число?** Если порядок значений в коде изменится, числа в старых записях изменят смысл, а имена нет (решение 4).
- **Почему дата это `Timestamp`, а не строка?** Строка `'2026-11-28'` сортируется «как текст» и теряет время; `Timestamp` хранит момент времени и сортируется правильно.

### 2.3 Живой список: `snapshots()` и `StreamBuilder`

Привычная схема «нажал кнопку, загрузил, показал» здесь не нужна. У Firestore запрос превращается в **трубу**:

```
Firestore (облако)  ──snapshots()──▶  Stream<List<DiaryEntry>>  ──StreamBuilder──▶  ListView
```

1. При подписке приходит **первый снимок** (то, что есть).
2. При **любом** изменении (мы добавили, удалили, пришло с другого телефона) приходит **новый снимок целиком**.
3. `StreamBuilder` на каждый снимок перестраивает список.

Поэтому код создания и удаления **не трогает список**: он только пишет в базу. Список обновляется как следствие. Это очень удобно (меньше мест для ошибок) и **единственный** путь, при котором выполняется требование сабжа «список обновляется» и для записей, пришедших со стороны.

**Важное правило:** поток создают **один раз** (в `initState`), а не в `build`. Иначе при каждой перерисовке страница подписывалась бы заново, а это лишние чтения и мигание индикатора.

### 2.4 Работа без сети: запись «уже есть», а сервер молчит

Firestore на телефоне держит **локальный кэш**. Поэтому:

- `add()` **сразу** записывает документ в кэш; ваш `snapshots()` **мгновенно** присылает новый снимок с этой записью (пометка «ожидающая запись»). Запись **видна в списке** без сети.
- А вот **`Future`, который вернул `add()`, завершается только когда сервер подтвердил** запись. Без сети это может быть через минуты и часы (когда связь вернётся).

Если просто сделать `await add(...)`, то приложение «зависнет» в ожидании. Поэтому мы ограничиваем ожидание (`writeConfirmationTimeout` = 8 секунд). Прошло восемь секунд: говорим пользователю «сохранено на устройстве, отправится, когда будет сеть». Запись при этом **никуда не пропала**: Firestore доделает отправку сам.

Что это значит для честности интерфейса: мы **не** показываем «ошибка сохранения», потому что ошибки нет (запись принята и будет отправлена), и **не** показываем «сохранено» без оговорки, потому что сервер ещё не подтвердил.

> **Не проверено без запуска.** Что именно возвращает Firestore без сети на конкретной версии плагина (иногда нет сообщений об ошибках вообще, иногда `unavailable`). Код обрабатывает оба случая: `TimeoutException` → «сохранено на устройстве», `unavailable` → «нет связи» (оба с понятными фразами).

### 2.5 Правила безопасности: единственная настоящая защита

Всё, что находится в приложении, пользователь (или злоумышленник) может **изменить**: приложение это файл на его телефоне. Поэтому «если не вошёл, профиль закрыт» защищает только честного пользователя. Настоящая защита это **правила на сервере Firestore**.

Наши правила (`firestore.rules`) говорят:

- **Читать и удалять** запись в `users/{userId}/entries/...` может только тот, у кого `request.auth.uid == userId`.
- **Создавать** может он же, **и только** документ правильной формы: ровно пять полей, нужные типы, заголовок 1-100 символов, текст 1-5000, `feeling` из пяти допустимых значений.
- **Обновлять** нельзя никому (сабж правку не просит).
- Всё, что не разрешено, **запрещено**: «по умолчанию нет».

Таблица «что пустят»:

| Кто | Что делает | Результат |
|---|---|---|
| не вошёл | читает чьи-то записи | **запрещено** (`request.auth == null`) |
| Алиса (uid=A) | читает `users/A/entries` | пустят |
| Алиса | читает `users/B/entries` | **запретят**: `A != B` |
| Алиса | создаёт запись в `users/A/entries` с пятью полями правильных типов | пустят |
| Алиса | создаёт запись с шестым полем `isAdmin: true` | **запретят**: `hasOnly` |
| Алиса | создаёт запись без `title` | **запретят**: `hasAll` |
| Алиса | создаёт запись с `feeling: 'ecstatic'` | **запретят**: не из списка |
| Алиса | создаёт запись с заголовком в 500 символов | **запретят**: `size() <= 100` |
| Алиса | удаляет свою запись | пустят |
| Алиса | меняет свою запись | **запретят**: `update: if false` |

Проверить правила без приложения можно во вкладке **Rules → Rules Playground** консоли Firebase (раздел 6.5).

### 2.6 Формы и проверка ввода

- `Form` + `GlobalKey<FormState>`: `_formKey.currentState!.validate()` вызывает `validator` **каждого** поля и рисует ошибки под ними; возвращает `true`, только если все прошли.
- `validator` возвращает `String?`: **текст ошибки** или `null`. У нас: `'Required'` для пустого или из одних пробелов.
- `trim()` убирает пробелы по краям; сохраняем **обрезанное**, а проверяем, что **после обрезки** что-то осталось.
- `maxLength` на поле: Flutter сам рисует счётчик и **не даёт** вводить больше. Эти же числа стоят в правилах базы: если приложение подменят, правила остановят.

### 2.7 Диалоги и результат «через `await`»

`showDialog<T>` возвращает `Future<T?>`: пока окно открыто, он не завершён; `Navigator.pop(значение)` внутри окна завершает его. Удобный паттерн:

```dart
final NewEntryData? data = await showDialog<NewEntryData>(...);
if (data == null) return;      // нажали Cancel или щёлкнули вне окна
```

- `pop(NewEntryData(...))`: «Save».
- `pop()` без значения: результат `null`, «Cancel».
- В окне чтения `pop(true)` означает «пользователь хочет удалить», а закрытие даёт `null`. `if (wantsDelete == true ...)`: сравниваем именно с `true`, потому что значение может быть и `null` (тип `bool?`).

### 2.8 Почему профиль нельзя открыть без входа

Три слоя (в порядке надёжности):

1. **Правила базы** (слой настоящей защиты): без входа данные не отдаются.
2. **Конструктор** `ProfilePage(user: AppUser)` требует **не-`null`** пользователя: компилятор не даст построить профиль «из ниоткуда».
3. **Охранник** внутри профиля подписан на `authStateChanges`: если вход пропал (выход, отзыв), страница сама возвращает на приветствие (`popUntil(isFirst)`), заодно закрывая **открытые диалоги**.

Слои 2 и 3 это удобство для честного пользователя, слой 1 защита от нечестного.

### 2.9 Время и дата: чьи часы

Дату записи ставит **приложение** (`DateTime.now()` на телефоне), а не сервер. Плюсы: запись видна в списке сразу и с датой, даже без сети. Минус: если часы на телефоне сбиты, дата в записи неправильная. Альтернатива `FieldValue.serverTimestamp()` ставит время сервера, но пока сервер не ответил, в локальном снимке поле будет `null` (запись «прыгает» в списке); подробнее в разделе 5. Для дневника «когда пользователь решил записать» и так личное время, поэтому выбрано первое.

## 3. Декомпозиция и решения

Части: **(а)** модели; **(б)** переводчик «запись ↔ документ»; **(в)** хранилище (интерфейс и Firestore); **(г)** страница профиля; **(д)** диалоги; **(е)** правила; **(ж)** тесты.

### Решение 1: имена полей берём из текста сабжа

- **Варианты:** (а) `email`, `date`, `title`, `feeling`, `content`; (б) как на картинке из сабжа (на ней, судя по расшифровке, поле самочувствия называется иначе: `icon`).
- **Выбрано:** (а).
- **Почему:** сабж прямо говорит: **верьте тексту, не картинкам** («картинки могут содержать необязательные добавления»). Текст перечисляет данные: почта, дата, заголовок, самочувствие, содержание. Картинка просит «напоминать» структуру, а не совпадать до буквы. Мы совпадаем **по составу** и названиям из текста.
- **Что теряем / риски:** проверяющий, сверяющий с картинкой, может заметить расхождение в имени поля. Ответ: «в тексте сабжа это самочувствие дня, поле называется `feeling`». Если захотите совпасть с картинкой, достаточно поменять **одну** константу в `entry_mapper.dart` и список в `firestore.rules`.

### Решение 2: подколлекция `users/{uid}/entries`

- **Варианты:** (а) подколлекция; (б) общая коллекция `entries` с полем `uid`; (в) один документ пользователя со списком записей внутри.
- **Выбрано:** (а).
- **Почему:** в (а) **владелец записан в путь**: правило «uid в пути равен uid вошедшего» это одна строка, и запрос «все записи пользователя» не нуждается ни в условии `where`, ни в составном индексе. (б) требует `where('uid', ==, ...)` + `orderBy('date')`: Firestore потребует **составной индекс** (его нужно создать в консоли), а правила придётся писать и для чтения, и для фильтрации. (в) документ в Firestore не больше 1 МиБ, и **весь** дневник пришлось бы перезаписывать при каждом изменении.
- **Что теряем / риски:** запросы «по всем пользователям» (аналитика) в (а) делаются сложнее (нужен `collectionGroup`). Для дневника не нужны.

### Решение 3: дата как `Timestamp`, новые сверху на стороне базы

- **Выбрано:** `Timestamp.fromDate(date)`, запрос `orderBy('date', descending: true)`.
- **Почему:** сортировку делает база (а не наш код), а при добавлении записи с другого устройства она встанет на нужное место сама. Для поля с одним условием Firestore строит **индекс автоматически**.
- **Что теряем / риски:** документ **без** поля `date` в такой выборке **не появится вообще** (так устроен `orderBy`). Руками из консоли добавляйте запись с датой.

### Решение 4: самочувствие хранится именем значения

- **Выбрано:** `feeling: 'verySatisfied'`.
- **Почему:** раздел 2.2. Незнакомое или пустое значение читается как `neutral` (одна «странная» запись не роняет список).
- **Что теряем / риски:** **переименовывать значения enum нельзя** (старые записи станут «нейтральными»). Это закреплено тестом `feeling_test.dart`: он упадёт, если имена изменят.

### Решение 5: терпимое чтение, строгая запись

- **Выбрано:** `entryFromMap` не бросает исключений (пустая строка, дата `1970`, `neutral`); правила и форма записи **строгие**.
- **Почему:** «читаем щедро, пишем аккуратно». Данные могла испортить консоль, старая версия приложения, другой клиент. Падение **всего списка** из-за одной записи хуже, чем «странная» запись.
- **Что теряем / риски:** испорченная запись молча показывается как пустая. Для учебного дневника это приемлемо; в продакшене такое логируют.

### Решение 6: интерфейс `DiaryRepository` и своя модель `DiaryEntry`

- **Выбрано:** как и `AuthService` (ex00, решение 3): экраны зависят от интерфейса; Firestore спрятан в `FirestoreDiaryRepository`.
- **Почему:** тест профиля **не должен** требовать проект Firebase. Подделка `FakeDiaryRepository` воспроизводит и «живой список», и «сервер молчит».
- **Что теряем / риски:** лишний слой перевода (`entry_mapper.dart`). Он же сам окупается тестами.

### Решение 7: `EntryDraft` и `DiaryEntry extends EntryDraft`

- **Выбрано:** черновик (без id) и запись (с id) как два класса, второй наследует первый.
- **Почему:** id выдаёт **база**, поэтому у новой записи его ещё нет. Один класс с `String? id` заставил бы везде проверять на `null`. С двумя типами компилятор **сам** не даст спутать.
- **Что теряем / риски:** наследование ради одного поля это почти максимум допустимого; если полей станет больше, лучше композиция.

### Решение 8: `add` ограничен восемью секундами ожидания, но запись не отменяется

- **Выбрано:** `action().timeout(writeConfirmationTimeout)` и сообщение «Saved on this device...».
- **Почему:** раздел 2.4. Не вешаем интерфейс, не врём.
- **Что теряем / риски:** `.timeout` **не отменяет** саму запись: так и нужно. Но если вы **не** хотите этого (скажем, операция «только онлайн»), потребуется другая схема.

### Решение 9: удаление всегда через вопрос

- **Выбрано:** и из строки, и из окна чтения: `AlertDialog` «Delete this entry?» с названием записи.
- **Почему:** мусорка рядом со строкой это лёгкая цель для случайного нажатия, а удаление необратимо (корзины нет).
- **Что теряем / риски:** лишнее нажатие. Альтернатива «отменить» (Undo) в полоске приятнее, но требует хранить удалённое: сложнее (раздел 5).

### Решение 10: окно чтения с кнопкой Delete, закрывающее себя результатом `true`

- **Выбрано:** окно возвращает `true` по «Delete» и `null` по «Close»; вопрос и удаление делает **профиль**.
- **Почему:** окно **ничего не знает** о базе. Один путь удаления (`_confirmAndDelete`) на оба места.
- **Что теряем / риски:** тип результата `bool?` (три состояния: `true`, `false`, `null`) придётся помнить; сравниваем строго с `true`.

### Решение 11: форма в диалоге, а не отдельная страница

- **Выбрано:** `AlertDialog` с `scrollable: true`.
- **Почему:** сабж: «кнопка создать новую запись» без требований к странице. Диалог короче в коде, а `scrollable` спасает на маленьком экране с клавиатурой.
- **Что теряем / риски:** на планшете окно мелковато; для длинных записей стоило бы сделать полноэкранную страницу.

### Решение 12: самочувствие: пять вариантов, значок **и** подпись **и** цвет

- **Выбрано:** `ChoiceChip` с значком лица, подписью («Very happy», «Happy», «Neutral», «Sad», «Very sad») и цветом.
- **Почему:** цвет не должен быть **единственным** носителем смысла (дальтонизм). У каждого значения свой значок и своя подпись.
- **Что теряем / риски:** вопрос, какие пять вариантов «правильные», в сабже не задан; взяты привычные.

### Решение 13: охранник профиля и возврат до первой страницы

- Описано в [04-ex00, решение 7](04-ex00.md#решение-7-профиль-охраняется-двумя-способами).

### Решение 14: правила: `update: false`

- **Выбрано:** запретить обновления.
- **Почему:** сабж просит создать, прочитать, удалить; **минимум прав**. Нужна правка: правило меняют осознанно, а не случайно открывают.
- **Что теряем / риски:** если в модуле 05 понадобится править, нужно будет поправить правила **и** опубликовать их заново.

## 4. Разбор кода

### 4.1 Слои по порядку

#### Слой 1: spike (раздел 1.6)

Ничего не пишем: руками создаём коллекцию в консоли и смотрим, как выглядят документы.

#### Слой 2: модели

**`lib/models/feeling.dart`**:

```dart
// «Самочувствие дня»: пять ступеней от «отлично» до «очень плохо».
//
// Храним в базе ИМЯ значения (строку 'satisfied'), а не номер: если завтра мы
// переставим значения местами или добавим новое, старые записи останутся верными.
// В примере из сабжа поле называется icon и тоже хранит строку «satisfied».
enum Feeling {
  verySatisfied('Very happy'),
  satisfied('Happy'),
  neutral('Neutral'),
  dissatisfied('Sad'),
  veryDissatisfied('Very sad');

  const Feeling(this.label);

  // Подпись для человека (на экране и в подсказках скринридера).
  final String label;

  // Значение из базы -> Feeling. Незнакомое или пустое значение не должно
  // ронять список: берём «нейтрально» (одна «странная» запись не ломает остальные).
  static Feeling fromName(Object? name) {
    for (final Feeling feeling in Feeling.values) {
      if (feeling.name == name) return feeling;
    }
    return Feeling.neutral;
  }
}
```

Разбор:

- **Enum с полем:** `verySatisfied('Very happy')`: каждое значение несёт подпись для человека. Конструктор `const Feeling(this.label)`.
- `feeling.name` (встроенное свойство enum) даёт строку `'verySatisfied'`; её мы и храним.
- `fromName(Object? name)`: принимает **что угодно** (из базы приходит `dynamic`) и обходит значения в поисках совпавшего имени. Нашлось, возвращаем его; иначе `Feeling.neutral`. Это решение 5 в одной функции.

**`lib/models/diary_entry.dart`**:

```dart
import 'feeling.dart';

// Что вводит пользователь и что дописывает приложение, ещё БЕЗ номера записи.
// Номер (id) выдаёт база при сохранении, поэтому у «черновика» его нет.
class EntryDraft {
  const EntryDraft({
    required this.email,
    required this.date,
    required this.title,
    required this.feeling,
    required this.content,
  });

  final String email; // почта автора (требование сабжа; у GitHub может быть пустой)
  final DateTime date; // когда записано
  final String title;
  final Feeling feeling; // самочувствие дня
  final String content;
}

// Запись, уже лежащая в базе: черновик плюс её номер.
class DiaryEntry extends EntryDraft {
  const DiaryEntry({
    required this.id,
    required super.email,
    required super.date,
    required super.title,
    required super.feeling,
    required super.content,
  });

  final String id;

  // Равенство по значению нужно тестам («в списке лежит именно эта запись»).
  @override
  bool operator ==(Object other) =>
      other is DiaryEntry &&
      other.id == id &&
      other.email == email &&
      other.date == date &&
      other.title == title &&
      other.feeling == feeling &&
      other.content == content;

  @override
  int get hashCode => Object.hash(id, email, date, title, feeling, content);

  @override
  String toString() => 'DiaryEntry($id, $title)';
}
```

Разбор:

- `EntryDraft`: то, что пользователь вводит (`title`, `feeling`, `content`) **плюс то, что дописывает приложение** (`email`, `date`). Всё `final`: запись неизменяема.
- `DiaryEntry extends EntryDraft`: добавляет `id`. `required super.email` (Dart 3: «параметр передаётся прямо в родительский конструктор»).
- `operator ==` и `hashCode`: равенство **по значению** (как у `AppUser`); пригодится тестам («в списке лежит именно эта запись»).

#### Слой 3: переводчик «запись ↔ документ»

**`lib/services/entry_mapper.dart`**:

```dart
import 'package:cloud_firestore/cloud_firestore.dart' show Timestamp;

import '../models/diary_entry.dart';
import '../models/feeling.dart';

// Перевод «запись <-> то, что лежит в Firestore». Отдельно от репозитория, чтобы
// проверять обычными тестами (без базы и без интернета).
//
// Поля документа (имена как в сабже: email, date, title, feeling, content):
//   email    string      почта автора
//   date     timestamp   когда записано
//   title    string      заголовок
//   feeling  string      имя значения Feeling ('satisfied', ...)
//   content  string      текст записи

const String fieldEmail = 'email';
const String fieldDate = 'date';
const String fieldTitle = 'title';
const String fieldFeeling = 'feeling';
const String fieldContent = 'content';

Map<String, Object?> draftToMap(EntryDraft draft) => {
  fieldEmail: draft.email,
  // Timestamp: родной тип даты Firestore (в консоли показывается как дата и время).
  fieldDate: Timestamp.fromDate(draft.date),
  fieldTitle: draft.title,
  fieldFeeling: draft.feeling.name,
  fieldContent: draft.content,
};

// Читаем ТЕРПИМО: пропавшее или кривое поле даёт безопасное значение, а не
// исключение. Иначе одна испорченная запись (скажем, добавленная руками в
// консоли) уронила бы весь список.
DiaryEntry entryFromMap(String id, Map<String, Object?> data) => DiaryEntry(
  id: id,
  email: _string(data[fieldEmail]),
  date: _date(data[fieldDate]),
  title: _string(data[fieldTitle]),
  feeling: Feeling.fromName(data[fieldFeeling]),
  content: _string(data[fieldContent]),
);

String _string(Object? value) => value is String ? value : '';

DateTime _date(Object? value) {
  if (value is Timestamp) return value.toDate();
  if (value is DateTime) return value;
  return DateTime.fromMillisecondsSinceEpoch(0); // дата не читается: «1970»
}
```

Разбор:

- Имена полей вынесены в **константы** (`fieldEmail`...): опечатка в строке `'titel'` не найдётся компилятором, а в константе найдётся. Они же используются в `orderBy(fieldDate)` репозитория.
- `draftToMap`: `Map<String, Object?>`; дата превращается в `Timestamp.fromDate`; самочувствие в `feeling.name`.
- `entryFromMap`: четыре маленьких помощника `_string`/`_date`/`Feeling.fromName`: каждый **не бросает**, а возвращает безопасное значение (`''`, `1970`, `neutral`). Условие `value is String ? value : ''`: «если это строка, берём её, иначе пустую».
- Функции верхнего уровня, не методы: не нужен объект, нужны только данные; проверять их проще всего.

#### Слой 4: хранилище

**`lib/services/diary_repository.dart`**:

```dart
import '../models/diary_entry.dart';

// Что может пойти не так при работе с базой.
sealed class DiaryFailure implements Exception {
  const DiaryFailure(this.message);

  final String message;

  @override
  String toString() => message;
}

// Правила базы не пустили (не тот пользователь, не прошла проверка данных).
class DiaryPermissionDenied extends DiaryFailure {
  const DiaryPermissionDenied()
    : super('The database refused this action. Try signing out and in again.');
}

// Нет связи с сервером.
class DiaryUnavailable extends DiaryFailure {
  const DiaryUnavailable()
    : super('Cannot reach the database. Check your internet connection.');
}

class DiaryUnknownFailure extends DiaryFailure {
  const DiaryUnknownFailure([String details = ''])
    : super(details == '' ? 'Something went wrong with the diary.' : 'Something went wrong: $details');
}

// Хранилище записей. Экраны знают только этот интерфейс; настоящая работа с
// Firestore спрятана в FirestoreDiaryRepository, а в тестах стоит подделка.
abstract interface class DiaryRepository {
  // Живой список записей пользователя, новые сверху. Присылает новый список при
  // каждом изменении (добавили, удалили, пришло с другого устройства), поэтому
  // экрану не нужно «обновлять» его вручную. Ошибки приходят как error в потоке.
  Stream<List<DiaryEntry>> watchEntries(String userId);

  // Создать запись. Future завершается, когда СЕРВЕР подтвердил: без сети он
  // может висеть долго (а запись при этом уже видна в watchEntries).
  Future<void> add(String userId, EntryDraft draft);

  // Удалить запись (то же замечание про ожидание сервера).
  Future<void> delete(String userId, String entryId);
}
```

- Три вида ошибок хранилища (`DiaryPermissionDenied`, `DiaryUnavailable`, `DiaryUnknownFailure`), всё как у `AuthFailure`: `sealed`, готовая фраза в `message`.
- Три операции: `watchEntries(userId)`, `add(userId, draft)`, `delete(userId, entryId)`. Комментарии в интерфейсе **предупреждают** про `Future`, который ждёт сервер (раздел 2.4).

**`lib/services/firestore_diary_repository.dart`**:

```dart
import 'dart:async';

import 'package:cloud_firestore/cloud_firestore.dart';

import '../models/diary_entry.dart';
import 'diary_repository.dart';
import 'entry_mapper.dart';

// Настоящее хранилище на Cloud Firestore.
//
// Где лежат записи:  users/{uid}/entries/{id}
//   users            коллекция пользователей (документов-«папок», самих данных в них нет)
//   {uid}            идентификатор пользователя из Firebase Auth
//   entries          его записи; у каждой автоматический id
//
// Так «чужие» записи недоступны по самому ПУТИ (правила в firestore.rules
// сверяют uid из пути с uid вошедшего), и не нужен составной индекс.
class FirestoreDiaryRepository implements DiaryRepository {
  FirestoreDiaryRepository([FirebaseFirestore? firestore])
    : _db = firestore ?? FirebaseFirestore.instance;

  final FirebaseFirestore _db;

  CollectionReference<Map<String, dynamic>> _entries(String userId) =>
      _db.collection('users').doc(userId).collection('entries');

  @override
  Stream<List<DiaryEntry>> watchEntries(String userId) {
    return _entries(userId)
        .orderBy(fieldDate, descending: true) // новые сверху
        .snapshots()
        .map(
          (QuerySnapshot<Map<String, dynamic>> snapshot) => [
            for (final QueryDocumentSnapshot<Map<String, dynamic>> doc in snapshot.docs)
              entryFromMap(doc.id, doc.data()),
          ],
        )
        .transform(
          StreamTransformer<List<DiaryEntry>, List<DiaryEntry>>.fromHandlers(
            handleError: (Object error, StackTrace stack, EventSink<List<DiaryEntry>> sink) {
              sink.addError(_translate(error), stack);
            },
          ),
        );
  }

  @override
  Future<void> add(String userId, EntryDraft draft) async {
    try {
      await _entries(userId).add(draftToMap(draft));
    } catch (e) {
      throw _translate(e);
    }
  }

  @override
  Future<void> delete(String userId, String entryId) async {
    try {
      await _entries(userId).doc(entryId).delete();
    } catch (e) {
      throw _translate(e);
    }
  }

  // Ошибка Firestore -> наша. Коды: permission-denied (правила не пустили),
  // unavailable (нет связи).
  static DiaryFailure _translate(Object error) {
    if (error is DiaryFailure) return error;
    if (error is FirebaseException) {
      switch (error.code) {
        case 'permission-denied':
          return const DiaryPermissionDenied();
        case 'unavailable':
          return const DiaryUnavailable();
      }
      return DiaryUnknownFailure(error.code);
    }
    return DiaryUnknownFailure('$error');
  }
}
```

Разбор:

- `_entries(userId)`: ссылка на подколлекцию `users/{uid}/entries`. Метод, чтобы путь был написан **в одном месте**.
- `watchEntries`:
  - `.orderBy(fieldDate, descending: true)`: новые сверху;
  - `.snapshots()`: живой поток снимков;
  - `.map(...)`: каждый снимок превращается в `List<DiaryEntry>` (список-выражение `[ for (...) ... ]`);
  - `.transform(StreamTransformer.fromHandlers(handleError: ...))`: **ошибки** потока (например, `permission-denied`) тоже переводятся в наши `DiaryFailure`. Без этого экран получил бы сырое исключение Firebase.
- `add` и `delete`: `try { await ... } catch (e) { throw _translate(e); }`.
- `_translate`: `permission-denied` → `DiaryPermissionDenied`; `unavailable` → `DiaryUnavailable`; остальные коды → `DiaryUnknownFailure(code)`. Незнакомое не прячем, показываем код.
- **Чего здесь нет:** ни слова про `Future` с таймаутом: это дело экрана (решение 8), хранилище честно отдаёт, как есть.

#### Слой 8: профиль

**`lib/ui/profile_page.dart`**:

```dart
import 'dart:async';

import 'package:material_ui/material_ui.dart';

import '../app_services.dart';
import '../config.dart';
import '../models/app_user.dart';
import '../models/diary_entry.dart';
import '../services/diary_repository.dart';
import 'entry_dialog.dart';
import 'feeling_icon.dart';
import 'formatters.dart';
import 'new_entry_dialog.dart';

// Профиль: список записей, кнопка «New diary entry», чтение и удаление.
//
// ДОСТУП ТОЛЬКО ДЛЯ ВОШЕДШИХ держится на двух вещах:
//   1. конструктор требует НЕ-null AppUser: профиль нельзя построить без
//      пользователя (компилятор не даст), поэтому к нему ведут только из мест,
//      где вход уже случился;
//   2. страница следит за authStateChanges и, если вход пропал (выход, отзыв
//      доступа), сама возвращает на приветствие.
// Настоящая защита данных всё равно в правилах Firestore (firestore.rules).
class ProfilePage extends StatefulWidget {
  const ProfilePage({super.key, required this.services, required this.user});

  final AppServices services;
  final AppUser user;

  @override
  State<ProfilePage> createState() => _ProfilePageState();
}

class _ProfilePageState extends State<ProfilePage> {
  late Stream<List<DiaryEntry>> _entries;
  StreamSubscription<AppUser?>? _authSubscription;

  @override
  void initState() {
    super.initState();
    _subscribeToEntries();
    // Охранник: вход пропал, значит уходим на приветствие.
    _authSubscription = widget.services.auth.authStateChanges().listen((AppUser? user) {
      if (user == null) _backToLogin();
    });
  }

  @override
  void dispose() {
    _authSubscription?.cancel();
    super.dispose();
  }

  // Поток создаём ОДИН раз (а не в build): иначе каждая перерисовка
  // переподписывалась бы на базу заново.
  void _subscribeToEntries() {
    _entries = widget.services.diary.watchEntries(widget.user.uid);
  }

  void _backToLogin() {
    if (!mounted) return;
    // До первой страницы (приветствия); заодно закрываются открытые окна.
    Navigator.of(context).popUntil((Route<dynamic> route) => route.isFirst);
  }

  Future<void> _signOut() async {
    // Сам переход сделает охранник, когда придёт «вошедших нет».
    await widget.services.auth.signOut();
  }

  // --- запись в базу с понятным поведением без сети --------------------------
  //
  // Без связи Firestore принимает запись в локальный кэш (список уже обновился),
  // а Future из add()/delete() завершится только когда ответит сервер, то есть,
  // возможно, через часы. Ждать вечно нельзя: через writeConfirmationTimeout
  // говорим, что записано на устройстве и отправится позже.
  Future<void> _runWrite(Future<void> Function() action, String pendingMessage) async {
    final ScaffoldMessengerState messenger = ScaffoldMessenger.of(context);
    try {
      await action().timeout(writeConfirmationTimeout);
    } on TimeoutException {
      messenger.showSnackBar(SnackBar(content: Text(pendingMessage)));
    } on DiaryFailure catch (failure) {
      messenger.showSnackBar(SnackBar(content: Text(failure.message)));
    }
  }

  Future<void> _newEntry() async {
    final NewEntryData? data = await showDialog<NewEntryData>(
      context: context,
      builder: (BuildContext context) => const NewEntryDialog(),
    );
    if (data == null || !mounted) return;

    final EntryDraft draft = EntryDraft(
      email: widget.user.email,
      date: widget.services.now(),
      title: data.title,
      feeling: data.feeling,
      content: data.content,
    );
    await _runWrite(
      () => widget.services.diary.add(widget.user.uid, draft),

- **`_EmptyView`/`_ErrorView`.** Простые виджеты по центру.

// Правила доступа Cloud Firestore для diary_app (модуль 04).
//
// Куда вставить: консоль Firebase -> Firestore Database -> вкладка Rules ->
// вставить файл целиком -> Publish. Или из командной строки (нужен Firebase CLI):
// firebase deploy --only firestore:rules
//
// Идея: пользователь видит и меняет ТОЛЬКО свои записи, лежащие по пути
// users/{его uid}/entries/{id}. Всё остальное запрещено по умолчанию.
rules_version = '2';

service cloud.firestore {
  match /databases/{database}/documents {

    match /users/{userId}/entries/{entryId} {

      // Читать (получить одну запись или список) и удалять: только владельцу.
      allow read, delete: if request.auth != null && request.auth.uid == userId;

      // Создать: владельцу и только запись правильной формы.
      allow create: if request.auth != null
        && request.auth.uid == userId
        // ровно эти поля, без лишних и без пропущенных
        && request.resource.data.keys().hasOnly(['email', 'date', 'title', 'feeling', 'content'])
        && request.resource.data.keys().hasAll(['email', 'date', 'title', 'feeling', 'content'])
        // типы и пределы (те же числа, что в lib/config.dart)
        && request.resource.data.email is string
        && request.resource.data.date is timestamp
        && request.resource.data.title is string
        && request.resource.data.title.size() > 0
        && request.resource.data.title.size() <= 100
        && request.resource.data.feeling in ['verySatisfied', 'satisfied', 'neutral', 'dissatisfied', 'veryDissatisfied']
        && request.resource.data.content is string
        && request.resource.data.content.size() > 0
        && request.resource.data.content.size() <= 5000;

      // Править существующие записи сабж не требует: запрещаем (профиль модуля 05
      // по сабжу тоже только читает и удаляет). Понадобится правка, правило меняют осознанно.
      allow update: if false;
    }
  }
}
```

Разбор:

- `rules_version = '2'`: текущий диалект.
- `match /users/{userId}/entries/{entryId}`: **путь с переменными**; `userId` потом можно использовать в условии.
- `allow read, delete: if request.auth != null && request.auth.uid == userId`: вошёл и владелец.
- `allow create`: владелец **и** форма данных: `keys().hasOnly([...])` (никаких лишних полей), `keys().hasAll([...])` (все на месте), типы (`is string`, `is timestamp`), длины (`size()`), `feeling in [...]`.
- `allow update: if false`: прямо запрещено (и без этой строки запрещено «по умолчанию», но явная строка читается как намерение).
- **Чего нет:** правила для всего остального. Любой путь вне `users/{uid}/entries` **закрыт**.

## 5. Альтернативы

| Подход | Суть | Плюсы | Минусы | Когда подойдёт |
|---|---|---|---|---|
| **Cloud Firestore, подколлекция на пользователя** (выбрано) | см. выше | живые обновления, офлайн, простые правила | привязка к Google; модель документов непривычна | наш случай |
| Firestore, общая коллекция `entries` с полем `uid` | один список всех записей | запросы по всем пользователям | составной индекс; правила и запросы сложнее | аналитика, общие записи |
| Firebase Realtime Database | старая база Firebase (JSON-дерево) | очень быстрые обновления | слабее запросы и модель | простые «чат»-данные |
| Supabase (Postgres) | SQL, открытый код | мощные запросы, RLS-правила | другая настройка, отдельный аккаунт | если нужен SQL |
| AWS Amplify (DynamoDB/AppSync) | облако Amazon | корпоративные возможности | тяжело и дорого настраивать | компания на AWS |
| Локальная БД (`sqflite`, `drift`, `isar`) | файл на телефоне | работает без облака, быстро | нет синхронизации между устройствами; сабж говорит о системе с пользователями | офлайн-дневник без аккаунтов |
| `shared_preferences` / файл JSON | просто сохранить текст | минимум кода | не масштабируется, нет «базы» | заметка, настройка |
| `get()` + кнопка «обновить» | разовая загрузка | проще | список не обновляется сам: нарушает сабж | статичные данные |
| `StreamBuilder` над `snapshots()` (выбрано) | живой поток | обновляется само, офлайн из коробки | подписку нужно создавать один раз | наш случай |
| `ChangeNotifier` + подписка в контроллере | состояние в отдельном объекте (как в модуле 02) | чище при росте логики | больше кода | когда экранов с этим списком несколько |
| Время клиента (`DateTime.now()`) | дата с телефона | видна сразу, работает без сети | часы могут быть неверны | наш случай |
| `FieldValue.serverTimestamp()` | время сервера | единые часы | до ответа сервера поле `null`, запись «скачет» | журнал аудита |
| Удаление с «Undo» вместо вопроса | запись исчезает, в полоске «Undo» | приятнее | нужно хранить удалённое и уметь вернуть | зрелое приложение |
| «Мягкое» удаление (флаг `deleted`) | запись скрывается, а не стирается | можно восстановить | правила и запросы сложнее | если нужна корзина |
| Правила через Cloud Functions | проверка на своём сервере | любая логика | нужен тариф Blaze и код сервера | сложная бизнес-логика |
| Тестовый режим базы (разрешено всё 30 дней) | быстро стартовать | не нужны правила | **любой в интернете** прочтёт и сотрёт, потом всё закроется само | никогда для личных данных |
| Полноэкранная страница новой записи | отдельный экран | удобно писать длинное | больше кода | когда записи длинные |

2. Если Google требует номер телефона для подтверждения, используйте свой **один раз**; привязку можно будет убрать позже.
3. Установите приложение на телефон и **войдите этим аккаунтом** (так создастся пользователь и его uid в базе).
4. Создайте **5-6 записей** **через приложение**, а не вручную в консоли (иначе структура может не совпасть с ожиданиями): разные заголовки, **все пять самочувствий**, одна длинная запись (проверка прокрутки), одна с эмодзи, одна «вчерашней» датой, если захотите (дату приложение ставит само: `now()`, поэтому «вчерашнюю» не получится; это нормально).
5. В консоли проверьте: `Authentication → Users` показывает этот аккаунт; `Firestore → users → {uid} → entries` содержит записи.
6. **Выйдите** из приложения (Log out): проверяющий сам войдёт этим аккаунтом.
7. **Проверьте вход с другого устройства или в окне инкогнито**, что аккаунт **не блокируется** (раздел 6.6 ex00: экран согласия, test users).
8. Передайте проверяющему логин и пароль **безопасным способом** (лично, а не в публичном репозитории и не в README). После защиты смените пароль или удалите аккаунт.

## 7. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| В профиле «The database refused this action...» | правила не опубликованы или запрещают | опубликовать `firestore.rules` (6.3); проверить Rules Playground |
| Профиль: «Cannot reach the database» | нет сети или база не создана | проверить сеть; Firestore → Create database (6.2) |
| В консоли у записи нет поля `date` / запись не видна в приложении | `orderBy('date')` не показывает документы без поля | добавить поле `date` типа timestamp |
| Запись, добавленная в консоли, не появляется | неверные имена/типы полей, нет `date`, или она лежит в другом пути | путь `users/{uid}/entries/...` с **вашим** uid |
| Запись появляется, но «пустая» (`1970`, без заголовка) | типы полей неправильные (дата строкой) | `date` типа timestamp, остальные string |
| Запись не сохраняется, в логе `permission-denied` | правило `create` не пропустило данные | лишнее поле, пустой заголовок/текст, слишком длинное, неверное `feeling` |
| Сохранили, список не обновился | потока нет или он пересоздаётся в `build` | поток создаётся в `initState` (раздел 2.3) |
| Список «мигает» индикатором при каждом действии | подписка пересоздаётся | то же |
| Полоска «Saved on this device...» при нормальной сети | сервер отвечает дольше 8 секунд или запись заблокирована | проверить сеть и правила; увеличить `writeConfirmationTimeout` |
| Консоль: «Missing or insufficient permissions» | то же `permission-denied` | правила (см. выше) |
| Запрос просит индекс (ссылка в логе) | в запросе появился `where` + `orderBy` по разным полям | наш запрос не требует; если добавляли условие, создайте индекс по ссылке из лога |
| Профиль открывается без входа в тесте | в подделке задан `signedIn` | проверить `Harness` |
| `flutter test`: `Bad state: No element` на `find.text` | текста нет: подпись изменилась | сверьте с `helpers.dart` и разделом 4.1 |
| `flutter test`: `A Timer is still pending` | в тесте остался таймер `timeout` | довести `tester.pump(writeConfirmationTimeout + ...)` |
| Тест: `The finder "..." could not find any matching widgets` на `ChoiceChip` | окно длиннее экрана теста | в тесте увеличить размер (`tester.view.physicalSize`) или прокрутить `scrollUntilVisible` |
| При создании записи окно закрывается, а записи нет | `writeFailure` в тесте или `permission-denied` в жизни | сообщение в полоске скажет, что именно |
| `use_build_context_synchronously` | `context` после `await` | брать `ScaffoldMessenger.of(context)` до `await`, проверять `mounted` |

## 8. Безопасность и риски

- **Правила это защита; интерфейс нет.** Любая проверка в приложении (формы, закрытый профиль) обходится. Правила проверяют **на сервере**. Опубликованы ли они, нужно проверить **отдельно** (6.3, 6.5).
- **Режим тестирования.** Если база создана в **test mode**, правила «разрешить всё» действуют **30 дней** и открывают дневник **всему интернету**; потом включается запрет «само», и приложение внезапно ломается. Production mode и свои правила с первого дня.
- **Приватность дневника.** Записи **не шифруются** на стороне клиента: администратор проекта Firebase (то есть вы) видит их в консоли. Для чужого дневника это важно сказать в политике конфиденциальности. Сквозное шифрование (ключ только у пользователя) возможно, но усложняет поиск и восстановление.
- **Почта в каждой записи.** Требование сабжа. Это **копия** почты, которая устаревает, если пользователь поменяет адрес; источником истины остаётся Firebase Auth.
- **Размер и стоимость.** Каждый заход читает **все** записи (снимок целиком). Для тысяч записей это дорого по чтениям: нужна постраничная загрузка (`limit`, `startAfter`). Бесплатные квоты и цены смотрите на странице тарифов Firebase: они меняются.
- **Клиентские часы** (раздел 2.9): дата записи может быть неверной, если часы сбиты.
- **Удаление необратимо.** Корзины нет; вопрос перед удалением единственная защита.
- **Аккаунт проверяющего.** Пароль отдельный и временный; не в репозиторий; после защиты поменять или удалить. Записи в нём **вымышленные**: это публичный для проверяющего аккаунт, личного там быть не должно.
- **Офлайн-кэш на устройстве.** Записи лежат на телефоне в локальном кэше Firestore. Если телефон общий, **выходите** и не оставляйте приложение открытым. (Очищает ли Log out этот кэш, я не проверяла: по умолчанию `signOut` его не стирает.)
- **Риск «непроверенного кода».** Правила, поведение без сети и внешний вид не запускались (см. пометку вверху).

## 10. Что запомнить

**Dart:**

- `Future.timeout(срок)` бросает `TimeoutException`, но **не отменяет** сам `Future`: операция продолжается.
- `bool?` имеет три состояния (`true`, `false`, `null`): сравнивайте `== true`, если `null` означает «закрыли окно».
- `[for (final x in xs) f(x)]`: список-выражение (collection for).
- `super.поле` в конструкторе: передать параметр прямо в родителя.
- `enum` с полями и методом: `Feeling.verySatisfied('Very happy')`; `.name` даёт строку-имя.
- `String.trim()` убирает пробелы по краям; `padLeft(2, '0')` добавляет нули.
- `() => действие`: передать **действие**, а не выполнить сразу.

**Flutter:**

- `StreamBuilder` + поток, созданный **один раз** в `initState`, а не в `build`.
- `Form` + `GlobalKey<FormState>` + `validator` (`null` значит «хорошо»), `maxLength` рисует счётчик.
- `showDialog<T>` возвращает `Future<T?>`; `pop(value)` завершает его; `null` значит «закрыли без выбора».
- `AlertDialog(scrollable: true)`; `ListView.builder` строит только видимое; нижний отступ списка под плавающую кнопку.
- `SnackBar` через `ScaffoldMessenger`, взятый **до** `await`; после `await` проверять `mounted`.

**Firestore:**

- Данные: **коллекции → документы → поля (и подколлекции)**; путь `users/{uid}/entries/{id}`.
- `snapshots()` даёт **живой** список: код записи/удаления список не трогает, он обновляется как следствие.
- Без сети запись **сразу** видна (локальный кэш), а `Future` ждёт сервер: ограничивайте ожидание и **честно** говорите «сохранено на устройстве».
- `orderBy('date')` скрывает документы **без** поля `date`.
- Правила на сервере единственная настоящая защита: владелец по пути, форма данных (`hasOnly`, `hasAll`, типы, длины), `update: false`, **production mode** с первого дня.
- Значения enum в базе хранятся **именем**; переименование ломает старые записи (тест это закрепляет).

**Архитектура и работа:**

- Читайте **щедро**, пишите **строго**: один испорченный документ не должен ронять список.
- Два типа вместо `String? id`: `EntryDraft` (без id) и `DiaryEntry` (с id).
- Для защиты: аккаунт проверяющего с **вымышленными** записями, создан и проверен **заранее**, пароль не в репозитории.

> **Про непроверенный код.** Этот файл и весь код к нему написаны без запуска Flutter и без настоящего проекта Firebase. Особенно перепроверьте: публикацию и работу правил (6.5), поведение без сети (6.4, пункт 8) и вход аккаунтом проверяющего (6.6).
