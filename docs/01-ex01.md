# Модуль 01, ex01: TopBar

> Второе упражнение модуля 01: оживляем верхнюю панель. Поле поиска и кнопка геолокации начинают **менять то, что показано на всех вкладках**. Главная новая тема: **подъём состояния** (lifting state up): два «соседних» места экрана (верхняя панель и страницы вкладок) должны видеть одни и те же данные, поэтому данные живут в общем родителе, а изменения поднимаются к нему через колбэки.

API сверены по исходникам `material_ui` и Flutter 3.35, но `flutter analyze` и `flutter test` ещё не гонялись. Первый прогон ваш; если что-то красное, смотрите [раздел 7](#7-диагностика).

## 1. Задача и с чего начать

### 1.1 Условия сабжа

- **Папка сдачи:** `mobileModule01`
- **Файлы для сдачи:** `weather_app` и все необходимые файлы (тот же проект, что и в ex00)
- **Запрещённые функции:** нет
- **Сабж:** *«и поле поиска, и кнопка геолокации должны работать правильно; приложение показывает либо введённый текст, либо данные геолокации, в зависимости от того, чем воспользовались»*.

### 1.2 Проблема

- Если ввести текст в поле поиска, **на всех вкладках** показывается **название вкладки и введённый текст**.
- Если нажать кнопку геолокации, **на всех вкладках** показывается **название вкладки и слово «Geolocation»**.
- «Либо то, либо другое»: показывается **последнее** действие пользователя.

Пример: ввели «Paris» и открыли Today. Страница показывает «Today» и под ним «Paris». Нажали кнопку геолокации. Страница показывает «Today» и «Geolocation». Свайпнули на Weekly. Там «Weekly» и «Geolocation».

### 1.3 Требования

**Функциональные:**

- Ввод текста: введённая строка видна на **каждой** вкладке рядом с названием вкладки.
- Кнопка геолокации: слово «Geolocation» видно на каждой вкладке.
- Переключение между «текстом» и «геолокацией» работает в обе стороны и сколько угодно раз.
- Всё из ex00 по-прежнему работает: старт на Currently, нажатие и свайп.

**Нефункциональные:**

- Адаптивность: ни при каком вводе (длинная строка, крупный шрифт, ландшафт, клавиатура) нет overflow.
- `flutter analyze`: `No issues found!`; `flutter test`: зелёный.
- Код пригоден «на вырост»: в модуле 02 на место слова «Geolocation» придут настоящие координаты, а на место текста — результат геокодинга.

### 1.4 Что не входит в задачу (non-goals)

- Реальная геолокация (GPS, разрешения): модуль 02.
- Запросы в сеть, подсказки городов, история поиска.
- Задержка ввода (debounce): нужна только когда каждый символ запускает сетевой запрос.
- Сохранение введённого между запусками.
- Менеджеры состояния (Provider, Riverpod, BLoC): избыточны.

### 1.5 Критерии успеха

- [ ] Ввод текста сразу виден на текущей вкладке и на всех остальных.
- [ ] Кнопка геолокации показывает «Geolocation» на всех вкладках.
- [ ] После кнопки поле пустеет, и новый ввод заменяет «Geolocation».
- [ ] Пустое или пробельное поле возвращает чистые вкладки (только названия).
- [ ] Нет overflow ни в одной ориентации и ни при каком шрифте.
- [ ] `flutter analyze` и `flutter test` зелёные.

### 1.6 Первый шаг (spike)

Самый дешёвый способ проверить главную идею: в `HomePage` (состояние) временно задать **жёсткое значение**, например `_request = const TextSearch('test')`, и убедиться, что «test» появилось на всех трёх вкладках. Это **слой 2** ниже. Если данные дошли до страниц, остаётся лишь научить верхнюю панель их менять.

## 2. Теория

### 2.1 Подъём состояния: кто хозяин данных

Задача: данные (что искали) **пишет** верхняя панель, а **читают** страницы вкладок. Это два разных поддерева виджетов, которые друг друга не знают:

```
HomePage            ← ХОЗЯИН: хранит _request
├── SearchAppBar    ← ПИШЕТ: «пользователь что-то ввёл»  (событие уходит ВВЕРХ)
└── TabBarView
    ├── TabPage     ← ЧИТАЕТ: показывает _request        (данные идут ВНИЗ)
    ├── TabPage
    └── TabPage
```

Правило Flutter: **данные идут вниз параметрами, события идут вверх колбэками.** Состояние живёт в **ближайшем общем родителе** всех, кто его использует. Это и есть «подъём состояния»: поле поиска не может хранить результат у себя (страницы его не увидят), поэтому результат живёт в `HomePage`.

Цикл одного ввода:

1. Пользователь вводит символ в `TextField`.
2. `TextField` вызывает `onChanged(text)`.
3. `SearchAppBar` превращает текст в `SearchRequest` и вызывает **колбэк** `onRequest(request)`: то есть функцию, которую ему дал `HomePage`.
4. `HomePage` в `setState` записывает `_request = request`.
5. Flutter заново вызывает `HomePage.build`: создаются новые `TabPage` с новым `request`.
6. Страницы показывают новое значение.

### 2.2 sealed class и switch-выражения (Dart 3)

Что искали: либо **текст**, либо **геолокацию**. Третьего не бывает. Для такой ситуации в Dart 3 есть `sealed class`:

```dart
sealed class SearchRequest {
  const SearchRequest();
  String get label => switch (this) {
    TextSearch(:final query) => query,
    GeolocationSearch() => 'Geolocation',
  };
}
final class TextSearch extends SearchRequest { ... }
final class GeolocationSearch extends SearchRequest { ... }
```

- **`sealed`**: класс **абстрактный**, а все его наследники обязаны лежать **в том же файле (библиотеке)**. Поэтому компилятор знает **полный список** вариантов.
- **`switch`-выражение** (не оператор!): `switch (x) { образец => значение, ... }` возвращает значение. Ветки разделяются запятыми, `break` не нужен.
- **Исчерпывающая проверка:** для `sealed`-типа компилятор требует разобрать **все** варианты. Забыли один: ошибка компиляции, а не баг в рантайме. Если завтра добавим `CitySearch`, компилятор сам покажет каждый `switch`, который надо дополнить.
- **Образец объекта** `TextSearch(:final query)`: «если это `TextSearch`, достань поле `query` в новую переменную `query`». Двоеточие перед именем значит «поле с тем же именем».
- **`final class`**: от него нельзя наследоваться снаружи. Не обязательно, но полезно: список вариантов закрыт со всех сторон.

Зачем это, если можно просто `String`? См. [решение 2](#решение-2-как-представить-запрос-string-или-sealed-класс).

### 2.3 Nullable и «ничего не искали»

`SearchRequest? _request` — тип «`SearchRequest` **или `null`**». `null` значит «пока ничего не искали» (или поле очистили). Работа с nullable-значением:

```dart
final SearchRequest? request = this.request;   // копия в локальную переменную
if (request != null) {
  request.label;   // здесь компилятор УЖЕ знает, что не null (type promotion)
}
```

Почему копия в **локальную** переменную: для **полей** класса Dart не делает автоматического «понижения» типа (поле теоретически может поменяться между проверкой и использованием), а для локальных переменных делает. Альтернатива: `request!.label` (восклицательный знак «я уверен, что не null», лучше не злоупотреблять) или `request?.label` (вернёт `null`, если `request == null`).

### 2.4 TextField: onChanged, onSubmitted, controller

| Что | Когда срабатывает | Для чего |
|---|---|---|
| `onChanged(text)` | **при каждом** изменении текста пользователем | живой поиск |
| `onSubmitted(text)` | по нажатию «ввод»/«поиск» на клавиатуре | поиск по команде |
| `TextEditingController` | это «пульт» поля: `.text`, `.clear()`, `.selection` | читать и менять текст **из кода** |

**Важное правило, на которое все натыкаются:** `onChanged` вызывается **только когда меняет пользователь**. Если вы программно сделали `_controller.clear()` или `_controller.text = '...'`, `onChanged` **не** вызывается. Мы используем это: после кнопки геолокации очищаем поле и сообщаем наверх **сами**.

**Жизненный цикл контроллера** (мы это учили в ex02, 2.7): создали один раз как поле `State`, **освободили в `dispose`**, `super.dispose()` последней строкой. Забытый `dispose`: утечка.

`textInputAction: TextInputAction.search` просто выбирает, какая клавиша «ввод» будет на экранной клавиатуре (лупа). Нажатие закрывает клавиатуру. Текст к этому моменту уже на экране, поэтому дополнительная обработка не нужна.

### 2.5 PreferredSizeWidget: почему AppBar нельзя «просто завернуть»

`Scaffold.appBar` принимает не любой виджет, а `PreferredSizeWidget`: виджет, который **заранее** умеет назвать свою высоту (`Size get preferredSize`). `Scaffold` нужна эта высота **до** построения, чтобы раздать оставшееся место телу (`body`).

`AppBar` это `PreferredSizeWidget`, а наш `SearchAppBar` (обёртка вокруг `AppBar`) — нет, пока мы не сказали об этом сами:

```dart
class SearchAppBar extends StatefulWidget implements PreferredSizeWidget {
  @override
  Size get preferredSize => const Size.fromHeight(kToolbarHeight);
  ...
}
```

- `implements PreferredSizeWidget`: «обещаю реализовать интерфейс»; `implements`, а не `extends`, потому что наш базовый класс уже `StatefulWidget`.
- `kToolbarHeight` — константа Flutter: **56** dp, стандартная высота панели.

### 2.6 setState и что на самом деле перестраивается

При каждом символе вызывается `HomePage.setState` и **вся** `HomePage.build`. Страшно? Нет, и вот почему:

- `build` только **описывает** дерево (создаёт лёгкие объекты-описания). Реальная работа начинается, когда Flutter **сравнивает** новое описание со старым.
- Flutter сопоставляет «старый» и «новый» виджет **по типу и позиции** (и ключу). Раз тот же тип на том же месте, то **`State` сохраняется**, обновляется только «настройка» (поля виджета).
- Поэтому новый `SearchAppBar` (мы создаём его заново на каждый символ!) **не теряет** свой `_controller` и введённый текст: `State` тот же. И `DefaultTabController` не пересоздаёт контроллер вкладок, выбранная вкладка не сбрасывается.
- Страницы `TabPage` получают новый `request`, перестраиваются и показывают новый текст.

Это и есть магия Flutter: **пересобирать дёшево, сбрасывать нечего**.

### 2.7 Фокус и клавиатура

- Фокус (`FocusNode`/`FocusScope`) определяет, какое поле сейчас принимает ввод. Пока у `TextField` фокус, показана клавиатура (на телефоне).
- `FocusScope.of(context).unfocus()` убирает фокус, клавиатура закрывается. Мы делаем это при нажатии кнопки геолокации: пользователь «закончил» работу с полем.
- `Scaffold(resizeToAvoidBottomInset: true)` (по умолчанию) **уменьшает `body`** на высоту клавиатуры. Нижняя панель при этом остаётся **под** клавиатурой (её не видно, пока клавиатура открыта). Это норма, но значит: страница может на время стать очень низкой (особенно в ландшафте), и содержимому надо уметь прокручиваться.

### 2.8 Адаптивность содержимого страницы

На странице вкладки (`TabPage`) не должно быть overflow ни при каких условиях. Источников переполнения три: низкий экран (ландшафт плюс клавиатура), крупный шрифт, длинный текст. Защита одна и та же:

```dart
Center(
  child: SingleChildScrollView(
    padding: const EdgeInsets.all(16),
    child: Column(mainAxisSize: MainAxisSize.min, children: [...]),
  ),
)
```

- `Center` даёт ребёнку **ослабленные** ограничения: он может быть любого размера до размеров родителя.
- `SingleChildScrollView` даёт колонке **неограниченную высоту** и, если колонка выше доступного, **прокручивается**.
- `Column(mainAxisSize: MainAxisSize.min)` занимает ровно столько высоты, сколько нужно, поэтому `Center` может поставить её по центру. (С `MainAxisSize.max` колонка в `SingleChildScrollView` вела бы себя неочевидно.)
- Длинный текст сам **переносится** по ширине (у `Text` по умолчанию `softWrap: true`), а по высоте работает прокрутка.

Поле поиска в `AppBar`: `Align(centerLeft)` + `ConstrainedBox(maxWidth: 560)`. На телефоне поле занимает всю доступную ширину; в широком окне Chrome (1600 px) не растягивается на всю панель.

### 2.9 Файлы, импорты, приватность

- **Один виджет (или группа тесно связанных) на файл**: `home_page.dart`, `search_app_bar.dart`, ... Так проще читать и тестировать.
- Внутри `lib/` импорты **относительные**: `import 'home_page.dart';`. Тесты (в `test/`) используют **пакетные**: `import 'package:weather_app/main.dart';`.
- Имена с подчёркиванием (`_HomePageState`) **приватны в пределах файла**. Состояние (`State`) всегда делаем приватным: снаружи на него незачем смотреть.
- `sealed` требует, чтобы наследники лежали **в одном файле**: поэтому `SearchRequest`, `TextSearch` и `GeolocationSearch` вместе в `search_request.dart`.

## 3. Декомпозиция и решения

Разбиваем на части: **(а)** модель «что искали», **(б)** хозяин состояния (`HomePage`), **(в)** читатели (`TabPage`), **(г)** писатель (`SearchAppBar`), **(д)** адаптивность и тесты. Слои из раздела 4 идут именно в таком порядке: от данных к интерфейсу.

### Решение 1: где живёт состояние

- **Варианты:** (а) в `HomePage` (`StatefulWidget`) + колбэк вверх + параметр вниз; (б) `InheritedWidget`; (в) `ValueNotifier` + `ValueListenableBuilder`; (г) пакет (Provider, Riverpod, BLoC).
- **Выбрано:** (а).
- **Почему:** общий родитель один (`HomePage`), глубина дерева маленькая, данных одно значение. Это самый простой вариант и он же «правильный» для такого размера. Для темы «Structure and Logic» он ещё и самый показательный.
- **Что теряем / риски:** когда в модулях 02-05 поверхностей (экранов) станет много, передавать параметры через несколько уровней станет утомительно. Тогда переходим на (б) или (в). Точка перехода понятна: меняется только способ доставки данных, а `SearchRequest` остаётся.

### Решение 2: как представить запрос: String или sealed-класс

- **Варианты:** (а) `String? _text` и для геолокации особая строка `'Geolocation'`; (б) `String` плюс `bool _isGeolocation`; (в) `sealed class SearchRequest` с двумя наследниками.
- **Выбрано:** (в).
- **Почему:** (а) путает пользовательский ввод и служебный маркер: пользователь может **сам напечатать** «Geolocation», и приложение не отличит его от кнопки. У (б) возможны **невозможные состояния** (`text = 'Paris'` и `isGeolocation = true` одновременно): их придётся постоянно «охранять». У (в) невозможных состояний нет по построению, и switch проверяется компилятором. В модуле 02 у геолокации появятся координаты (`GeolocationSearch(lat, lon)`), а у текста — результат геокодинга: данные у каждого варианта **свои**, и (в) принимает это без переделок.
- **Что теряем / риски:** три небольших класса вместо строки; новичку нужно знать синтаксис Dart 3 (`sealed`, образцы). Объяснено в [2.2](#22-sealed-class-и-switch-выражения-dart-3).

### Решение 3: когда обновлять вкладки: на каждый символ или по «Enter»

- **Варианты:** (а) `onChanged` (живой); (б) `onSubmitted` (по кнопке «ввод»); (в) оба.
- **Выбрано:** (а). Нажатие «ввод» просто закрывает клавиатуру.
- **Почему:** сабж говорит *«если вы вводите текст в поле поиска, приложение должно показать...»*, что ближе всего к «сразу». Живой вариант одновременно удовлетворяет и тому, кто смотрит экран, не нажимая «ввод» (проверяющий в Chrome), и тому, кто нажимает. Вариант (б) на проверке выглядел бы как «ничего не происходит».
- **Что теряем / риски:** на каждый символ перестраиваются страницы (дёшево). Когда в модуле 02 символ начнёт запускать **сетевой запрос**, понадобится задержка (debounce) или переход на (б).

### Решение 4: кто владеет TextEditingController

- **Варианты:** (а) `SearchAppBar` (`State` панели); (б) `HomePage` и передача контроллера вниз.
- **Выбрано:** (а).
- **Почему:** поле и контроллер — «внутренности» панели: `HomePage` знает только результат (`SearchRequest?`). Меньше связность: хозяину не нужно знать, что в панели есть поле.
- **Что теряем / риски:** `HomePage` не может программно очистить поле. Пока ему это не нужно: очистку при геолокации делает сама панель.

### Решение 5: что показывать, пока не искали

- **Варианты:** (а) только название вкладки; (б) название и заглушка вроде «Enter a location»; (в) название и пустую строку.
- **Выбрано:** (а).
- **Почему:** в ex00 страница показывала «только название вкладки», и ex01 говорит, что **в дополнение** к названию выводится текст или «Geolocation». Нет запроса, значит дополнять нечем.
- **Что теряем / риски:** разумное поведение для пустого состояния («введите город»), но пока вне сабжа: лишний текст на странице мог бы быть расценён как «добавлено лишнее».

### Решение 6: что считать «пустым» вводом

- **Выбрано:** текст обрезается по краям (`trim()`); пустая после обрезки строка = `null` (то есть «ничего не искали»).
- **Почему:** строка из одних пробелов осмысленного поиска не задаёт; `'  Paris '` и `'Paris'` один и тот же запрос.
- **Что теряем / риски:** пробелы внутри и по краям нельзя «показать»; пользователь этого не заметит.

### Решение 7: что делает кнопка геолокации с полем

- **Варианты:** (а) показать «Geolocation» и **оставить** текст в поле; (б) показать «Geolocation» и **очистить** поле.
- **Выбрано:** (б), плюс снимаем фокус (закрывается клавиатура).
- **Почему:** сабж «**либо** текст, **либо** геолокация». Если в поле остаётся «Paris», а на вкладках «Geolocation», экран **противоречит сам себе**, и непонятно, что сейчас активно. Очищая поле, мы делаем единственный источник правды: то, что на вкладках.
- **Что теряем / риски:** пользователь теряет введённый текст (минус небольшой); если проверяющий ожидает, что текст остаётся, — маловероятно, но об этом стоит помнить. Если понадобится (а), достаточно удалить строку `_controller.clear()`.

### Решение 8: как сделать верхнюю панель

- **Варианты:** (а) `StatefulWidget` + `implements PreferredSizeWidget`; (б) функция/метод, возвращающая `AppBar`; (в) готовый `PreferredSize` вокруг своего виджета; (г) всё поле прямо в `HomePage`.
- **Выбрано:** (а).
- **Почему:** контроллеру нужен `State` с `dispose` (а у функции его нет); `PreferredSize(preferredSize: ..., child: ...)` это ещё один уровень обёрток; в (г) `HomePage` разрастается и смешивает ответственность.
- **Что теряем / риски:** нужно помнить `implements PreferredSizeWidget` и `preferredSize`, иначе Scaffold не примет виджет (ошибка компиляции с понятным сообщением).

### Решение 9: разбиение на файлы

- **Выбрано:** шесть файлов: `main.dart`, `home_page.dart`, `search_app_bar.dart`, `tab_page.dart`, `weather_tab.dart`, `search_request.dart`.
- **Почему:** каждый файл отвечает на один вопрос («что искали», «какие вкладки», «как выглядит панель»). `main.dart` остаётся маленьким. Тесты импортируют только нужное.
- **Что теряем / риски:** на старте файлов больше, и по ним надо «прыгать». Для проекта, который растёт до модуля 05, это окупается сразу.

### Решение 10: надёжность страницы вкладки

- **Выбрано:** `Center` + `SingleChildScrollView` + `Column(mainAxisSize: min)` (2.8).
- **Почему:** не знаем заранее, какой высоты будет экран (ландшафт плюс клавиатура) и какой текст введёт пользователь.
- **Что теряем / риски:** лишний виджет-прокрутка в дереве; на странице может появиться ненужная прокрутка (только если содержимое реально не помещается).

#### Слой 1: модель «что искали»

Цель: завести тип данных и **проверить его без интерфейса**. Новый файл `lib/search_request.dart`:

```dart
sealed class SearchRequest {
  const SearchRequest();

  String get label => switch (this) {
    TextSearch(:final query) => query,
    GeolocationSearch() => 'Geolocation',
  };
}

final class TextSearch extends SearchRequest {
  const TextSearch(this.query);

  final String query;
}

final class GeolocationSearch extends SearchRequest {
  const GeolocationSearch();
}
```

**Разбор по строкам:**

- `sealed class SearchRequest`: закрытая иерархия (2.2). `const SearchRequest();` константный конструктор: наследники тоже `const`.
- `String get label => switch (this) {...}`: геттер `label` без параметров. Внутри `switch` по самому объекту (`this`). Первая ветка: «если я `TextSearch`, достань `query` и верни его». Вторая: «если я `GeolocationSearch`, верни слово `Geolocation`».
- Ветки перечислены полностью. Закомментируйте любую, и компилятор выдаст ошибку «The type 'SearchRequest' is not exhaustively matched» («тип не разобран полностью»): это и есть проверка полноты.
- `final class TextSearch extends SearchRequest`: наследник; поле `query` через `this.query` в конструкторе.

**Проверка без UI** (маленький тест; уже есть в `test/widget_test.dart`, группа «модель»):

```dart
expect(const TextSearch('Paris').label, 'Paris');
expect(const GeolocationSearch().label, 'Geolocation');
```

**Разбор:**

- `TabPage` — `StatelessWidget`: свои данные получает **только параметрами** (`tab`, `request`). Состояния у него нет и быть не должно.
- `required this.tab, required this.request`: именованные обязательные параметры. `request` обязателен, но может быть `null` (тип `SearchRequest?`): «передай значение, даже если это `null`». Это нарочно: забыть передать запрос нельзя.
- `final SearchRequest? request = this.request;`: локальная копия для понижения типа (2.3). Слева имя локальной переменной **затеняет** поле: это допустимо и распространено.
- `if (request != null) Text(...)`: **collection if** внутри списка детей. Если условие ложно, элемент просто не добавляется.
- `HomePage` теперь `StatefulWidget`: пара «виджет + `State`» (ex01 модуля 00, 2.2). Поле `_request` лежит в `State`.
- `TabPage(tab: tab, request: _request)`: данные идут **вниз** параметрами.
- Пока `_request` не меняется нигде: это spike.

Если это работает, дальше остаётся научить панель менять `_request`. **Помните:** после правки начального значения нужен **hot restart** (`R`), а не hot reload: `State` сохраняет старое значение поля.

#### Слой 3: верхняя панель сообщает запрос наверх

Цель: поле поиска реально меняет `_request`. Новый файл `lib/search_app_bar.dart` (версия слоя 3) и подключение в `HomePage`.

```dart
// lib/search_app_bar.dart (версия слоя 3)
import 'package:material_ui/material_ui.dart';

import 'search_request.dart';

class SearchAppBar extends StatelessWidget implements PreferredSizeWidget {

    return AppBar(
      title: TextField(
        onChanged: _handleTextChanged,
        decoration: const InputDecoration(
          hintText: 'Search location...',
          prefixIcon: Icon(Icons.search),
        ),
      ),
      actions: [
        IconButton(
          icon: const Icon(Icons.my_location),
          tooltip: 'Geolocation',
          onPressed: () {}, // слой 4
        ),
      ],

  }

```

Изменения в `HomePage` (`lib/home_page.dart`):

```dart
import 'search_app_bar.dart';          // новый импорт

class _HomePageState extends State<HomePage> {
  SearchRequest? _request;             // уже БЕЗ временного значения: null

  void _handleRequest(SearchRequest? request) {
    setState(() {
      _request = request;
    });
  }

  // в build:
  //   appBar: SearchAppBar(onRequest: _handleRequest),
  // (старый const AppBar(...) целиком удаляем)
```

**Разбор:**

- `ValueChanged<SearchRequest?>`: стандартный тип функции «принимает одно значение и ничего не возвращает» (`void Function(SearchRequest?)`). Нужен, чтобы **панель** могла сообщить наверх результат, не зная, кто хозяин. Панель только вызывает `onRequest(...)`, а что с этим делать, решает `HomePage`.
- `implements PreferredSizeWidget` и `preferredSize` (2.5).
- `_handleTextChanged(String text)`: `trim()` обрезает пробелы по краям; `isEmpty ? null : TextSearch(query)`: пустой ввод превращается в «ничего не искали».
- `onChanged: _handleTextChanged`: передаём **саму функцию**, без скобок (мы не вызываем её, а даём `TextField`, чтобы он вызывал при каждом изменении). Частая ошибка новичков: `onChanged: _handleTextChanged(...)`.
- `HomePage._handleRequest`: **единственное место**, где меняется `_request`; изменение обёрнуто в `setState`, иначе экран не обновится (ex01 модуля 00, 2.3).
- В слое 3 панель — `StatelessWidget`: пока ей **нечего помнить** (контроллера нет). Состояние добавим, когда оно потребуется.

**Что на экране:** набираем «Paris»: на каждой вкладке под названием появляется «Paris», буква за буквой. Стираем всё: надпись пропадает. **Проверка:** вкладки переключаются нажатием и свайпом, ввод не теряется.

#### Слой 4: кнопка геолокации

Цель: кнопка показывает «Geolocation» и очищает поле. Это тот момент, когда панели **нужно состояние** (контроллер поля), поэтому `SearchAppBar` становится `StatefulWidget`.

```dart
// lib/search_app_bar.dart (версия слоя 4)
import 'package:material_ui/material_ui.dart';

import 'search_request.dart';

class SearchAppBar extends StatefulWidget implements PreferredSizeWidget {
  const SearchAppBar({super.key, required this.onRequest});

  final ValueChanged<SearchRequest?> onRequest;

  @override
  Size get preferredSize => const Size.fromHeight(kToolbarHeight);

  @override
  State<SearchAppBar> createState() => _SearchAppBarState();
}

class _SearchAppBarState extends State<SearchAppBar> {
  final TextEditingController _controller = TextEditingController();

  @override
  void dispose() {
    _controller.dispose();
    super.dispose();
  }

  void _handleTextChanged(String text) {
    final String query = text.trim();
    widget.onRequest(query.isEmpty ? null : TextSearch(query));
  }

  void _handleGeolocation() {
    _controller.clear();
    FocusScope.of(context).unfocus();
    widget.onRequest(const GeolocationSearch());
  }

  @override
  Widget build(BuildContext context) {
    return AppBar(
      title: TextField(
        controller: _controller,
        onChanged: _handleTextChanged,
        decoration: const InputDecoration(
          hintText: 'Search location...',
          prefixIcon: Icon(Icons.search),
        ),
      ),
      actions: [
        IconButton(
          icon: const Icon(Icons.my_location),
          tooltip: 'Geolocation',
          onPressed: _handleGeolocation,
        ),
      ],
    );
  }
}
```

**Разбор изменений относительно слоя 3:**

- `StatelessWidget` → `StatefulWidget` + `State`: появилось, что хранить (`_controller`). Теперь `onRequest` доступен как `widget.onRequest`: из `State` к полям своего виджета обращаются через `widget.`.
- `final TextEditingController _controller = TextEditingController();` — создаётся один раз при создании `State`.
- `dispose`: освобождаем, `super.dispose()` последней.
- `controller: _controller` в `TextField`: подключаем «пульт».
- `_handleGeolocation`: три шага **в таком порядке**: **1)** `_controller.clear()` очищает поле (без вызова `onChanged`!); **2)** `FocusScope.of(context).unfocus()` убирает фокус, закрывается клавиатура; **3)** `widget.onRequest(const GeolocationSearch())` сообщает наверх «искали по геолокации». Шаг 3 мы вызываем **сами**, потому что программная очистка `onChanged` не вызвала бы (2.4). Иначе страницы остались бы со старым «Paris», хотя поле пустое.
- `onPressed: _handleGeolocation`: снова без скобок.

**Что на экране:** набираем «Paris»: везде «Paris». Нажимаем прицел: поле пустеет, везде «Geolocation». Печатаем «Rome»: «Geolocation» заменено на «Rome». **Проверка:** попробуйте цепочку «ввод → геолокация → ввод → стереть → геолокация».

#### Слой 5: устойчивость и аккуратность

Цель: убрать последние источники overflow и довести внешний вид. Два места.

**1. `TabPage`** становится устойчивой к малой высоте (2.8): `Center` + `SingleChildScrollView` + паддинг:

```dart
return Center(
  child: SingleChildScrollView(
    padding: const EdgeInsets.all(16),
    child: Column(
      mainAxisSize: MainAxisSize.min,
      children: [
        Text(tab.title, style: textTheme.headlineMedium, textAlign: TextAlign.center),
        if (request != null) ...[
          const SizedBox(height: 8),
          Text(request.label, style: textTheme.titleLarge, textAlign: TextAlign.center),
        ],
      ],
    ),
  ),
);
```

- `if (request != null) ...[ a, b ]`: collection-if со **spread** (`...`): добавляет сразу **несколько** элементов: отступ и текст.
- `textAlign: TextAlign.center`: длинная строка, перенесённая на несколько строк, выравнивается по центру, а не по левому краю.

**2. `SearchAppBar`:** поле не растягивается на всю панель в широком окне, добавлены скругление и заливка, клавиша «поиск»:

```dart
title: Align(
  alignment: Alignment.centerLeft,
  child: ConstrainedBox(
    constraints: const BoxConstraints(maxWidth: _maxFieldWidth),
    child: TextField(
      controller: _controller,
      onChanged: _handleTextChanged,
      textInputAction: TextInputAction.search,
      decoration: InputDecoration(
        hintText: 'Search location...',
        prefixIcon: const Icon(Icons.search),
        filled: true,
        isDense: true,
        border: OutlineInputBorder(
          borderRadius: BorderRadius.circular(28),
          borderSide: BorderSide.none,
        ),
      ),
    ),
  ),
),
```

- `Align(centerLeft)`: `AppBar` на разных платформах по-разному выравнивает заголовок (на iOS и macOS по центру, на Android и в Chrome под Linux/Windows слева). `Align` занимает всю ширину отведённого под заголовок места и прижимает поле **влево** одинаково везде.
- `ConstrainedBox(maxWidth: 560)`: «не шире 560 dp»; на телефоне (360) поле использует всю ширину.
- `filled: true` + `border: ...borderSide: BorderSide.none`: заливка цветом темы без обводки, скруглённые края (радиус 28).
- `isDense: true`: компактная высота поля, чтобы оно уместилось в 56 dp панели.
- `InputDecoration` больше не `const` (в нём вычисляемый `BorderRadius.circular`).

```dart
import 'package:material_ui/material_ui.dart';

import 'search_request.dart';

// Верхняя панель: поле поиска + кнопка геолокации.
//
// Почему StatefulWidget: у поля есть TextEditingController, а контроллер надо
// создать один раз, а в конце освободить (dispose). Это работа State.
//
// Почему implements PreferredSizeWidget: Scaffold.appBar принимает только
// виджеты, которые заранее умеют сказать свою высоту (preferredSize), чтобы
// Scaffold знал, сколько места отдать телу страницы.
class SearchAppBar extends StatefulWidget implements PreferredSizeWidget {
  const SearchAppBar({super.key, required this.onRequest});

  // Панель сама ничего не показывает, она только сообщает наверх, что искали.
  // null = поле очистили, искать нечего.
  final ValueChanged<SearchRequest?> onRequest;

  @override
  Size get preferredSize => const Size.fromHeight(kToolbarHeight);

  @override
  State<SearchAppBar> createState() => _SearchAppBarState();
}

class _SearchAppBarState extends State<SearchAppBar> {
  // Поле на широких экранах не растягиваем до безобразия.
  static const double _maxFieldWidth = 560;

  final TextEditingController _controller = TextEditingController();

  @override
  void dispose() {
    _controller.dispose();
    super.dispose(); // super.dispose() всегда последним
  }

  // Срабатывает на каждый введённый или стёртый символ.
  void _handleTextChanged(String text) {
    final String query = text.trim();
    widget.onRequest(query.isEmpty ? null : TextSearch(query));
  }

  void _handleGeolocation() {
    // Очищаем поле, чтобы то, что в поле, и то, что на вкладках, не расходились.
    // Программная очистка onChanged НЕ вызывает, поэтому дальше сообщаем сами.
    _controller.clear();
    // Убираем фокус: на телефоне клавиатура закрывается.
    FocusScope.of(context).unfocus();
    widget.onRequest(const GeolocationSearch());
  }

  @override
  Widget build(BuildContext context) {
    return AppBar(
      title: Align(
        alignment: Alignment.centerLeft,
        child: ConstrainedBox(
          constraints: const BoxConstraints(maxWidth: _maxFieldWidth),
          child: TextField(
            controller: _controller,
            onChanged: _handleTextChanged,
            textInputAction: TextInputAction.search,
            decoration: InputDecoration(
              hintText: 'Search location...',
              prefixIcon: const Icon(Icons.search),
              filled: true,
              isDense: true,
              border: OutlineInputBorder(
                borderRadius: BorderRadius.circular(28),
                borderSide: BorderSide.none,
              ),
            ),
          ),
        ),
      ),
      actions: [
        IconButton(
          icon: const Icon(Icons.my_location),
          tooltip: 'Geolocation',
          onPressed: _handleGeolocation,
        ),
      ],
    );
  }
}
```

### 4.4 Симуляция: ввод «Pa», геолокация, ввод «Rome»

Начальное состояние: `_request = null`; поле пустое; вкладка Currently.

| № | Действие | Что происходит | `_request` | Экран (текущая вкладка) |
|---|---|---|---|---|
| 0 | запуск | `build`: `TabPage(request: null)` | `null` | «Currently» |
| 1 | вводим «P» | `onChanged('P')` → `trim` → `'P'` → `onRequest(TextSearch('P'))` → `setState` | `TextSearch('P')` | «Currently» / «P» |
| 2 | вводим «a» | `onChanged('Pa')` → `TextSearch('Pa')` | `TextSearch('Pa')` | «Currently» / «Pa» |
| 3 | свайп на Today | `TabController` меняет индекс; `HomePage` не перестраивается | то же | «Today» / «Pa» |
| 4 | кнопка геолокации | `clear()` (без `onChanged`), `unfocus()`, `onRequest(GeolocationSearch())` | `GeolocationSearch()` | «Today» / «Geolocation», поле пусто |
| 5 | вводим «R» | `onChanged('R')` → `TextSearch('R')` | `TextSearch('R')` | «Today» / «R» |
| 6 | дописываем «ome» | три вызова `onChanged` | `TextSearch('Rome')` | «Today» / «Rome» |
| 7 | стираем всё | `onChanged('')` → `trim` → пусто → `onRequest(null)` | `null` | «Today» |
| 8 | вводим «   » (3 пробела) | `trim()` даёт `''` → `onRequest(null)` | `null` | «Today» |

Обратите внимание на шаг 3: смена вкладки **не меняет** `_request` и не перестраивает `HomePage`: между `TabBar` и `TabBarView` работает только `TabController`. Данные «поиск» и данные «вкладка» живут независимо.

### 4.5 Симуляция: что перестраивается на один символ

Ввод «P» (шаг 1):

1. `setState` помечает `_HomePageState` «грязным».
2. Flutter вызывает `HomePage.build`: создаётся **новое** дерево описаний: `DefaultTabController`, `Scaffold`, **новый** `SearchAppBar`, `TabBarView`, три **новых** `TabPage`.
3. Сравнение с прежним деревом по типу и позиции. `SearchAppBar` на том же месте ⇒ **его `State` остаётся**, `_controller` и введённый текст живы. `DefaultTabController` тот же ⇒ выбранная вкладка не сбрасывается.
4. `TabPage` получили другой `request` ⇒ их `build` вызывается снова, на экране новый `Text`.

Сколько работы: одна пересборка дерева из нескольких десятков элементов на каждый символ. Это в сотни раз меньше бюджета кадра, поэтому оптимизировать здесь нечего.

```dart
      await tester.pumpWidget(const WeatherApp());

      await tester.enterText(find.byType(TextField), '  Paris  ');
      await tester.pump();
      expect(pageText('Paris'), findsOneWidget);
    });
  });

  group('адаптивность: ни одного overflow', () {
    const Map<String, Size> sizes = {
      'узкий телефон': Size(320, 480),
      'телефон': Size(390, 844),
      'телефон в ландшафте': Size(844, 390),
      'низкий ландшафт': Size(640, 280),
      'планшет': Size(1024, 768),
      'широкий веб': Size(1600, 900),
    };

    sizes.forEach((String name, Size size) {
      testWidgets(name, (tester) async {
        tester.view.physicalSize = size;
        tester.view.devicePixelRatio = 1.0;
        addTearDown(tester.view.reset);

        await tester.pumpWidget(const WeatherApp());
        await tester.enterText(find.byType(TextField), 'Saint-Petersburg');
        await tester.pump();

        expect(tester.takeException(), isNull);
        expect(pageText('Saint-Petersburg'), findsOneWidget);
      });
    });

    testWidgets('крупный шрифт и очень длинный текст', (tester) async {
      tester.view.physicalSize = const Size(360, 640);
      tester.view.devicePixelRatio = 1.0;
      tester.platformDispatcher.textScaleFactorTestValue = 2.0;
      addTearDown(tester.view.reset);
      addTearDown(tester.platformDispatcher.clearAllTestValues);

      await tester.pumpWidget(const WeatherApp());
      await tester.enterText(find.byType(TextField), 'Very long name ' * 20);
      await tester.pump();

      expect(tester.takeException(), isNull);
    });
  });
}
```

Что проверяют группы, относящиеся к ex01:

- **«ввод виден на всех вкладках»:** вводим «Paris» и обходим все три вкладки; на каждой есть и название, и «Paris».
- **«кнопка геолокации»:** тап по иконке `Icons.my_location`; на странице «Geolocation»; на другой вкладке тоже.
- **«геолокация очищает поле»:** проверяем `controller.text` пустым и то, что «Paris» с экрана исчезло, а следующий ввод заменяет «Geolocation».
- **«пустое и пробельное поле»:** `'   '` возвращает чистые вкладки.
- **«обрезка»:** `'  Paris  '` показывается как «Paris».
- **«адаптивность»:** шесть размеров экрана и крупный шрифт с очень длинным текстом: `takeException()` пуст.

Что **не** проверяют: поведение настоящей клавиатуры и фокуса (в тестах нет экранной клавиатуры), визуальный вид (для этого есть глаза и скриншоты).

## 5. Альтернативы

| Подход | Суть | Плюсы | Минусы | Когда подойдёт |
|---|---|---|---|---|
| **State в HomePage + колбэк** (выбрано) | `setState` + параметр вниз + колбэк вверх | минимум кода, всё на виду | при глубоком дереве параметры тянутся через много уровней | маленькие и средние экраны |
| `ValueNotifier<SearchRequest?>` + `ValueListenableBuilder` | «наблюдаемое» значение; слушатели перестраиваются сами | перестраиваются только читатели, а не весь `HomePage` | ещё одна сущность, `dispose` | когда пересборка `HomePage` дорогая |
| `InheritedWidget` / `InheritedNotifier` | данные доступны любому потомку | не надо протаскивать параметры | заметно больше шаблонного кода | много читателей на разной глубине |
| Provider / Riverpod / BLoC | пакеты управления состоянием | масштабируются, тестируются | зависимость, обучение, вне сабжа | большие приложения (модули 04-05, возможно) |
| `onSubmitted` вместо `onChanged` | искать только по «ввод» | меньше перестроений, не мигает при наборе | выглядит как «ничего не происходит» | когда символ запускает сетевой запрос |
| Debounce | реагировать через ~400 мс после последнего символа | экономит запросы | нужен `Timer`, `dispose` | модуль 02 (запросы в сеть) |
| `SearchBar` / `SearchAnchor` (Material 3) | готовый виджет поиска с подсказками | подсказки из коробки | своя логика, другой внешний вид; лишнее для этого сабжа | когда нужны подсказки |
| `String` + флаг вместо `sealed` | просто и знакомо | меньше классов | невозможные состояния; путаница ввода и маркера | совсем маленький прототип |
| Очищать поле при геолокации или оставлять | см. решение 7 | | | зависит от продукта |

**О «Provider и компании».** Они не плохи, и вы с ними ещё встретитесь, но для **одного значения в одном родителе** пакет — это пушка по воробьям. Урок модуля — понять, **что** такое состояние и **кто** им владеет. Пакеты автоматизируют ровно то, что вы сделали руками.

## 7. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| `The argument type 'SearchAppBar' can't be assigned to the parameter type 'PreferredSizeWidget?'` | Забыли `implements PreferredSizeWidget` (или `preferredSize`) | Добавить `implements PreferredSizeWidget` и `Size get preferredSize => ...` |
| `The type 'SearchRequest' is not exhaustively matched` | В `switch` по `sealed`-типу не хватает ветки | Добавить недостающий случай |
| Страницы не обновляются при вводе | Изменили `_request` **без** `setState` | Менять внутри `setState(() { ... })` |
| Надпись «Paris» на страницах остаётся, а поле уже пустое после кнопки | После `clear()` не позвали `onRequest` (программная очистка `onChanged` не вызывает) | Вызвать `widget.onRequest(const GeolocationSearch())` |
| Ввод стирается сам при каждом символе | `TextEditingController` создаётся в `build` (а не в `State`) или `SearchAppBar` пересоздаётся с другим типом/ключом | Контроллер только полем `State`; не менять тип и позицию виджета |
| Ошибка про использование `context` после `await` | (пока не про нас) | В `_handleGeolocation` нет `await`; появится в модуле 02, тогда проверять `mounted` |
| Изменил начальное значение `_request`, а на экране старое | Hot reload не обновляет уже созданное `State` | Hot restart (`R` в консоли `flutter run`) |
| `onChanged` не вызывается после `clear()` | Так и задумано | Звать колбэк вручную (решение 7) |
| Поле поиска растянулось на всю ширину в Chrome | Нет `ConstrainedBox(maxWidth: ...)` вокруг `TextField` (поле жадное по ширине) | `Align(centerLeft)` + `ConstrainedBox(maxWidth: 560)` (слой 5) |
| Overflow на странице при открытой клавиатуре | Нет `SingleChildScrollView` в `TabPage` | Слой 5 |
| `undefined_identifier: Icons.my_location` | Нет импорта `material_ui` в файле | Добавить `import 'package:material_ui/material_ui.dart';` |
| Тест не находит `'Paris'` | `find.text('Paris')` ищет по всему дереву, в нём может быть и само поле | Искать внутри страниц: `pageText('Paris')` |
| `The following assertion was thrown... A TextEditingController was used after being disposed` | `dispose` вызван, а виджет ещё использует контроллер | Освобождать только в `dispose` `State`; не хранить контроллер вне `State` |

## 8. Безопасность и риски

- **Пользовательский ввод:** строка выводится `Text`-ом как **данные**, не как разметка и не как код; внедрить через неё ничего нельзя. Переполнение исключено: `Text` переносится, страница прокручивается.
- **Приватность:** сейчас ввод никуда не отправляется и нигде не сохраняется. Когда в модуле 02 запрос уйдёт в сеть (геокодинг), нельзя писать введённое в `debugPrint` и в логи.
- **Геолокация:** в ex01 это просто слово «Geolocation». Настоящая геолокация (модуль 02) потребует разрешений и согласия пользователя; координаты нельзя запрашивать без разрешения пользователя.
- **Зависимости:** новых нет.
- **Риск «непроверенного кода»:** см. пометку в начале. До сдачи прогнать `flutter analyze` и `flutter test` самому.
- **Риск понимания:** ответ на вопрос проверяющего «почему состояние в `HomePage`?» должен быть вашим словами: общий родитель; данные вниз, события вверх.

## 10. Что запомнить

**Dart:**

- `sealed class` + `final class`: закрытая иерархия, а `switch` по ней обязан быть **исчерпывающим**: компилятор следит.
- `switch`-выражение: `switch (x) { Образец => значение, ... }`; образец объекта `TextSearch(:final query)`.
- Nullable `T?` и понижение типа: для локальных переменных работает `if (x != null)`, для полей нужна локальная копия.
- Collection `if` и `...[ ]` (spread) внутри списка виджетов.
- Функцию передают **без скобок**: `onChanged: _handle`, а не `_handle()`.

**Flutter:**

- **Данные вниз параметрами, события вверх колбэками; состояние живёт в ближайшем общем родителе.**
- `StatefulWidget` вводим, **когда появляется, что хранить** (слой 3 `StatelessWidget`, слой 4 `StatefulWidget`).
- Новый виджет того же типа на том же месте **сохраняет `State`**: пересборка на каждый символ дешёвая и ничего не сбрасывает.
- `TextEditingController`: создаём в `State`, освобождаем в `dispose`; `clear()` и `text =` **не вызывают** `onChanged`.
- `Scaffold.appBar` принимает только `PreferredSizeWidget`; `kToolbarHeight` = 56.
- `FocusScope.of(context).unfocus()` закрывает клавиатуру.
- Страница, которая должна переживать любой экран: `Center` + `SingleChildScrollView` + `Column(mainAxisSize: min)`.
- Hot reload не меняет уже созданное `State`: поменяли начальное значение поля, делайте hot restart.

**Логика и реализация:**

- Данные модели (`SearchRequest`, `WeatherTab`) ничего не знают про интерфейс; интерфейс зависит от модели, а не наоборот.
- «Либо то, либо другое» моделируется типом (**sealed**), а не парой «строка + флаг»: невозможные состояния невозможны по построению.
- Единый источник правды: то, что в поле, и то, что на вкладках, не должны противоречить друг другу (поэтому кнопка очищает поле).
- Рефакторинг отдельно от новой функциональности: слой 0 ничего не меняет в поведении.
- Слоями: данные → хозяин → читатели → писатель → устойчивость; на каждом шаге можно запустить и проверить.
