# Модуль 02, ex01: Searcher

> Второе упражнение третьего модуля: поиск города **по-настоящему**. Пока пользователь печатает, под строкой поиска появляется **список подсказок** («город, регион, страна») из геокодера Open-Meteo. Выбор подсказки загружает погоду; поиск без выбора (клавиша «Поиск» на клавиатуре) тоже работает. Главные новые темы: **HTTP и JSON из Dart**, **геокодинг**, **debounce** (пауза после набора), **гонки запросов**, **`Stack`** для выпадающего списка и **поднятие состояния** текстового поля.

> **Честная пометка о проверке.** Как и в [ex00](02-ex00.md), код и тесты написаны **без запуска** (нет Flutter SDK, нет доступа к pub.dev и к самим API). Формат ответов Open-Meteo и BigDataCloud взят из **их документации** (раздел «Источники»), но сверить его с живым ответом можно только вам: команда `curl` в слое 1 для этого и придумана. Если реальный ответ отличается от разобранного здесь, **прав сервер, а не документация и не я**: пришлите ответ, и поправим парсер и тест.

## 1. Задача и с чего начать

### 1.1 Условия сабжа

- **Папка сдачи:** `mobileModule02`, проект `medium_weather_app` (тот же, что в ex00)
- **Запрещённые функции:** нет
- **Требования сабжа:**
  - при вводе названия города под строкой поиска появляется **динамический список подсказок** в виде «город, регион, страна»;
  - пока ничего не введено, подсказок нет;
  - при выборе подсказки приложение получает погоду для **этого** места;
  - поиск **без выбора** подсказки (пользователь просто нажал «поиск») тоже должен работать;
  - используется **геокодинг-API Open-Meteo**;
  - когда место определено по GPS, его **название** (город, регион, страна) тоже показывается: для этого нужен геокодинг **по координатам**.

### 1.2 Проблема

Есть три пути к погоде, и все они должны привести к одному и тому же: «известно **место** (название и координаты) → просим прогноз».

1. **GPS** (ex00): известны координаты, названия нет. Нужен «обратный геокодинг» «координаты → город».
2. **Выбор подсказки**: пользователь выбрал строку из списка: место (с координатами) уже известно.
3. **Ввод и «поиск»** без выбора: известен только текст. Нужен «прямой геокодинг» «название → место», берём лучшее совпадение.

### 1.3 Требования

**Функциональные:**

- Подсказки появляются **во время набора**, не раньше 2 символов, и пропадают, когда текст стёрт, когда город выбран, когда нажат «поиск» или геолокация.
- Каждая подсказка: **название** и под ним **«регион, страна»**.
- Выбор подсказки вписывает название в поле и загружает погоду; список закрывается.
- «Поиск» на клавиатуре: берём первый найденный город.
- Пустой запрос игнорируется (экран остаётся как был).

**Нефункциональные:**

- Не устраивать **шквал запросов**: каждая буква не должна быть запросом (лимиты API, батарея, трафик).
- **Старый ответ не затирает новый** (гонка запросов).
- Сбой подсказок не должен выглядеть как авария: это удобство, а не функция.
- Не падать на странных ответах сервера и не показывать кракозябры вместо «Île-de-France».

### 1.4 Что не входит в задачу (non-goals)

- Сама погода (ex02), ошибки «города нет» и «нет сети» (ex03; но заготовки уже в коде).
- История поиска, «избранные города».
- Клавиатурная навигация по списку подсказок, `SearchAnchor`/`Autocomplete` (см. альтернативы).
- Распознавание «не тот Paris»: показываем регион и страну, выбор за пользователем.

### 1.5 Критерии успеха

- [ ] Набираем «Par»: через долю секунды список из нескольких «Paris, Île-de-France, France» и т. п.
- [ ] Быстро печатаем «Paris»: в сеть уходит **один** запрос, а не пять.
- [ ] Тап по подсказке: в поле «Paris», список скрыт, на вкладках погода этого Paris.
- [ ] «Enter» без выбора: погода для первого найденного.
- [ ] Стёрли текст: список исчез.
- [ ] Прицел (геолокация) очищает поле и закрывает список.
- [ ] Тесты геокодеров и контроллера зелёные.

### 1.6 Первый шаг (spike)

Прежде чем писать Dart, **посмотрите на ответ сервера глазами**. Это слой 1: одна команда в терминале.

```bash
curl -s 'https://geocoding-api.open-meteo.com/v1/search?name=Paris&count=2&language=en&format=json'
```

Вы увидите (сокращено) что-то вроде:

```json
{"results":[
  {"id":2988507,"name":"Paris","latitude":48.85341,"longitude":2.3488,
   "country":"France","country_code":"FR","admin1":"Île-de-France", ...},
  {"id":4717560,"name":"Paris","latitude":33.66094,"longitude":-95.55551,
   "country":"United States","admin1":"Texas", ...}
],"generationtime_ms":0.5}
```

Попробуйте ещё два запроса и запомните, как выглядит ответ:

```bash
curl -s 'https://geocoding-api.open-meteo.com/v1/search?name=Atlantisxyz&count=2'   # ничего не нашлось
curl -s 'https://geocoding-api.open-meteo.com/v1/search?name=Sao%20Paulo&count=1'   # пробел в имени: %20
```

Что мы выяснили дёшево: (1) какие поля есть (`name`, `latitude`, `longitude`, `country`, `admin1`), (2) что **нет совпадений** выглядит иначе, чем «пустой список»: ключа `results` просто нет (документация: *«Empty fields are not returned»*), (3) что пробел кодируется. Именно на этом построен парсер.

## 2. Теория

### 2.1 Геокодинг: прямой и обратный

- **Прямой** («forward»): *«Paris»* → место с координатами. Это то, что умеет Geocoding API Open-Meteo.
- **Обратный** («reverse»): *(41.39, 2.17)* → *«Barcelona, Catalonia, Spain»*. У Open-Meteo такого запроса **нет**.

Поэтому для названия места при GPS нужен **второй сервис**. Мы выбрали BigDataCloud (решение 3), а запасной вариант Nominatim (раздел 5).

Как Open-Meteo ищет: параметр `name`: *«Empty and single-character searches return no results»*, **два символа** дают совпадение только с **точным** названием, **три и больше** дают **поиск по началу названия** (*«normalized prefix matching»*, без учёта регистра и диакритики). Практический вывод: подсказки «Par» работают как «всё, что начинается с par», а «Pa» найдёт только место, которое называется ровно «Pa». Мы запрашиваем с 2 символов (редкие короткие названия вроде «Ur», «Ho Chi...» не должны теряться), но большинство подсказок живёт с третьей буквы.

### 2.2 HTTP GET и JSON из Dart

Пакет `http`:

```dart
final http.Client client = http.Client();
final http.Response response = await client.get(uri);   // Future: ждём ответ
response.statusCode;     // 200 = успех
response.bodyBytes;      // тело как байты
```

Ключевые вещи:

- **`Uri.https(host, path, queryParameters)`** собирает адрес и **сам кодирует** параметры: «São Paulo, Brazil» превратится в `S%C3%A3o%20Paulo%2C%20Brazil`. Склеивать строки руками (`'...?name=$query'`) нельзя: пробел, `&` или `#` в названии сломают запрос (и это ещё и дыра в безопасности, если текст не ваш).
- **Код ответа**: `200` успех; `400` «ваши параметры плохие»; `5xx` «сервер сломался»; `402`/`429` «вас ограничили». Все не-200 мы считаем ошибкой сервера.
- **Кодировка.** `response.body` (строка) угадывает кодировку по заголовку `Content-Type`; без `charset=utf-8` пакет `http` считает тело **Latin-1**, и «Île-de-France» превращается в «Ã\u008ele-de-France». Мы берём **байты** и декодируем `utf8.decode(response.bodyBytes)` сами. Тест `Île-de-France` это проверяет.
- **JSON**: `jsonDecode(text)` возвращает `dynamic`: `Map<String, dynamic>`, `List`, `String`, `num`, `bool` или `null`. Типы **не гарантированы**: сервер мог прислать что угодно. Отсюда `as`-приведения в одном месте (`parseResponse`), которые при ошибке превращаются в `ServerFailure`.
- **`num`**: JSON-число `33` приходит в Dart как `int`, а `33.5` как `double`. Если написать `json['latitude'] as double`, то на `33` будет `TypeError`. Правильно: `(json['latitude'] as num).toDouble()`. Тест с целыми координатами («нет admin1, а координаты целые числа») существует именно из-за этой ловушки.
- **Таймаут**: `client.get(uri).timeout(Duration(seconds: 10))`. Без него зависший сервер = вечный индикатор.

### 2.3 Какие исключения бывают на «проводе»

| Что случилось | Что бросает `http` | Что делаем |
|---|---|---|
| Нет интернета | `ClientException` (на dart:io внутри `SocketException`; на web `ClientException`) | `ConnectionFailure` |
| DNS не нашёл хост, обрыв, TLS | то же | `ConnectionFailure` |
| Не дождались | `TimeoutException` | `ConnectionFailure` |
| Ответ пришёл, но код не 200 | исключения нет | `ServerFailure(statusCode)` |
| Тело не JSON | `FormatException` | `ServerFailure` |
| JSON не той формы | `TypeError`, `RangeError`: это **`Error`**, не `Exception` | `ServerFailure` через `on Object` |

Обратите внимание на последнюю строку: `catch (e)` без `on` и `on Object` ловят и `Error`, а `on Exception` их **не** ловит. Поэтому на сети мы ловим `on Exception` (сеть бросает исключения), а при **разборе чужих данных** ловим `on Object` (там бывают ошибки типов).

### 2.4 Debounce

Пользователь печатает «Paris»: событий пять (P, Pa, Par, Pari, Paris). Идти за подсказками на каждое: 5 запросов, из них 4 никому не нужны: ответы на «P»/«Pa» устареют, пока летят. У Open-Meteo бесплатный лимит на 600 запросов в минуту, 5000 в час, 10 000 в сутки; активный пользователь без debounce выбьет его за считанные минуты.

**Debounce** («гашение дребезга»): при каждом нажатии **сбрасываем таймер** и запускаем новый на 300 мс. Запрос уходит только если пользователь **замолчал** на 300 мс.

```text
время (мс)   0    80   160   240        540
ввод         P    a    r     i  ...тишина...
таймер       ▶    ✖▶   ✖▶    ✖▶ ──────── сработал: запрос «Pari»
```

В коде это `Timer`:

```dart
_debounceTimer?.cancel();                                  // сбросить прежний
_debounceTimer = Timer(suggestDebounce, () => load(query)); // запустить новый
```

**Debounce и throttle** — разные вещи: debounce ждёт **тишины**, throttle пропускает не чаще раза в N мс. Для поиска нужен debounce.

### 2.5 Гонка запросов (race condition)

Debounce не спасает от такого: запрос «Par» ушёл, пользователь допечатал «Paris», ушёл второй, а первый **ответил позже** (сервер/сеть капризные). Если применять ответы по мере прихода, на экране окажется список для «Par», хотя в поле «Paris».

Лекарство: **номерки** (в коде `_suggestId`, `_requestId`). Каждый новый запрос берёт следующий номер; когда ответ пришёл, сверяем: «я ещё последний?» Если нет, ответ **выбрасываем**.

```dart
final int id = ++_suggestId;          // мой номерок
final found = await _geocoding.search(...);
if (id != _suggestId) return;         // пока ждали, появился новее: устарело
```

Альтернатива: **отмена** запроса (`CancelableOperation` из `async`, токены отмены). Пакет `http` отмену сам не умеет (в версиях 1.x есть `AbortableRequest`, но тогда придётся отказаться от простого `client.get`). Номерки проще и достаточны: лишний ответ придёт, но мы его проигнорируем.

### 2.6 Stack, Align и выпадающий список

Подсказки должны лежать **поверх** вкладок, а не сдвигать их. Виджет, который кладёт детей слоями друг на друга, это `Stack`:

```dart
Stack(children: [
  TabBarView(...),                    // нижний слой: страницы
  if (suggestions.isNotEmpty)         // верхний слой: только когда есть что показать
    SuggestionsList(...),
])
```

Внутри `SuggestionsList`:

- `Align(alignment: topCenter)`: прижать список к верху и центру. **Важное свойство:** пустое место вокруг списка *не перехватывает нажатия*, они проваливаются в нижний слой (страницы вкладок остаются живыми).
- `ConstrainedBox(maxWidth: 600, maxHeight: 320)`: не шире 600 px (на планшете и в вебе) и не выше 320 px.
- `Material(elevation: 4)`: даёт фон и тень (без `Material` у `ListTile` не будет ни «подсветки нажатия», ни фона; будет красная ошибка «No Material widget found»).
- `ListView.builder(shrinkWrap: true)`: список по запросу; `shrinkWrap` сжимает его до высоты содержимого (иначе он займёт всю доступную высоту).

### 2.7 Поднятие состояния ещё раз

В модуле 01 (ex01) контроллер текстового поля жил внутри `SearchAppBar`: сама панель хозяйничала своим полем (решение 4). Теперь поле должно меняться **снаружи** (выбор подсказки вписывает город), поэтому `TextEditingController` снова **поднят** в `HomePage`, а `SearchAppBar` опять `StatelessWidget`, всё получает параметрами. Это не откат, а тот же принцип: **состояние живёт у ближайшего общего предка всех, кому оно нужно**. В модуле 01 нужным местом было «внутри панели»; теперь изменился набор участников.

Важный нюанс: `controller.text = '...'` из кода **не вызывает** `onChanged` у `TextField` (он срабатывает только на ввод пользователя). Поэтому выбор подсказки не запустит новый поиск подсказок для вписанного названия: это нужное нам поведение, и тест на него есть.

## 3. Декомпозиция и решения

Части: **(а)** модели `Place`; **(б)** общий слой HTTP (`getJson`); **(в)** `GeocodingService`; **(г)** `ReverseGeocodingService`; **(д)** действия контроллера (`search`, `select`, `queryChanged`); **(е)** экран подсказок; **(ж)** тесты.

### Решение 1: HTTP-клиент

- **Варианты:** (а) `dart:io` `HttpClient` напрямую; (б) пакет `http`; (в) пакет `dio`; (г) `chopper`/`retrofit` (генерация клиента).
- **Выбрано:** (б).
- **Почему:** `dart:io` не работает на web (а мы собираем и под Chrome). `dio` богаче (перехватчики, отмена, повторы), но это лишний пакет ради двух-трёх GET-запросов. `http` маленький, официальный (dart.dev), работает везде и имеет **`MockClient` для тестов без сети**.
- **Что теряем / риски:** повторы, отмена и логирование «из коробки» пишем сами (повтор есть в ex03; отмену заменяют номерки).

### Решение 2: прямой геокодинг

- **Выбрано:** Geocoding API Open-Meteo: `GET https://geocoding-api.open-meteo.com/v1/search?name=...&count=...&language=en&format=json`.
- **Почему:** этого требует сабж; без ключа, с лимитами, достаточными для учебного проекта; тот же поставщик, что и у погоды.
- **Что теряем / риски:** бесплатный API **для некоммерческого использования**, без гарантий доступности, с обязательным указанием источника данных (CC BY 4.0); в настоящем продукте нужен платный план или свой сервер.

### Решение 3: обратный геокодинг (координаты → название)

- **Варианты:** (а) **BigDataCloud** `reverse-geocode-client`; (б) **Nominatim** (OpenStreetMap); (в) пакет `geocoding` (платформенный геокодер Android/iOS); (г) показывать только координаты.
- **Выбрано:** (а).
- **Почему:** (а) без ключа, возвращает именно `city`/`locality`/`principalSubdivision`/`countryName`, а условия «client-side» бесплатного эндпоинта (вызывать с устройства пользователя для **его** текущего места) это наш случай слово в слово. (б) Nominatim годится, но политика OSM требует **собственный `User-Agent`**, лимит 1 запрос в секунду и **запрещает автодополнение на клиенте** (нам для обратного запроса это не мешает, но условия строже и нужно «подписаться» своим приложением). (в) `geocoding` использует системные геокодеры: нужен Google Play Services / может не работать на эмуляторе и на web. (г) нарушает сабж («название места»).
- **Что теряем / риски:** третья сторона получает **координаты пользователя**; нет гарантий SLA (при злоупотреблении ответ `402` и блокировка по IP). Поэтому при сбое обратного геокодера (`ServerFailure`) мы **не падаем**: контроллер подставляет `Place.atCoordinates` (название = сами координаты), и погода всё равно загружается. Сменить поставщика можно, написав **другую реализацию** `ReverseGeocodingService`: больше ничего менять не надо.

### Решение 4: что значит «поиск без выбора»

- **Варианты:** (а) взять **первый** результат геокодера; (б) показать подсказки и **заставить выбрать**; (в) искать и по тексту, и по подсказкам одновременно.
- **Выбрано:** (а): `search(text)` просит у геокодера `count: 1`.
- **Почему:** сабж явно требует, чтобы это работало; Open-Meteo сортирует по релевантности (в том числе по населению), так что «Paris» даёт французский Paris, а не Paris в Техасе.
- **Что теряем / риски:** при неоднозначных названиях можно получить не тот город (пользователь может выбрать из подсказок). Сообщение в заголовке вкладки показывает «город, регион, страна», поэтому ошибка видна.

### Решение 5: debounce 300 мс и минимум 2 символа

- **Выбрано:** 300 мс и `query.length >= 2`.
- **Почему:** 300 мс это типичный компромисс «успел допечатать слово» против «не тормозит»; 2 символа: меньше геокодер всё равно ничего не вернёт (документация).
- **Что теряем / риски:** подсказки появляются с задержкой в треть секунды. Значения вынесены в **параметры конструктора** (`suggestDebounce`), в тестах они миллисекунды.

### Решение 6: сбой подсказок молчит

- **Выбрано:** если запрос подсказок упал (сеть, сервер), список просто пропадает, **состояние погоды не меняется**.
- **Почему:** подсказки удобство. Красное сообщение посреди экрана оттого, что не загрузился выпадающий список, ввело бы в заблуждение (погода-то есть). Настоящее сообщение пользователь увидит, нажав «поиск» (ex03).
- **Что теряем / риски:** пользователь не узнает, *почему* подсказок нет. Для учебного приложения нормально.

### Решение 7: номерки против отмены

См. 2.5. **Выбрано:** номерки.

### Решение 8: где живёт текстовое поле

См. 2.7. **Выбрано:** `TextEditingController` в `HomePage`, `SearchAppBar` без состояния.

### Решение 9: выпадающий список своими руками

- **Варианты:** (а) свой `SuggestionsList` на `Stack`; (б) `Autocomplete` (встроенный виджет Flutter); (в) `SearchAnchor` из Material 3.
- **Выбрано:** (а).
- **Почему:** сабж задаёт конкретный вид (поле в `AppBar`, подсказки под ним, вкладки не сдвигаются). `Autocomplete` рассчитан на **синхронный** список опций и свой оверлей; с асинхронным геокодером, debounce и номерками его пришлось бы обходить. `SearchAnchor` открывает отдельный «поисковый экран» поверх всего, это другой UX, чем в сабже.
- **Что теряем / риски:** нет встроенной навигации стрелками по списку (важно для клавиатуры в вебе) и озвучки для скринридера; см. «Что дальше».

**`lib/models/place.dart`**: место для показа и для запроса погоды.

```dart
import 'coordinates.dart';

// Место на карте: то, что пользователь видит как «город, регион, страна».
class Place {
  const Place({
    required this.name,
    required this.coordinates,
    this.region,
    this.country,
  });

  // Место, про которое известны только координаты (обратный геокодер не ответил).
  // Погоду по координатам получить всё равно можно, а на экране будет «41.3874, 2.1686».
  factory Place.atCoordinates(Coordinates coordinates) =>
      Place(name: coordinates.toString(), coordinates: coordinates);

  final String name;
  final String? region; // admin1 у Open-Meteo: область, провинция, штат...
  final String? country;
  final Coordinates coordinates;

  // «Île-de-France, France»: всё, что есть, кроме названия. Пусто, если ничего нет.
  String get subtitle => [
    if (region != null && region!.isNotEmpty) region!,
    if (country != null && country!.isNotEmpty) country!,
  ].join(', ');

  @override
  String toString() => subtitle.isEmpty ? name : '$name, $subtitle';
}
```

Разбор:

- Три необязательных поля (`String?`): у Open-Meteo `admin1` и `country` могут отсутствовать (*«Empty fields are not returned»*). `null` честнее, чем пустая строка.
- `subtitle`: **коллекция с `if` внутри** (`[ if (...) region!, if (...) country! ]`) и `join(', ')`. Если нет региона, получим просто «France»; нет обоих: пустую строку (виджет её не покажет). Восклицательный знак `region!` безопасен: проверка `region != null` в этом же `if`.
- `factory Place.atCoordinates(...)`: **фабричный конструктор**: запасной вариант, когда название места неизвестно. Имя = `"41.3874, 2.1686"`.
- У `Place` нет `==`: сравниваем `Place` по **идентичности** (один и тот же объект). Нам этого достаточно, в тестах мы возвращаем одни и те же константы `paris`, `parma`.

**`lib/services/http_json.dart`**: общая часть всех запросов.

```dart
import 'dart:convert';

import 'package:http/http.dart' as http;

import '../failures.dart';

// Общая часть всех запросов: GET, проверка кода ответа, разбор JSON-объекта.
// Все ошибки превращаются в WeatherFailure, чтобы остальной код не знал про
// SocketException, ClientException и прочую «сантехнику».
Future<Map<String, dynamic>> getJson(
  http.Client client,
  Uri uri, {
  Duration timeout = const Duration(seconds: 10),
}) async {
  final http.Response response;
  try {
    response = await client.get(uri).timeout(timeout);
  } on Exception {
    // Сюда попадает всё, что бывает на проводе: нет сети (ClientException,
    // в том числе с SocketException внутри), обрыв, TLS, таймаут (TimeoutException).
    // dart:io здесь не импортируем: на вебе его нет.
    throw const ConnectionFailure();
  }

  if (response.statusCode != 200) {
    throw ServerFailure(statusCode: response.statusCode);
  }

  try {
    // Декодируем БАЙТЫ как UTF-8 сами. response.body угадывает кодировку по
    // заголовку, и без `charset=utf-8` «Île-de-France» превращается в кракозябры.
    final Object? decoded = jsonDecode(utf8.decode(response.bodyBytes));
    if (decoded is Map<String, dynamic>) {
      return decoded;
    }
  } on FormatException {
    // не JSON: падаем ниже
  }
  throw const ServerFailure();
}

// Обёртка для разбора ЧУЖИХ данных: любая неожиданность в их форме
// (нет ключа, не тот тип, число вместо строки) означает «сервер ответил не то».
// Мы ловим именно Object: TypeError и RangeError это Error, а не Exception.
T parseResponse<T>(T Function() parse) {
  try {
    return parse();
  } on Object {
    throw const ServerFailure();
  }
}
```

Разбор:

1. Сигнатура: `Future<Map<String, dynamic>> getJson(http.Client client, Uri uri, {Duration timeout = ...})`: функция верхнего уровня (не метод), клиент **передаётся** (для подмены в тестах).
2. `client.get(uri).timeout(timeout)`: `Future.timeout` бросает `TimeoutException`, если ответ не пришёл вовремя.
3. `on Exception { throw const ConnectionFailure(); }`: **любое** исключение на проводе (в том числе `TimeoutException`, `ClientException`, `HandshakeException`) становится «нет связи». Мы не импортируем `dart:io`, потому что на web его нет.
4. `statusCode != 200`: `ServerFailure(statusCode: ...)`.
5. `jsonDecode(utf8.decode(response.bodyBytes))`: сначала **байты в строку по UTF-8**, потом строка в структуру.
6. `decoded is Map<String, dynamic>`: **проверка типа с автоприведением** (type promotion): внутри `if` компилятор уже знает тип.
7. `FormatException` от `jsonDecode` ловится, и мы выходим на финальный `throw const ServerFailure()`: любое «не то» (не JSON, JSON-массив вместо объекта) это «сервер ответил странно».
8. **`parseResponse<T>(T Function() parse)`**: дженерик-обёртка: всё, что внутри бросит (`TypeError` от `as`, `RangeError`, `FormatException` от `DateTime.parse`), станет `ServerFailure`. `on Object`, потому что `TypeError` это `Error`, а не `Exception`.

**`lib/services/geocoding_service.dart`**:

```dart
import 'package:http/http.dart' as http;

import '../failures.dart';
import '../models/coordinates.dart';
import '../models/place.dart';
import 'http_json.dart';

// «Название => места»: поиск города по тексту.
abstract interface class GeocodingService {
  // Возвращает до [count] подходящих мест (пустой список = ничего не нашлось).
  // Бросает ConnectionFailure или ServerFailure.
  Future<List<Place>> search(String query, {int count = 5});
}

// Geocoding API от Open-Meteo: https://open-meteo.com/en/docs/geocoding-api
final class OpenMeteoGeocodingService implements GeocodingService {
  OpenMeteoGeocodingService(this._client);

  final http.Client _client;

  @override
  Future<List<Place>> search(String query, {int count = 5}) async {
    // Uri.https сам экранирует параметры: «São Paulo, Brazil» уйдёт как надо.
    final Uri uri = Uri.https('geocoding-api.open-meteo.com', '/v1/search', {
      'name': query,
      'count': '$count',
      'language': 'en',
      'format': 'json',
    });

    final Map<String, dynamic> json;
    try {
      json = await getJson(_client, uri);
    } on ServerFailure catch (failure) {
      // 400 здесь значит «эти параметры недопустимы» (например, слишком
      // длинное название). Для пользователя это «такого города нет».
      if (failure.statusCode == 400) {
        return const [];
      }
      rethrow;
    }

    // Если ничего не найдено, ключа `results` в ответе просто нет.
    final Object? results = json['results'];
    if (results == null) {
      return const [];
    }

    return parseResponse(
      () => [
        for (final Object? item in results as List<Object?>)
          _placeFrom(item as Map<String, dynamic>),
      ],
    );
  }

  Place _placeFrom(Map<String, dynamic> json) => Place(
    name: json['name'] as String,
    region: json['admin1'] as String?,
    country: json['country'] as String?,
    coordinates: Coordinates(
      (json['latitude'] as num).toDouble(),
      (json['longitude'] as num).toDouble(),
    ),
  );
}
```

Разбор:

- Интерфейс `GeocodingService` и реализация `OpenMeteoGeocodingService` (тот же приём, что у `LocationService`: контроллер знает интерфейс).
- `Uri.https('geocoding-api.open-meteo.com', '/v1/search', {...})`: параметры в словаре, кодирование автоматическое. Значения словаря обязаны быть **строками**, поэтому `'$count'`.
- `language=en`: названия на английском (язык интерфейса приложения английский).
- `on ServerFailure catch (failure) { if (failure.statusCode == 400) return const []; rethrow; }`: Open-Meteo отвечает `400`, когда параметры недопустимы (например, текст из 500 символов). Для пользователя это «такого города нет». Остальные ошибки пробрасываем (`rethrow`).
- `json['results']` может **отсутствовать**: это «ничего не нашлось», возвращаем `[]`.
- `_placeFrom`: приводит каждый элемент. `as String?` для необязательных полей: если ключа нет, значение `null`, и `null as String?` проходит.
- `(json['latitude'] as num).toDouble()`: ловушка `int`/`double` (2.2).

#### Слой 3: контроллер, версия этапа ex01

Что нового в контроллере по сравнению с ex00: три действия, подсказки и номерки.

```dart
// Поиск «без выбора из списка»: берём первое, что нашёл геокодер.
Future<void> search(String text) {
  final String query = text.trim();
  _clearSuggestions();
  if (query.isEmpty) {
    return Future.value();        // пустое игнорируем: экран остаётся как был
  }
  return _run(() async {
    final List<Place> found = await _geocoding.search(query, count: 1);
    if (found.isEmpty) {
      throw CityNotFoundFailure(query);     // заготовка для ex03
    }
    return _weather.fetch(found.first);     // заготовка для ex02
  });
}

// Пользователь выбрал город из списка подсказок.
Future<void> select(Place place) {
  _clearSuggestions();
  return _run(() => _weather.fetch(place));
}

// Пользователь печатает: обновляем подсказки (с задержкой).
void queryChanged(String text) {
  _debounceTimer?.cancel();
  final String query = text.trim();
  final int id = ++_suggestId;

  if (query.length < 2) {
    _setSuggestions(const []);
    return;
  }
  _debounceTimer = Timer(suggestDebounce, () => _loadSuggestions(query, id));
}
```

Полный итоговый файл и разбор внутренней кухни (`_run`, повторы) в [ex03](02-ex03.md#42-итоговые-файлы); здесь важно только следующее.

Разбор:

- **`search`**: `trim()`: пробелы по краям не часть названия. Пустой текст возвращает **готовый `Future.value()`** и ничего не меняет (и не стирает данные на экране). Обратите внимание: функция не `async`, а возвращает `Future` (для `return Future.value();` и для `return _run(...)`): так проще и нет лишней обёртки.
- **Лямбда `() async {...}`**: «задание» передаётся в общий `_run`: он умеет загрузку, ошибки и повтор (ex03). `search` описывает только **что** делать.
- **`found.first`**: безопасно, потому что пустой случай уже обработан выше.
- **`queryChanged`**:
  1. `_debounceTimer?.cancel()`: прежний отложенный запрос отменён.
  2. `final int id = ++_suggestId;`: новый номерок (**до** проверки длины: любое изменение текста обесценивает летящие запросы).
  3. `query.length < 2`: подсказки очищаем сразу, без сети.
  4. `Timer(suggestDebounce, () => _loadSuggestions(query, id))`: запрос через 300 мс (если до этого не отменят).
- **`_loadSuggestions`** (приватный): запрашивает `count: 5`, сверяет номерок и ставит список; на `WeatherFailure` прячет список (решение 6).
- **`_setSuggestions`** не рассылает уведомление, если список был пуст и остался пуст: меньше лишних перерисовок экрана при каждом нажатии клавиши.
- **`_clearSuggestions`**: отменяет таймер, увеличивает номерок (старые ответы не применятся) и очищает список. Его зовут `search`, `select` и `useCurrentLocation`.

**Тест-подсказка по порядку:** `select` вызывает `_clearSuggestions()` **до** `_run`; поэтому тест «выбор и поиск убирают подсказки и отменяют ожидающий запрос» проверяет, что отложенный запрос после выбора **не уходит**.

#### Слой 5: обратный геокодер

**`lib/services/reverse_geocoding_service.dart`**:

```dart
import 'package:http/http.dart' as http;

import '../failures.dart';
import '../models/coordinates.dart';
import '../models/place.dart';
import 'http_json.dart';

// «Координаты => место»: какой это город.
// У Open-Meteo такого запроса НЕТ (их геокодер ищет только по названию),
// поэтому берём отдельный сервис.
abstract interface class ReverseGeocodingService {
  Future<Place> lookup(Coordinates coordinates);
}

// BigDataCloud, бесплатный «client-side» запрос без ключа:
// https://www.bigdatacloud.com/docs/api/free-reverse-geocode-to-city-api
// Условия: вызывать надо с устройства пользователя для ЕГО текущего места
// (ровно наш случай), не с сервера и не пакетами.
final class BigDataCloudReverseGeocodingService
    implements ReverseGeocodingService {
  BigDataCloudReverseGeocodingService(this._client);

  final http.Client _client;

  @override
  Future<Place> lookup(Coordinates coordinates) async {
    final Uri uri = Uri.https(
      'api.bigdatacloud.net',
      '/data/reverse-geocode-client',
      {
        'latitude': '${coordinates.latitude}',
        'longitude': '${coordinates.longitude}',
        'localityLanguage': 'en',
      },
    );

    final Map<String, dynamic> json = await getJson(_client, uri);

    return parseResponse(() {
      // city бывает пустой строкой (не null!), тогда берём locality.
      final String name = _firstNotEmpty(json['city'], json['locality']);
      if (name.isEmpty) {
        throw const FormatException('no city name'); // станет ServerFailure
      }
      return Place(
        name: name,
        region: _firstNotEmpty(json['principalSubdivision']),
        country: _firstNotEmpty(json['countryName']),
        coordinates: coordinates,
      );
    });
  }

  // Первая непустая строка из кандидатов, иначе ''.
  String _firstNotEmpty(Object? a, [Object? b]) {
    for (final Object? value in [a, b]) {
      if (value is String && value.trim().isNotEmpty) {
        return value.trim();
      }
    }
    return '';
  }
}
```

Разбор:

- Запрос: `GET https://api.bigdatacloud.net/data/reverse-geocode-client?latitude=..&longitude=..&localityLanguage=en`. Ключа нет.
- Из ответа берём `city`, `locality`, `principalSubdivision`, `countryName`. **Ловушка:** у BigDataCloud `city` иногда **пустая строка** (не `null`), а населённый пункт лежит в `locality`. Поэтому `_firstNotEmpty(json['city'], json['locality'])` берёт первую **непустую** строку (`is String && trim().isNotEmpty`; ведь `null is String` ложно, отдельная проверка на `null` не нужна).
- `throw const FormatException('no city name')` внутри `parseResponse`: «ни города, ни населённого пункта» (середина океана, пустыня) превращается в `ServerFailure`. А контроллер на `ServerFailure` от этого сервиса подставляет координаты (решение 3).
- `coordinates: coordinates`: место получает **наши** координаты (те, что дал GPS), а не те, что вернул сервис.

**Вызов из контроллера** (в `useCurrentLocation`):

```dart
final Coordinates coordinates = known ??= await _location.currentCoordinates();
final Place place = await _placeAt(coordinates);   // название по координатам
return _weather.fetch(place);                      // погода
```

`known ??= await ...`: **«присвоить, если `null`»**: переменная `known` запоминает координаты, чтобы при повторе после обрыва (ex03) GPS **не опрашивался заново**.

`_placeAt` перехватывает `ServerFailure` и возвращает `Place.atCoordinates`; а вот `ConnectionFailure` пролетает наверх: если связи нет совсем, погоды тоже не получить, и повторим всё целиком.

## 5. Альтернативы

| Подход | Суть | Плюсы | Минусы | Когда подойдёт |
|---|---|---|---|---|
| **`http` + Open-Meteo Geocoding** (выбрано) | см. выше | без ключа, тестируется `MockClient` | лимиты бесплатного плана | наш случай |
| Пакет `dio` | продвинутый HTTP-клиент | перехватчики, отмена, повторы, логи | ещё один пакет | сложная сеть |
| Пакет `geocoding` (платформенный) | прямой и обратный геокодинг через систему | один пакет на оба направления | нужны сервисы платформы, нестабилен на эмуляторе и web | если нужен только мобильный клиент |
| **Nominatim** (OSM) вместо BigDataCloud | обратный геокодинг от OpenStreetMap | открытые данные | свой `User-Agent`, 1 запрос/с, автодополнение на клиенте запрещено | замена обратного геокодера |
| `Autocomplete<Place>` | встроенный виджет подсказок | меньше своего кода, доступность из коробки | синхронная модель опций, свой оверлей | простые локальные списки |
| `SearchAnchor` (M3) | «поисковый экран» поверх всего | готовые подсказки и история | другой UX, чем в сабже | отдельный экран поиска |
| Отмена запросов вместо номерков | `CancelableOperation`, `AbortableRequest` | не тратим трафик на лишние ответы | сложнее | дорогие запросы, мобильный трафик |
| `StreamController` + `debounce` из `rxdart` | реактивный поток ввода | компактный debounce и `switchMap` (сам отменяет старое) | пакет и новая парадигма | много потоков событий |
| Пакет `easy_debounce` и т. п. | готовый debounce | меньше строк | зависимость ради 5 строк `Timer` | если debounce нужен в десяти местах |
| Подсказки при каждом символе, без debounce | проще | мгновенно | шквал запросов, гонки, лимиты | **не рекомендую** |

## 7. Диагностика

| Симптом | Причина | Что делать |
|---|---|---|
| Подсказок нет вообще | Нет разрешения INTERNET в release-манифесте (в debug работает) | `tools/patch_android_manifest.sh`; в debug смотреть логи |
| Подсказки приходят только на «Par», не на «Pa» | Два символа ищутся по **точному** названию (документация) | Нормально; смотреть со 3-го символа |
| `Île-de-France` показывает `Ã\u008ele-de-France` | Декодировка не как UTF-8 (`response.body` без `charset`) | Брать `utf8.decode(response.bodyBytes)` (так и сделано) |
| `type 'int' is not a subtype of type 'double'` | `as double` на JSON-числе без точки | `(x as num).toDouble()` |
| `type 'Null' is not a subtype of type 'String'` в парсере | Нет обязательного поля или не то ожидание | Это `ServerFailure` через `parseResponse`; смотреть реальный ответ `curl` |
| Список подсказок закрывает всё и не реагирует | `Stack` без `Align`/`Material` или список без ограничения высоты | Использовать готовый `SuggestionsList` |
| `No Material widget found` | `ListTile` вне `Material` | `Material(elevation: 4)` вокруг списка |
| После выбора подсказки поле снова даёт подсказки | Записали текст и вызвали `queryChanged` вручную | Не вызывать: `controller.text = ...` и так не вызывает `onChanged` |
| Список «мигает» старыми данными | Нет номерков или сверки `id` | См. 2.5 |
| Тест: `Timer is still pending` | Контроллер не освобождён | `addTearDown(controller.dispose)` |
| `flutter test` на `MockClient`: `Failed host lookup` | В тесте создан настоящий `http.Client()` | Подставить `MockClient` |
| 429 или 402 от сервера | Слишком много запросов с одного адреса | Увеличить debounce; для BigDataCloud см. условия (client-side, не пакетами) |

## 8. Безопасность и риски

- **Не склеивайте адреса строками.** Параметры только через `Uri.https(..., {...})`: иначе пользовательский текст (`&`, `#`, пробелы) способен изменить запрос.
- **Что уходит наружу.** Открытый запрос поиска: введённый текст отправляется на `geocoding-api.open-meteo.com` (**до** выбора города: каждое слово, которое печатает пользователь). Координаты GPS: на `api.bigdatacloud.net` и `api.open-meteo.com`. Всё по HTTPS. В настоящем приложении это отражается в политике конфиденциальности.
- **Не логируем запросы и координаты.** В нашем коде `debugPrint` используется только для ошибок плагина и неожиданных исключений.
- **Лимиты и условия.** Open-Meteo бесплатно только для **некоммерческого** использования (600/мин, 5000/час, 10 000/сутки), с указанием источника (CC BY 4.0); BigDataCloud client-side: только с устройства для его собственного текущего положения. Debounce в 300 мс держит нас далеко от лимитов.
- **Недоверие к чужим данным.** Любое поле ответа может отсутствовать, быть другого типа или `null`. Весь разбор идёт через `parseResponse`, поэтому странный ответ даёт аккуратное `ServerFailure`, а не краш.
- **Таймаут обязателен.** Ни один сетевой вызов не должен ждать вечно.

## 10. Что запомнить

**Dart:**

- `Uri.https(host, path, {параметры})` кодирует параметры сам. Никогда не склеивать строки.
- JSON-число это `num`: `(x as num).toDouble()`. Типы из JSON не гарантированы: приведения только в одном месте, с общей обёрткой `parseResponse`.
- `Exception` и `Error` разные: на проводе ловим `on Exception`, при разборе чужих данных `on Object`.
- Байты, а не `body`: `utf8.decode(response.bodyBytes)`.
- `??=`: присвоить, если пусто. Условные элементы коллекций: `[ if (условие) x ]`.
- `Timer` + `cancel()` = debounce. `late` для переменной, которой значение придёт позже.

**Flutter:**

- `Stack` кладёт слои друг на друга; `Align` без ребёнка в точке нажатия **не перехватывает** нажатия; `Material` нужен под `ListTile`.
- `controller.text = ...` из кода не вызывает `onChanged`.
- Состояние поднимают к **общему предку всех, кому оно нужно**; если набор участников изменился, оно может переехать и обратно.

**Логика и реализация:**

- Debounce: запрос только после паузы; номерки: ответ применяется, только если запрос всё ещё последний.
- Прямой геокодинг (имя → место) и обратный (координаты → имя) это разные сервисы с разными условиями.
- Подсказки удобство: их сбой не должен выглядеть как авария приложения.
- Любая ошибка сети превращается в наш тип на границе сервиса.
- Тесты сети: `MockClient`, никаких настоящих запросов.
