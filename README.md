# 42 Barcelona: Piscine Mobile (Flutter / Dart)

Репозиторий с решениями и подробными конспектами к мобильной писцине 42 Barcelona.
Стек: **Flutter + Dart**. Работаем на Linux-машинах кампуса, без `sudo`, с маленьким home и общим хранилищем `sgoinfre`.

Этот README это «входная дверь» в проект. Здесь собрано всё общее: как поднять окружение, как устроен репозиторий, как работать с устройствами, как не забить диск и как сдавать. Подробные разборы конкретных упражнений лежат в [`docs/`](docs/index.md).

> **Важно.** Это **личный** репозиторий (GitHub), в нём работаем над всеми модулями сразу. **Репозиторий для защиты в кампусе** отдельный и свой на каждый модуль: туда выгружается только папка модуля (`mobileModuleNN`) в том виде, как требует сабж. Как это устроено: [раздел 8](#8-git-и-сдача).

## 1. О репозитории

### 1.1 Что здесь есть

- **Решения** упражнений писцины. Каждый модуль лежит в папке с **точным именем из сабжа** (`mobileModule00` и так далее): эта папка потом выгружается в репозиторий кампуса без изменений.
- **Установщик окружения** [`setup_flutter_campus.sh`](setup_flutter_campus.sh): один скрипт, который за несколько минут поднимает Flutter, JDK и Android SDK на любой машине кампуса без `sudo`.
- **Конспекты** в [`docs/`](docs/index.md): по каждому упражнению отдельный разбор с теорией, решениями, кодом по строкам, альтернативами и типичными ошибками. Цель конспектов: чтобы через месяц можно было открыть файл и всё вспомнить, а не только «оно как-то работало».
- **Скрипт выгрузки** [`tools/export_module.sh`](tools/export_module.sh): переносит готовый модуль в репозиторий кампуса, не прихватывая лишнего.

### 1.2 Структура

```
Mobile/                          ← личный репозиторий (GitHub)
├── README.md                    ← этот файл (общее на все модули)
├── setup_flutter_campus.sh             ← установщик окружения
├── .gitignore
├── tools/
│   └── export_module.sh         ← выгрузка модуля в репозиторий кампуса
├── docs/                        ← конспекты по упражнениям
│   ├── index.md
│   ├── _template.md
│   ├── 00-ex00.md
│   ├── 00-ex01.md
│   ├── 00-ex02.md
│   └── 00-ex03.md
├── mobileModule00/              ← имя = папка сдачи по сабжу
│   ├── ex00/                    ← Flutter-проект
│   ├── ex01/
│   ├── ex02/
│   └── calculator_app/          ← проект упражнения ex03 (так назван в сабже)
├── mobileModule01/              ← и так далее, имена уточнять по сабжу модуля
└── ...
```

В репозиторий кампуса попадает **только** содержимое `mobileModuleNN/`. Всё остальное (README, docs, скрипты) остаётся в личном репозитории.

### 1.3 Как устроена документация

| Уровень | Файл | О чём |
|---|---|---|
| Общее | этот `README.md` | окружение, инструменты, процессы, модули |
| Индекс | [`docs/index.md`](docs/index.md) | список всех разборов, как их писать |
| Упражнение | `docs/NN-exMM.md` | задача, теория, решения, код, альтернативы, диагностика |

Каждый разбор упражнения следует одному плану: задача и с чего начать → теория → декомпозиция и решения → разбор кода → альтернативы → запуск → диагностика → безопасность → что дальше → **«Что запомнить»**. Шаблон: [`docs/_template.md`](docs/_template.md).

### 1.4 Соглашения

- Язык документации: русский. Идентификаторы в коде и комментарии к коду: английский.
- Команды даны для `zsh` и `bash` (если есть различия, они отмечены).
- `~` это home пользователя. Пути вида `~/sgoinfre/...` одинаковы на всех машинах кампуса.

## 2. Быстрый старт

Если окружение ещё не поставлено:

```bash
cd ~/Projects/Mobile
chmod +x setup_flutter_campus.sh
./setup_flutter_campus.sh          # 5–15 минут при первом запуске
```

Откройте **новый терминал** (или выполните `source ~/.flutter_env.sh`) и проверьте:

```bash
flutter doctor -v           # ждём: No issues found
```

Запуск упражнения:

```bash
cd ~/Projects/Mobile/mobileModule00/ex00
flutter pub get
flutter analyze             # No issues found!
flutter test                # All tests passed!
flutter run -d chrome       # быстрая проверка в браузере
flutter run                 # на подключённом телефоне
```

Если что-то пошло не так, смотрите [раздел 11](#11-диагностика).

## 3. Окружение без sudo

### 3.1 Ограничения кампуса

Кампусная машина это не «своя» машина. От этого и зависят все решения ниже.

| Место | Что это | Особенности |
|---|---|---|
| `~` (home) | Общий для всех машин, **маленький** (около 4.7 ГБ) | Исходники проектов. Тяжёлое сюда нельзя: забьётся |
| `~/goinfre` | **Локальный** диск конкретной машины | Быстрый, но на другой машине пустой; периодически чистится |
| `~/sgoinfre` | Хранилище, **общее** для машин | Переживает смену компьютера. Проверено на практике: на второй машине Flutter и Android SDK уже были на месте |

Следствия:

1. **Права root нет**, поэтому всё ставится из архивов в домашние каталоги.
2. **SDK-файлы** (Flutter, Android SDK, JDK) читаются часто и меняются редко. Их кладём в `sgoinfre`: поставил один раз и работает везде.
3. **Кэши сборки** (Gradle, pub) активно пишутся и используют файловые блокировки. Их кладём в локальный `goinfre`. Это быстрее и безопаснее, чем писать на общий том (на сетевых файловых системах блокировки бывают медленными или глючными).
4. **Исходники** живут в `~/Projects` и сохраняются через git. Никакого хранения кода только в goinfre.

### 3.2 Что именно устанавливается

| Компонент | Зачем | Куда ставится |
|---|---|---|
| **Flutter SDK** (по умолчанию 3.50.0, Dart 3.14) | Фреймворк и инструмент `flutter` | `~/sgoinfre/flutter` |
| **JDK 17** | Нужен Gradle для сборки Android-приложений | Системный JDK ≥17, если он есть; иначе Temurin 17 в `~/sgoinfre/jdk-17` |
| **Android cmdline-tools** | `sdkmanager`, лицензии, установка пакетов | `~/sgoinfre/android-sdk/cmdline-tools/latest` |
| **platform-tools** | `adb`: связь с телефоном | `~/sgoinfre/android-sdk/platform-tools` |
| **Android platform + build-tools** | Библиотеки и инструменты сборки под Android (сейчас API 36, build-tools 36.0.0) | `~/sgoinfre/android-sdk/platforms`, `.../build-tools` |
| **Кэш pub** (`PUB_CACHE`) | Скачанные Dart-пакеты | `~/goinfre/.pub-cache` |
| **Кэш Gradle** (`GRADLE_USER_HOME`) | Зависимости Android-сборки | `~/goinfre/.gradle` |
| **AVD** (`ANDROID_AVD_HOME`) | Образы эмуляторов, если когда-нибудь понадобятся | `~/goinfre/.android-avd` |

Специально остаётся в home: каталог **`~/.android`**. Там лежит ключ `adbkey`, по которому телефон «узнаёт» компьютер. Благодаря этому телефон не спрашивает разрешение на отладку заново на каждой машине. Каталог маленький.

**Android Studio не ставим.** Он тяжёлый, медленно стартует, плодит конфиги в home, а кампус сам не рекомендует его для кластеров. Всё делается из терминала.

### 3.3 Скрипт `setup_flutter_campus.sh`

**Скрипт только для кампуса** (отсюда `_campus` в имени): он рассчитан на `sgoinfre`/`goinfre`, переписывает `.zshrc`/`.bashrc` и ставит свой Flutter первым в `PATH`. Дома его не запускают (см. [8.9](#89-работа-с-нескольких-машин-дом-и-кампус)).

**Идея.** Один скрипт, который можно запускать на любой машине сколько угодно раз. Он **идемпотентный**: каждый шаг сначала проверяет, не сделан ли он уже, и пропускает готовое. На новой машине, где `goinfre` пуст, а `sgoinfre` заполнен, он отработает за секунды и лишь пересоздаст каталоги кэшей и файл окружения.

**Что он делает, по шагам:**

| Шаг | Действие |
|---|---|
| 0 | Выбирает, где жить SDK: `~/sgoinfre`, если он существует и доступен на запись, иначе `~/goinfre`. Кэши всегда в `~/goinfre` |
| 1 | Проверяет окружение: архитектура x86_64, наличие `tar`, `unzip`, `git`, `python3`, `wget` или `curl`, свободное место (предупреждение, если меньше 6 ГБ) |
| 2 | **Flutter:** скачивает архив `.tar.xz` из `storage.googleapis.com` и распаковывает в `SDK_BASE/flutter` |
| 3 | **JDK:** берёт каталог `jdk-17` из SDK_BASE, иначе системный JDK версии не ниже 17, иначе скачивает Temurin 17 (Adoptium) |
| 4 | **Android SDK:** распаковывает cmdline-tools в `cmdline-tools/latest` (именно такая структура обязательна), принимает лицензии, ставит `platform-tools`, платформу и build-tools. В конце **проверяет результат**: если `platforms/` пуст или нет `adb`, скрипт падает с ошибкой, а не врёт «Готово» |
| 5 | **Настройка Flutter:** `flutter config --android-sdk`, `--jdk-dir`, отключает Linux-desktop (на кампусе без sudo не собрать), отключает аналитику, принимает лицензии |
| 6 | Пишет файл [`~/.flutter_env.sh`](#34-файл-flutter_envsh) и подключает его в `~/.zshrc` и `~/.bashrc` (если они существуют и строки ещё нет) |
| 7 | Запускает `flutter doctor` |

**Переменные, которыми можно управлять:**

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `FLUTTER_VERSION` | `3.50.0` | Версия Flutter. Значение `latest` берёт текущий stable с сервера Google |
| `JDK_MAJOR` | `17` | Минимальная/устанавливаемая версия JDK |
| `SDK_BASE` | `~/sgoinfre` (или `~/goinfre`) | Где ставить Flutter, Android SDK, JDK |
| `CACHE_BASE` | `~/goinfre` | Где держать кэши (pub, Gradle, AVD) и скачанные архивы |

Примеры:

```bash
./setup_flutter_campus.sh                        # как обычно
FLUTTER_VERSION=latest ./setup_flutter_campus.sh # свежий stable
SDK_BASE=~/goinfre ./setup_flutter_campus.sh     # всё локально (если sgoinfre капризничает)
```

**Когда запускать повторно:**

- сели за **новую машину** (кэшей в goinfre нет);
- **goinfre почистили** (пропали Gradle/pub-кэши или сам SDK, если он был там);
- `flutter doctor` ругается на отсутствующий компонент.

Скрипт безопасен к повторному запуску: готовое не трогает. Если загрузка оборвалась, `wget -c` докачивает файл.

### 3.4 Файл `~/.flutter_env.sh`

Скрипт генерирует его сам, а в `.zshrc`/`.bashrc` добавляет одну строку, которая его подключает:

```bash
[ -f "$HOME/.flutter_env.sh" ] && . "$HOME/.flutter_env.sh"
```

Что в нём:

| Переменная | Значение |
|---|---|
| `FLUTTER_HOME` | каталог Flutter SDK |
| `JAVA_HOME` | выбранный JDK |
| `ANDROID_HOME`, `ANDROID_SDK_ROOT` | каталог Android SDK |
| `ANDROID_AVD_HOME` | каталог образов эмуляторов (goinfre) |
| `PUB_CACHE` | кэш Dart-пакетов (goinfre) |
| `GRADLE_USER_HOME` | кэш Gradle (goinfre) |
| `CHROME_EXECUTABLE` | только если найден Chromium, а не Google Chrome |
| `PATH` | в начало добавляются `java`, `sdkmanager`, `adb`, `flutter` и утилиты pub (без дублей) |

Файл лежит в общем home, значит **одинаков на всех машинах**. Это удобно, но есть нюанс про `JAVA_HOME` (см. [3.6](#36-подводные-камни)). В конце файла есть напоминалка: если на машине нет Flutter или каталога Gradle, при открытии терминала выведется подсказка запустить скрипт.

### 3.5 Проверка: `flutter doctor`

Эталонный результат (так и должно выглядеть на готовой машине):

```
[✓] Flutter (Channel stable, 3.50.0, ...)
[✓] Android toolchain - develop for Android devices (Android SDK version 36.0.0)
[✓] Chrome - develop for the web
[✓] Connected device (N available)
[✓] Network resources

• No issues found!
```

Что считать нормой:

- Строки про **Android Studio** нет или она с пометкой «not installed». Мы его сознательно не ставим.
- **Connected device** без телефона показывает только Chrome. Телефон появится после подключения (раздел 6).
- Предупреждение **«Multiple adb binaries found»** информационное (разбор в [3.6](#36-подводные-камни)).

### 3.6 Подводные камни

**`sdkmanager` объявлен устаревшим.** Теперь он перенаправляет на новый «Android CLI» (команда `android`). Из-за этого `sdkmanager --list` вместо списка пакетов печатает сообщения о скачивании и текст лицензии. Скрипт больше не полагается на разбор этого списка вслепую: если список не удалось разобрать, берутся запасные версии (платформа `android-36`, `build-tools;36.0.0`), а результат установки проверяется. Для Flutter 3.50 эти версии подходят. Если Gradle когда-нибудь запросит другую, он докачает её сам (лицензии приняты). Документация Android CLI не описывает, куда он распаковывает свои файлы; поэтому после установки стоит проверить размер home (раздел 7).

**«Multiple adb binaries found».** Doctor нашёл два `adb`: наш в `sgoinfre` и системный (`/usr/bin/adb`, пакет Ubuntu; `/bin/adb` это тот же файл). Наш стоит в `PATH` **первым**, поэтому используется именно он. Проверка:

```bash
which -a adb        # первым должен идти путь из sgoinfre
adb version         # у нас: 1.0.41, Version 37.x
/usr/bin/adb version
```

Конфликт «серверы убивают друг друга» возникает при разных версиях **протокола** (число `1.0.NN`). Если у системного тоже `1.0.41`, предупреждение можно спокойно игнорировать. Убрать его без `sudo` нельзя (системный пакет не удалить). Если телефон всё же начинает пропадать: `adb kill-server && adb devices`.

**`JAVA_HOME` в общем файле.** Если на машине был системный JDK 17, скрипт прописывает в `.flutter_env.sh` его путь (`/usr/lib/jvm/java-17-openjdk-amd64`). Файл лежит в общем home и «ездит» по машинам. Образы кампуса одинаковые, но если на какой-то этого JDK нет, перезапустите скрипт: он перепишет файл под текущую машину.

**Первая сборка на новой машине медленная.** Локальный `goinfre` пуст, поэтому Gradle и pub скачивают всё заново (несколько минут и сотни мегабайт). Это единоразово.

**Файловые блокировки на общем томе.** Flutter хранит lock в `flutter/bin/cache`. Если на общем `sgoinfre` команды зависают с сообщением `Waiting for another flutter command to release the startup lock...`, поставьте всё локально: `SDK_BASE=~/goinfre ./setup_flutter_campus.sh` (минус: на каждой машине придётся ставить заново).

**Напоминалка в `.flutter_env.sh`.** Если на машине нет Flutter или каталога Gradle, при открытии терминала выводится подсказка с **полным путём к скрипту**: скрипт запоминает своё расположение при установке (переменная `SETUP_FLUTTER_SCRIPT`). Если вы перенесли или переименовали скрипт, запустите его один раз заново, и путь в `.flutter_env.sh` обновится. Достаточно, чтобы клон репозитория лежал по одному и тому же пути на всех кампусных машинах (`~/Projects/Mobile`): он общий, потому что общий home.

**zsh и символ `!`.** В `zsh` конструкция `[!.]` воспринимается как история команд («event not found»). Для перечисления скрытых файлов используйте `~/.??*`, она работает и в bash, и в zsh.

### 3.7 Альтернативные способы установки

| Способ | Плюсы | Минусы | Когда подходит |
|---|---|---|---|
| **Наш скрипт** (архивы + sgoinfre) | Быстро, повторяемо, без sudo, переживает смену машины | Нужно поддерживать скрипт | Основной вариант для кампуса |
| **Ручная установка по инструкции кампуса** | Прозрачно, ничего лишнего | Кэши по умолчанию уходят в home и забивают его; нужно помнить все шаги | Разово, для понимания процесса |
| **`git clone -b stable` Flutter** | `flutter upgrade` работает через git | Тяжелее; с `--depth 1` upgrade ломается | Если нужны частые обновления |
| **FVM / puro** (менеджеры версий) | Разные версии Flutter для разных проектов | Лишний слой, ещё один инструмент | Когда проектам нужны разные версии |
| **Android Studio** | Всё автоматом, есть эмулятор и профайлер | Тяжёлый, плодит файлы в home, кампус не рекомендует | Дома, но не на кластере |
| **Flutter Web без Android SDK** | Минимум установки | Нет проверки на реальном устройстве, не всё доступно в браузере | Для упражнений без устройства |

## 4. Важно: `material_ui` вместо `flutter/material.dart`

Начиная с Flutter 3.47 библиотеки Material и Cupertino **вынесены из ядра SDK в отдельные пакеты**:

| Было | Стало |
|---|---|
| `import 'package:flutter/material.dart';` | `import 'package:material_ui/material_ui.dart';` |
| `import 'package:flutter/cupertino.dart';` | `import 'package:cupertino_ui/cupertino_ui.dart';` |

Многие туториалы и ответы нейросетей в интернете всё ещё показывают старый импорт. Это главный источник путаницы.

**Что изменилось:** только путь импорта и появление зависимости в `pubspec.yaml`. Названия виджетов и их API те же (`Scaffold`, `AppBar`, `ElevatedButton`, `ThemeData`). Версия 1.0 пакета визуально совпадает со старым Material.

**Что осталось в самом Flutter:** «ядро» (`Widget`, `StatelessWidget`, `Column`, `Padding`, `Center`, `Text`, `SizedBox`, `rendering`, `gestures`, `services`). Пакет `material_ui` делает `export 'package:flutter/widgets.dart'` (проверено в его исходнике), поэтому **одного импорта `material_ui.dart` достаточно** для обычного экрана.

**Как добавить зависимость:**

```bash
grep material_ui pubspec.yaml || flutter pub add material_ui
```

**Как мигрировать старый код автоматически:**

```bash
dart fix --apply --code=migrate_design_widgets
```

Команда добавляет зависимость и переписывает импорты.

**Подводные камни:**

- **Смешанные импорты.** Старый и новый Material в одном файле дают ошибки дублирующихся определений. Оставьте один.
- **Порядок.** Если запустить `dart fix` до появления пакета в `pubspec.yaml`, импорты могут не разрешиться. Сначала `flutter pub add`.
- **Сторонние пакеты на старом Material.** Если библиотека ещё импортирует `flutter/material.dart`, может понадобиться `MaterialUiCompatibilityBridge` (оборачивается в `MaterialApp.builder`).
- **Сроки.** Во вторичных источниках пишут, что старый импорт будет объявлен устаревшим в ноябрьском стабильном релизе, а удалён в релизе 2027 года. Это не проверено по официальной документации; считайте ориентиром.

### 5.1 Создание проекта

Каждое упражнение это **отдельный Flutter-проект** с именем из сабжа. Создаём его внутри папки модуля:

```bash

Предыдущее упражнение не меняем: оно сдаётся тоже.
- `flutter create` кладёт в проект рабочий пример (счётчик). Его **заменяем**, и тут есть ловушка с тестом: см. [`docs/00-ex00.md`](docs/00-ex00.md#7-диагностика).

### 5.4 Горячая перезагрузка

В консоли запущенного `flutter run`:

| Клавиша | Действие |
|---|---|
| `r` | **Hot reload**: подтягивает изменения кода, **сохраняя состояние** |
| `R` | **Hot restart**: полный перезапуск приложения, состояние сбрасывается |
| `q` | Выход |

Hot reload работает, потому что в debug-режиме Dart выполняется через JIT. В release код компилируется заранее (AOT), там горячей перезагрузки нет. Правка `main()` или глобальных переменных требует hot restart.

## 6. Тестирование на устройствах

Варианты в порядке удобства для кампуса:

1. **Flutter Web (`flutter run -d chrome`).** Самый быстрый цикл. Подходит для большинства упражнений, которым не нужны функции устройства. Если Chrome капризничает, `flutter run -d web-server` и открыть выданный адрес в любом браузере.
2. **Реальный Android-телефон по USB.** Нужен для всего, что связано с устройством (сенсоры, разрешения, настоящая адаптивность).
3. **Эмулятор.** На кампусных машинах **не использовать**: слабое железо, машина зависает или перезагружается.

**Про планшет.** В сабже на картинках показаны и телефон, и планшет. Планшет проще всего имитировать широким окном Chrome (800 пикселей и шире, в том числе через режим устройств в DevTools). Проверку на реальном телефоне и в браузере стоит провести заранее, а не на защите.

### Подключение телефона по USB

1. Включите режим разработчика: *Настройки → О телефоне → Сведения о ПО → Номер сборки* (нажмите 7 раз; на Samsung путь такой, на других телефонах он слегка отличается).
2. *Настройки → Параметры разработчика → Отладка по USB*: включить.
3. Подключите кабель (нужен кабель с передачей данных, а не только зарядный).
4. На телефоне подтвердите «Разрешить отладку по USB».
5. Проверьте: `adb devices` и `flutter devices`.

Состояния в выводе `adb devices`:

| Состояние | Значение | Что делать |
|---|---|---|
| `device` | Всё хорошо | Запускайте |
| `unauthorized` | Телефон не подтвердил компьютер | Разблокируйте экран, нажмите «Разрешить» |
| `offline` | Связь нестабильна | Переподключите кабель, `adb kill-server && adb devices` |
| `no permissions (missing udev rules?)` | Нет udev-правил (нужен root) | См. беспроводную отладку ниже |
| пусто | Телефон не виден | Другой кабель или порт, режим «Передача файлов» |

### Беспроводная отладка (если USB не работает)

Android 11 и новее: *Параметры разработчика → Отладка по Wi-Fi → Подключить с кодом*. Затем:

```bash
adb pair <IP>:<ПОРТ_ПАРЫ>       # ввести код с телефона
adb connect <IP>:<ПОРТ>
adb devices
```

Оговорка: сеть кампуса может изолировать клиентов друг от друга, тогда этот способ не сработает.

## 7. Дисковое место

Лимит home небольшой, и именно он чаще всего ломает работу. Что растёт:

| Что | Где | Размер | Как справляемся |
|---|---|---|---|
| Сборка проекта | `<проект>/build/` | сотни МБ **на каждый проект** | `flutter clean` по окончании упражнения |
| Анализатор и кэш проекта | `<проект>/.dart_tool/` | десятки-сотни МБ | `flutter clean` |
| Кэш pub | `~/goinfre/.pub-cache` | сотни МБ | Уже вне home |
| Кэш Gradle | `~/goinfre/.gradle` | 1–2 ГБ | Уже вне home |
| Кэш Dart-анализатора | `~/.dartServer` | десятки МБ | Можно удалять, пересоздастся |
| Прочие кэши | `~/.cache` | разное | Смотреть через `du` |

Диагностика «кто съел home»:

```bash
du -sh ~/.??* ~/* 2>/dev/null | sort -h | tail -15
df -h ~ | tail -1
```

Найти самые тяжёлые `build/` и `.dart_tool/` в проектах:

```bash
find ~/Projects -type d \( -name build -o -name .dart_tool \) -prune -exec du -sh {} + | sort -h
```

Правила гигиены:

1. Закончили упражнение, сделали `flutter clean`.
2. Не копируем проекты «про запас».
3. После установки окружения один раз проверяем `du` (см. камень про Android CLI в [3.6](#36-подводные-камни)).

### 8.1 Два репозитория

| | Личный репозиторий (GitHub) | Репозиторий кампуса (на модуль) |

- **Папка сдачи** в каждом упражнении модуля 00: `mobileModule00`.

- «Only the work inside your repository will be evaluated during the defense. Don't hesitate to double check the names of your folders and files»: имена папок проверяются буквально.
- Проверка проходит **на компьютере проверяемой группы**, то есть на вашем. Flutter и проекты должны запускаться там, где вы будете защищаться.

|---|---|
| `lib/`, `test/`, `pubspec.yaml`, `pubspec.lock`, `analysis_options.yaml`, `android/`, `web/` | `build/`, `.dart_tool/`, `android/local.properties`, `.idea/`, `*.iml` |

Нужные исключения есть и в `.gitignore` каждого проекта (его создаёт `flutter create`), и в корневом `.gitignore` личного репозитория. Не удаляйте оттуда строки. `pubspec.lock` для приложений принято коммитить: он фиксирует версии пакетов.

### 8.5 Выгрузка модуля в репозиторий кампуса

Выгрузка делается скриптом [`tools/export_module.sh`](tools/export_module.sh).

**Подготовка (один раз на модуль):** клонируйте репозиторий кампуса в отдельную папку, **не внутрь** личного репозитория:

```bash
cd ~/Projects
git clone <адрес_репозитория_кампуса> campus-mobile-00
```

**Каждая выгрузка:**

```bash
cd ~/Projects/Mobile
git add -A && git commit -m "Module 00 ready"        # всё закоммичено
CHECK=1 tools/export_module.sh 00 ~/Projects/campus-mobile-00
cd ~/Projects/campus-mobile-00
git add -A && git status                              # глазами: нет build/ и .dart_tool/
git commit -m "Module 00" && git push
```

Что делает скрипт:

1. Проверяет, что в `mobileModule00` нет незакоммиченных изменений (иначе остановится).
2. Проверяет состав папки модуля: лишней папки быть не должно (для модуля 00 ожидаются `ex00`, `ex01`, `ex02`, `calculator_app`; если какого-то нет, это лишь предупреждение). Для других модулей список задаётся переменной `EXPECTED="ex00 ex01 ..."`.
3. Очищает `mobileModule00` в репозитории кампуса и кладёт туда копию состояния последнего коммита (`git archive`). В копию попадают **только отслеживаемые git файлы**, поэтому `build/` и `.dart_tool/` не попадут.
4. При `CHECK=1` в копии запускает `flutter pub get`, `flutter analyze`, `flutter test` по каждому проекту: вы проверяете именно то, что уйдёт на защиту.
5. Показывает `git status` репозитория кампуса. **Коммит и push остаются вручную**: сдаваемое должно пройти через ваши глаза.

Скрипт протестирован на тестовых репозиториях: happy path, незакоммиченные правки, лишняя папка, неверные пути.

**Почему именно так, а не иначе:**

| Способ | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| **`git archive` (наш скрипт)** | Берёт ровно закоммиченное, не тащит `build/`, сохраняет папку `mobileModule00` | Нет истории личного репозитория в кампусном (она и не нужна) | **Выбрано** |
| `rsync` / `cp -r` | Просто | Прихватит `build/`, `.dart_tool/`, `local.properties`; надо помнить все исключения | Рискованно |
| `git subtree split` | Сохраняет историю | Делает содержимое папки корнем: **пропадает** папка `mobileModule00`, а она обязательна | Не подходит |
| `git filter-repo --path` | Сохраняет историю и путь | Переписывает историю, тяжёлый, отдельный инструмент | Избыточно |
| Git submodules | Формально «один код» | Кампус получит ссылку, а не файлы | Не подходит |
| Один общий репозиторий и для себя, и для кампуса | Без выгрузки | Лишние README, docs и скрипты в сдаче; нельзя разделить модули по дням | Противоречит сабжу |

### 8.6 Правила, чтобы две копии не разъехались

1. **Правки только в личном репозитории.** Репозиторий кампуса не редактируем руками.
2. Исправления после замечаний на защите: сначала в личном, потом новая выгрузка.
3. **Сначала `git commit`, потом выгрузка.** Скрипт остановится, если забыли, но привычка важнее.
4. После выгрузки не запускайте `flutter` в корне репозитория кампуса без нужды: `build/` и `.dart_tool/` не должны попадать в коммиты (они ограждены `.gitignore` проекта, но проверяйте `git status`).
5. Выгружайте **заранее**, а не за минуту до закрытия репозитория: в сабже сказано, что дата закрытия в интре совпадает с началом 24-часового периода взаимной проверки.
6. Репозиторий кампуса лежит **рядом**, а не внутри личного: иначе получится вложенный git-репозиторий.

В личном репозитории лежат решения заданий. Если репозиторий публичный, их увидят другие участники писцины, а это риск для вас (подозрение в списывании при совпадениях) и для них. Разумный вариант: держать репозиторий **приватным** до закрытия проверок, затем решить. Это ваше решение.

### 8.9 Работа с нескольких машин (дом и кампус)

**Принцип:** GitHub это единственный «транспорт» между машинами. Две привычки решают почти всё:

- **ушли: `commit` и `push`**;
- **пришли: `pull`**.

Лучше держать клон личного репозитория по **одному и тому же пути** на всех машинах (`~/Projects/Mobile`): тогда команды из этого README работают везде одинаково.

**Что синхронизируется, а что нет:**

| Синхронизируется (в git) | Не синхронизируется (создаётся на каждой машине заново) |
|---|---|
| `lib/`, `test/`, `pubspec.yaml`, `pubspec.lock`, `android/`, `web/`, `docs/`, `tools/` | `build/`, `.dart_tool/`, `android/local.properties`, кэши pub и Gradle |

После `git pull` в каждом проекте нужен `flutter pub get`, а первая сборка на машине будет долгой (скачиваются кэши). Это нормально.

**Рабочий цикл:**

```bash
# дома, первый раз
mkdir -p ~/Projects && cd ~/Projects
git clone git@github.com:Knowledge82/Mobile.git
cd Mobile

# каждый раз, когда садитесь работать (дом или кампус)
cd ~/Projects/Mobile
git pull
cd mobileModule00/ex01 && flutter pub get

# работа ...
flutter analyze && flutter test

# каждый раз, когда встаёте из-за компьютера
cd ~/Projects/Mobile
git add -A && git status --short      # проверить: нет build/, .dart_tool/, local.properties
git commit -m "ex01: toggle text"
git push
```

Коммиты можно делать частые и сырые (WIP): это ваш личный репозиторий. Выгрузка в репозиторий кампуса ([8.5](#85-выгрузка-модуля-в-репозиторий-кампуса)) берёт состояние на момент выгрузки, история ей не важна.

**Версия Flutter должна совпадать на всех машинах.** На кампусе 3.50.0 (Dart 3.14). Проект, созданный `flutter create`, записывает в `pubspec.yaml` ограничение на версию Dart (`environment: sdk: ^3.x.y`). Если дома Flutter старше, `flutter pub get` откажется работать (`version solving failed`), а `material_ui` может потребовать свежий Flutter. Проверка дома:

```bash
flutter --version
```

Если версия не 3.50.0, есть два пути:

| Вариант | Как | Плюсы | Минусы |
|---|---|---|---|
| **А. Обновить основной Flutter** | `flutter upgrade` | Проще всего | Затрагивает и другие ваши Flutter-проекты (после обновления прогоните в них `flutter analyze`) |
| **Б. Вторая копия SDK под писцину** | `mkdir -p ~/dev/flutter-3.50 && tar xf flutter_linux_3.50.0-stable.tar.xz -C ~/dev/flutter-3.50`, запуск через `~/dev/flutter-3.50/flutter/bin/flutter` (удобно сделать `alias`) | Основной Flutter не трогаем, версии как на кампусе | Две копии на диске; надо следить, каким `flutter` запускаете |

**Не запускайте `setup_flutter_campus.sh` дома**, если Flutter там уже стоит: скрипт пишет `~/.flutter_env.sh`, подключает его в `.zshrc`/`.bashrc` и ставит свой Flutter **первым** в `PATH`. Он рассчитан на кампус (`sgoinfre`/`goinfre`).

**Подводные камни:**

| Ситуация | Что происходит | Как избежать или лечить |
|---|---|---|
| Забыли `push` на кампусе | Дома нет последних правок; завтра на кампусе они лежат незапушенные | Привычка «встал из-за компьютера: commit и push». Если дома сделали то же самое с теми же файлами, будет конфликт при `git pull`: разрешите его вручную (в файле метки `<<<<<<<`), затем `git add` и `git commit` |
| Забыли `pull` | Правите старую версию, при `push` отказ (`rejected`) | Сначала `git pull`, потом `push`. Конфликты решаются как выше |
| `flutter pub get` падает: `version solving failed` | Версия Dart/Flutter дома ниже, чем при создании проекта | Выровнять версии (таблица выше) |
| Дома первая сборка просит лицензии или платформу Android | В домашнем Android SDK нет нужных компонентов | `flutter doctor --android-licenses`, затем сборка докачает платформу |
| Телефон дома снова просит разрешить отладку | У каждой машины свой ключ `adb` | Нажать «Разрешить» один раз |
| В коммит попали `build/` или `local.properties` | Нарушен `.gitignore` или добавили вручную | `git rm -r --cached <путь>`, закоммитить, проверить `.gitignore` |
| Токен или ключ доступа к GitHub | На кампусе и дома нужен доступ к репозиторию | Лучше SSH-ключ с паролем (`ssh -T git@github.com` проверяет доступ); токены в открытом виде в общем home не хранить |

**Финальная проверка перед защитой выполняется на кампусе.** По сабжу защита идёт на компьютере проверяемой группы, поэтому последний прогон `flutter analyze`, `flutter test` и запуск на телефоне делайте там (удобно через `CHECK=1 tools/export_module.sh`).

**Альтернативы схеме «GitHub как транспорт»:**

| Способ | Вердикт |
|---|---|
| Флешка или облачная папка (Syncthing, Dropbox и подобное) | Тащит `build/` и кэши, нет истории, легко затереть чужие правки |
| Работать только на кампусе | Надёжно, но теряете вечер и выходные |
| Удалённый доступ к кампусной машине | Недоступен и не нужен |
| Облачные среды (Codespaces и подобные) | Тяжёлые для Flutter, не нужны, когда есть git |

## 9. Минимум теории Flutter

Полный разбор с примерами лежит в [`docs/00-ex00.md`](docs/00-ex00.md#2-теория). Здесь только опорные идеи.

- **Всё есть виджет.** Экран это дерево вложенных виджетов.
- **Три дерева:** Widget (неизменяемое описание) → Element (живой экземпляр, хранит состояние) → RenderObject (размеры и отрисовка).
- **StatelessWidget** не меняется сам. **StatefulWidget** хранит `State`, а `setState` вызывает перестроение через `build()`.
- **Раскладка:** ограничения идут вниз, размеры вверх, позицию решает родитель.
- **`BuildContext`** это «адрес» виджета в дереве, через него ищут тему, размер экрана, навигатор.
- **`const`** создаёт объект на этапе компиляции и позволяет Flutter не перестраивать неизменившиеся поддеревья.
- Flutter **сам рисует** каждый пиксель (движок Impeller), а не оборачивает нативные кнопки.

## 11. Диагностика

| Симптом | Вероятная причина | Что делать |
|---|---|---|
| `flutter: command not found` | Окружение не подключено в этом терминале | `source ~/.flutter_env.sh`; проверьте, что в `~/.zshrc` есть строка подключения |
| `Unable to locate Android SDK` / `No valid Android SDK platforms found` | Платформа не установилась | Перезапустите скрипт; вручную: `yes \| sdkmanager "platforms;android-36" "build-tools;36.0.0"` |
| Doctor ругается на лицензии | Лицензии Android не приняты | `flutter doctor --android-licenses`, везде `y` |
| `Waiting for another flutter command to release the startup lock...` | Блокировка на общем томе или зависший процесс | Закройте другие `flutter`; если не помогает, ставьте SDK локально (`SDK_BASE=~/goinfre`) |
| `No space left on device` | Забит home | Раздел [7](#7-дисковое-место): `flutter clean`, `du`, чистка кэшей |
| `adb devices`: пусто / `unauthorized` / `no permissions` | Кабель, подтверждение, udev | Раздел [6](#6-тестирование-на-устройствах) |
| Телефон то появляется, то пропадает | Конфликт `adb` | `adb kill-server && adb devices`; используйте только наш `adb` (первый в `PATH`) |
| Первая сборка очень долгая | Пустой goinfre на новой машине | Подождать: Gradle и pub качают кэши единоразово |
| Ошибки «duplicate definition» после миграции | Смешаны старый и новый Material | Оставить один импорт ([раздел 4](#4-важно-material_ui-вместо-fluttermaterialdart)) |
| `flutter test` красный после `flutter create` | Остался тест от примера-счётчика | Заменить `test/widget_test.dart` (см. [docs/00-ex00.md](docs/00-ex00.md#7-диагностика)) |
| `event not found: .]` | zsh трактует `!` как историю | Использовать `~/.??*` вместо `~/.[!.]*` |
| Chrome не запускается | Нет Google Chrome, есть Chromium | Скрипт выставит `CHROME_EXECUTABLE`; иначе `flutter run -d web-server` |
